# 관리자 보안 구성

> 2026-10-14 프로젝트 오너 결정에 따라 지시서 §12의 WebAuthn/FIDO2 보안 키 인증은 **구현하지 않는다**(FIDO 장치 없음). 아래 통제로 대체한다.

## 인증과 세션

| 통제 | 구현 |
|---|---|
| 분리된 콘솔 | `admin.<domain>`에서 별도 Worker가 서빙한다. 플레이어 사이트에는 관리자 화면이 없다 |
| 별도 세션 | 쿠키 `jc_asid`(HttpOnly, Secure, **SameSite=Strict**). 플레이어 쿠키(`jc_sid`)로는 관리자 API에 접근할 수 없다 |
| 세션 수명 | 유휴 30분, 최대 8시간. 토큰은 D1에 SHA-256 해시로만 저장한다 |
| 권한 판정 | 매 요청마다 D1의 `users.role`을 다시 읽는다(클라이언트 값은 쓰지 않음). 그 역할로 아래 "권한 매트릭스"의 규칙을 적용한다. 강등되면 관리자 세션을 즉시 폐기한다 |
| 출처 검사 | `/api/admin/*` 요청의 Origin은 `ADMIN_ORIGIN`과 같아야 한다 |
| 시도 제한 | 로그인은 계정당 15분에 5회, IP당 15분에 20회. 재확인은 15분에 10회. 실패는 감사 로그에 남긴다 |
| 비밀번호 저장 | PBKDF2-SHA256 100,000회, 솔트 16바이트, 상수 시간 비교 |

## 민감 작업 재확인

다음 작업은 최근 5분 안에 비밀번호를 다시 입력해야 한다(`POST /api/admin/auth/reauth`). 콘솔이 자동으로 비밀번호 창을 띄운다.

- 회원 정지·해제, 권한 변경(슈퍼관리자만). 해제와 권한 변경도 사유(2–200자)가 필요하다. 콘솔은 실행 전에 변경 전 → 후(상태·권한)와 현재 정지 사유를 보여 주고, 감사 기록에 사유와 변경 전후를 남긴다(`user.suspend` `{reason, from, to, previousReason}`, `user.unsuspend` `{reason, from, to, suspendedReason}`, `user.role` `{from, to, reason}`). 정지는 활성 회원에만 한 번 적용된다: 이미 정지된 회원은 409 `already_suspended`로 거절해 사유를 덮어쓰거나 제재 쪽지를 다시 보내지 않고, 두 관리자가 동시에 눌러도 조건부 갱신이라 하나만 반영된다. 탈퇴한 계정은 404로, 정지 뒤 해제로 `active`가 되살아나는 경로를 막았다(PART C 전에는 탈퇴 계정도 정지·해제되어 `active`로 돌아갔다)
- 회원 강제 연결 종료(로그인 세션 삭제와 테이블 연결 종료, `user.disconnect` 감사 기록에 사유·결과)
- 가상 칩 지급·차감(멱등 키, 음수 잔액 불가, 절대값 100,000 이상은 슈퍼관리자만: 아래 "가상 칩 조정과 정합성 정정")
- 비밀번호 재설정 링크 발급(자기 계정은 불가, 비밀번호 변경 사용)
- 회원 정보 CSV 내보내기(슈퍼관리자만, `user.export` 감사 기록)

대상이 관리자(ADMIN·SUPER_ADMIN)일 때 정지·해제, 강제 연결 종료, 칩 조정, 재설정 링크 발급은 슈퍼관리자만 할 수 있다. 재설정 링크는 계정을 넘겨받을 수 있는 토큰이기 때문이다.
- 테이블 종료(진행 중 핸드가 끝난 뒤 전원 환급)
- 테이블 긴급 제어: 새 핸드 중단·재개, 신규 입장 차단·해제(사유 필수, `table.control` 감사 기록에 사유와 룸 반영 여부)
- 테이블 설정의 동시 수정: 설정 수정(`PATCH /tables/:id`)은 읽은 행이 그대로일 때만 쓰고, 그 사이 다른 관리자의 수정·긴급 제어가 끼어들면 다시 읽어 보낸 열만 얹는다. 그래서 이름 변경과 입장 차단이 동시에 와도 둘 다 남는다. 콘솔은 보던 `updatedAt`을 함께 보낸다. 다른 관리자가 먼저 바꿨으면 409 `table_conflict`로 거절하고(`table.update.failed` 감사), 화면을 다시 불러와 확인한 뒤 다시 저장하게 한다.
- 종료된 핸드의 전체 카드 열람(`hand.view_sensitive` 감사 기록)
- 정합성 이벤트 해결 처리(메모만 남기기, 차이를 원장에 기록, 잔액 되돌리기: 기록·되돌리기는 슈퍼관리자만)
- 무료 칩 보충 정책 변경(최고 관리자만), 새 보충 긴급 중지(관리자)·재개(최고 관리자만). 모두 사유가 필요하고 `refill.policy`(변경 전후)·`refill.pause`·`refill.resume`으로 남는다
- 테이블 봇 정책 변경(켜기·기금 한도·최대 봇 수, 최고 관리자만, 다시 켜기도 여기서만)과 긴급 중지(기능 `bots`가 있는 관리자). 둘 다 사유가 필요하고 `bots.policy`(변경 전후, 반영한 룸 수)·`bots.stop`으로 남는다. 봇 계정에는 회원 관리 조치(정지·칩 조정·권한·재설정 링크 등)를 할 수 없다(409 `bot_account`)
- 추천 보상 정책 변경(켜기·양쪽 보상액·하루/누적 한도·필요 핸드 수·검토 기준, 최고 관리자만)과 지급 일시중지(기능 `referral`이 있는 관리자)·재개(최고 관리자만), 검토 대기 추천의 승인, 대기·검토 추천의 거절. 모두 사유가 필요하고 `referral.policy`(변경 전후)·`referral.pause`·`referral.resume`·`referral.approve`·`referral.reject`로 남는다. 다시 정산(`referral.settle`)은 재확인 없이 감사 기록만 남는다(한쪽에 한 번 넘게 지급하지 않음). 감사 기록에는 추천 상태·실패 코드·지급액만 담고 이메일·네트워크 같은 회원 정보는 담지 않는다. 거절은 이미 지급한 칩을 회수하지 않으며, 회수는 회원 칩 조정(`refLedgerId`)으로 한다
- 서비스 점검 예약·변경·지금 종료·취소(사유 필수, `maintenance.*` 감사 기록에 사유와 룸 반영 결과). 공지 작성·수정·내리기·삭제는 재확인 없이 감사 기록만 남는다(`service.notice.*`)
- 회원 계정 설정 초기화·복구(기능 `settings`, 아래 "계정 설정 동기화 관리")
- VIP 회원 지정·색 변경·해제(기능 `vip`, 아래 "VIP 회원 관리")
- 시간 은행 정책 변경(최고 관리자만)과 테이블 타이머 복구(기능 `tableControl`). 둘 다 사유가 필요하고 `timebank.policy`(변경 전후, 적용 경계, 반영한 룸 수)·`table.timer_recover`로 남는다(아래 "시간 은행 관리")
- 소셜 정책 변경(빠른 반응 켜기·간격·횟수, 운영진 표시, 최고 관리자만). 사유가 필요하고 `social.policy`(변경 전후, 회원에게 바뀌는 것, 반영한 룸 수)로 남는다(아래 "소셜 운영")

## 계정 설정 동기화 관리

`apps/api/src/routes/admin-settings.ts`, 콘솔은 회원 상세의 "계정 설정" 패널(`apps/admin/src/pages/MemberSettings.tsx`).

- **보는 것(진단에 필요한 최소)**: 저장 여부, 버전(`rev`), 초기화 세대(`epoch`), 저장 형식 버전, 값이 있는 설정 수(7개 중), 즐겨찾기 수, 마지막 변경 시각, 회원 기기의 마지막 동기화 시각(10분 단위), 마지막 초기화(시각·관리자·복구 가능 기한·복구 시각). **설정 값과 즐겨찾기 테이블은 응답에 없다.** 조회는 회원 ID·닉네임과 개수만 담아 감사 로그에 남기지 않는다(회원 상세 `user.view`가 이미 남음).
- **편집 없음**: 관리자가 회원의 설정을 특정 값으로 바꾸는 API·화면은 만들지 않았다. 할 수 있는 것은 초기화와 그 초기화의 복구뿐이다.
- **초기화**: 동기화 대상 설정 전부(`SYNCED_PREF_KEYS`)와 즐겨찾기를 기본값으로 되돌리고 `epoch`을 올린다. 회원 기기는 다음 동기화 때(저장은 409 `settings_reset`, 불러오기는 바뀐 `epoch`) 아직 저장하지 못한 변경을 버리고 계정 값을 받는다. 동기화 이전 기기 설정(`legacy`)은 `epoch` 0일 때만 받으므로, **서버 설정을 지워도 기존 기기의 로컬 설정이 다시 올라오지 않는다.** 저장한 적 없는 계정도 초기화할 수 있다(기기에 남은 이전 설정이 올라오지 않게 막는 용도, 되돌릴 것은 없음). 기기마다 남는 설정(사운드·최근 테이블·설치 안내)은 건드리지 않는다. 자동 머크는 2026-10-19부터 설정이 아니어서 테이블에 아무것도 보내지 않는다(이전 기기가 저장한 칸은 다른 칸처럼 초기화·복구된다).
- **복구**: 초기화 직전 값(값과 변경 시각)을 그 행에 보관해 두고, 7일(`SETTINGS_RESTORE_MS`) 안에 회원이 아무것도 바꾸지 않았을 때만 한 번 되돌린다(`epoch`을 다시 올림). 회원이 그 사이 바꿨거나 기한이 지났거나 이미 복구했으면 409 `settings_not_restorable`.
- **미리보기·재확인·사유**: 둘 다 `preview: true`로 범위(지울·되돌릴 설정 수와 즐겨찾기 수, 착석한 테이블 수, 복구 가능 기간)를 먼저 보여 주고, 실행은 비밀번호 재확인과 사유(2–200자)를 받는다. 미리보기도 아래 역할 검사를 거친다.
- **동시 수정**: 요청은 관리자가 보던 `rev`를 담는다. 그 사이 회원·다른 관리자가 바꿨으면 409 `settings_changed`(지금 상태를 `details.settings`로), 이미 초기화된 뒤 바뀐 것이 없으면 409 `settings_already_reset`. 쓰기 자체도 같은 `rev`·`epoch` 조건을 건 한 문장이라 두 관리자가 동시에 눌러도 하나만 성공한다.
- **대상 제한**: 자기 계정 400, 탈퇴 회원 404, 테이블 봇 409 `bot_account`, 관리자 계정은 `admins.manage`(최고 관리자)만(그 밖은 403).
- **회원 안내**: 초기화·복구가 실제로 쓰인 경우에만 같은 D1 batch에서 쪽지 한 통(카테고리 `admin`, 계정 언어 ko·en)을 쓴다. 쪽지에 관리자의 사유는 넣지 않는다.
- **감사 기록**: `settings.reset` `{reason, before{rev, epoch, fields, favourites}, after{…}, restorable}`, `settings.restore` `{reason, resetAt, before, after}`(2026-10-19 이전 기록에는 `muck`이 있다). 개수만 담고 설정 값·즐겨찾기 테이블은 담지 않는다. 거절은 `settings.reset.failed`·`settings.restore.failed`.
- **운영 통계**: 날짜별 저장·병합 충돌·밀린 변경·초기화 뒤 거절·실패 이유별(입력·요청 제한·경합·오류·불러오기·기기에서 실패)·초기화·복구 횟수(`ss_*`, 운영 통계의 "계정 설정 동기화" 카드). 회원별 수치는 없다.
- 토너먼트(6인 SNG): 조회·대회 만들기·등록 마감·시작·일시정지·재개·복구는 기능 `tournaments`(위임 가능), 시작 전 취소와 운영 중단은 여기에 비밀번호 재확인·사유를 더하고 운영 중단은 대회 이름 입력까지 받는다. 템플릿(대회 구조) 관리는 능력 `tournament.structure`(최고 관리자만). 시작 뒤 스택·카드·승자·순위를 바꾸는 경로는 없다. 대회 테이블에는 테이블 종료·긴급 제어·설정 변경이 409 `tournament_table`로 막힌다(턴 타이머 복구는 그대로). 자세한 규칙은 `docs/TOURNAMENT.md`

## 시간 은행 관리

`apps/api/src/routes/admin-timebank.ts`, 콘솔은 "테이블 → 시간 은행"(`apps/admin/src/pages/TimeBank.tsx`)과 테이블 상세의 "턴 타이머" 패널.

- **정책(최고 관리자만)**: 켜기, 회원 방에도 켜기, 처음 지급(0–120초), 최대 보유(5–300초), 한 번 사용(5–60초), 보충(1–100핸드마다 0–60초). 모두 초 단위이고, 처음 지급과 한 번 사용은 최대 보유를 넘을 수 없다. 정책은 덮어쓰지 않고 버전으로 쌓인다(`time_bank_policies`, 최근 20개를 변경 이력으로 보여 준다). 마이그레이션 0025가 버전 1(켜짐, 30초·60초·10초·10핸드마다 5초)을 넣는다.
- **적용 경계**: 새 버전은 각 테이블의 **다음 핸드부터** 적용된다. 진행 중인 핸드는 받은 규칙을 그대로 쓰고, 진행 중인 차례의 마감 시각과 이미 더한 시간은 바뀌지 않는다. 최대를 낮추면 넘는 남은 시간은 그 회원이 다음 핸드를 받을 때 줄어든다(미리보기의 `cutToMax`). 콘솔은 정책 화면 맨 위와 미리보기에 이 경계를 적고, 테이블 상세에는 이 핸드의 규칙과 다음 핸드의 규칙(버전)을 따로 보여 준다.
- **미리보기·재확인·사유·동시 수정**: `preview: true`로 정책 전 → 후, 적용 경계, 바뀌는 테이블 수(회원 방 설정이 바뀌면 회원 방 포함)와 그중 지금 핸드를 진행 중인 수를 먼저 보여 주고, 저장은 비밀번호 재확인과 사유(2–200자)를 받는다. 요청은 관리자가 보던 `baseVersion`을 담는다. 그 사이 다른 관리자가 저장했으면 409 `time_bank_policy_conflict`(지금 정책을 `details.policy`로)로 거절한다. 쓰기도 "최신 버전이 그대로일 때만" 넣는 한 문장이라 동시에 눌러도 하나만 저장된다. 바뀐 값이 없으면 400 `time_bank_no_change`.
- **룸 반영**: 저장 뒤 플레이 중인 테이블(최대 100곳)에 정책을 다시 읽게 하고, 물은 곳·답한 곳·답하지 않은 곳을 화면과 감사 기록에 남긴다. 답하지 않은 룸도 다음 핸드를 기록할 때(같은 D1 batch) 새 정책을 읽는다. 어느 쪽이든 적용은 다음 핸드부터다.
- **개인 시간 편집 없음**: 관리자가 회원 한 명의 남은 시간을 정하거나 더하거나 지우는 API·화면은 만들지 않았다. 테이블 상세는 좌석별 남은 시간을 읽기만 한다. 정책 변경은 모든 회원에게 같게 적용되는 규칙이라 회원별 쪽지를 보내지 않는다(다음 핸드부터 테이블 화면의 남은 시간·버튼이 새 값을 보여 준다).
- **타이머 복구(정해진 복구 정책)**: 테이블 진단이 `timer_unarmed`(진행 중인 차례에 알람이 없거나 마감보다 늦음)나 `turn_overdue`(마감이 5초 넘게 지남)를 보이면, 관리자(기능 `tableControl`, 재확인·사유)가 `POST /tables/:id/timer-recover`로 룸에 자기 규칙을 지금 적용하게 한다. 마감이 지났으면 알람이 했을 처리(회원은 체크 또는 폴드 타임아웃, 봇은 행동)를 하고, 아니면 알람을 다시 건다. 누구의 시간·스택·카드·결과도 바꾸지 않으며, 다시 보내도 같은 차례를 두 번 처리하지 않는다. 감사 `table.timer_recover`에 사유, 룸이 답했는지, 결과(`timed_out`·`bot_moved`, 알람만 다시 건 `rearmed`, 걸 알람이 없는 `none`), 핸드, 마감, 지연, 복구 전후 알람을 남긴다. 룸이 답하지 않아도 감사에 남기고 503 `room_unavailable`을 돌려준다.
- **진단**: 테이블 상세의 "턴 타이머" 패널은 차례 시작·기본 턴 시간·시간 은행으로 더한 시간·마감·알람 시각·지연(`live.timer`)과 정상·지연·알람 없음 상태를 보여 준다. "시간 은행" 패널은 이 핸드와 다음 핸드의 규칙, 이 핸드의 사용 횟수, 일어선 뒤 보관 중인 회원 수, 좌석별 남은 시간을 보여 준다. 카드 정보는 없다.
- **감사 기록**: `timebank.policy` `{from, to, reason, appliesFrom, rooms{tables, reached, more}}`, `table.timer_recover`. 거절(409·400·403)은 `timebank.policy.failed`·`table.timer_recover.failed`로 남는다. 조회(`GET /time-bank`)는 회원 정보가 없어 남기지 않는다.
- **운영 통계**: 날짜별 사용 횟수(`tb_use`), 사용한 초(`tb_sec`), 남은 시간 부족 거절(`tb_empty`), 더한 시간까지 다 쓴 타임아웃(`tb_expired`), 알람이 5초 넘게 늦은 타임아웃(`tb_late`), 타이머 복구(`tb_recover`), 시간 초과로 서버가 체크·폴드한 모든 턴(`tb_timeout`, `tb_expired`는 그 일부). 운영 통계의 "시간 은행" 카드와 정책 화면의 기간별 표에 보인다. 회원별 수치는 없다.

## 소셜 운영

`apps/api/src/routes/admin-social.ts`, 콘솔은 "테이블 → 소셜 운영"(`apps/admin/src/pages/Social.tsx`, 메뉴를 새로 만들지 않고 테이블 화면의 링크)과 테이블 상세 "턴 타이머" 패널의 정책 버전 표시.

- **정책(최고 관리자만)**: 빠른 반응 켜기, 회원당 반응 간격(0.5–30초), 구간 안 최대 횟수(1–20회)와 구간(5–300초), 다른 회원에게 최고 관리자 표시·관리자 표시를 보일지. 버전으로 쌓이고(`social_policies`, 최근 20개를 변경 이력으로) 마이그레이션 0028이 이전 동작과 같은 버전 1(켜짐, 2초, 30초 5회, 두 표시 모두 보임)을 넣는다. 정책 행이 없거나 읽을 수 없으면 모든 읽는 쪽이 같은 기본값(`SOCIAL_DEFAULTS`)을 쓴다.
- **표시 숨김의 범위**: 숨기면 회원이 보는 응답(좌석·테이블 채팅·로비의 방장·게시판 글과 댓글·친구 목록·핸드 기록과 리플레이)에서 그 역할의 `role`을 뺀다. 역할 자체·권한·관리자 콘솔(회원 목록·게시판 관리 등은 실제 역할을 그대로 보여 줌)은 바뀌지 않고, 운영진 차단·신고 규칙(`block_staff`·`report_super_admin`)도 실제 역할로 정한다. 저장된 채팅 줄과 좌석은 역할을 가지고 있으므로 다시 보이게 하면 돌아온다. 회원 한 명의 표시를 따로 바꾸는 경로는 없다(역할은 여전히 `POST /users/:id/role`로만).
- **적용 시점**: api 응답은 다음 요청부터(운영진이 들어 있는 응답에서만 요청당 한 번 D1을 읽는다). 룸은 저장 직후 연결이 있는 열린·종료 중 테이블(연결 많은 순 최대 100곳)이 다시 읽고(한 번 더 시도), 물은 곳·답한 곳·답하지 않은 곳을 화면과 감사 기록에 남긴다. 답하지 않았거나 100곳 밖의 룸은 다음 핸드를 기록할 때(같은 D1 batch) 읽는다. 표시가 바뀌면 룸이 화면의 채팅을 다시 보내고 좌석은 다음 상태부터 바뀐다.
- **미리보기·재확인·사유·동시 수정**: `preview: true`로 정책 전 → 후, 회원에게 바뀌는 것(반응 켜짐·꺼짐, 제한 변경, 새로 보이거나 숨는 표시), 다시 읽힐 테이블 수(100곳 넘으면 표시)를 먼저 보여 주고, 저장은 비밀번호 재확인과 사유(2–200자)를 받는다. 요청은 관리자가 보던 `baseVersion`을 담고, 그 사이 다른 관리자가 저장했으면 409 `social_policy_conflict`(지금 정책을 `details.policy`로). 쓰기도 "최신 버전이 그대로일 때만" 넣는 한 문장이라 동시에 눌러도 하나만 저장된다. 바뀐 값이 없으면 400 `social_no_change`.
- **회원 안내**: 서비스 전체에 같게 적용되는 표시 규칙이라 회원별 쪽지를 보내지 않는다(테이블 화면의 반응 버튼이 바로 꺼지거나 새 간격을 따른다).
- **감사 기록**: `social.policy` `{from, to, reason, effects{reactions, limits, badgesShown, badgesHidden}, appliesFrom, rooms{tables, reached, more}}`. 거절(409·400·403)은 `social.policy.failed`. 조회(`GET /social`)는 회원 정보가 없어 남기지 않는다.
- **권한**: 조회는 기능 `social`(스위치 `tables`, 테이블 업무), 변경은 능력 `social.policy`(최고 관리자, 스위치로 넘겨줄 수 없음).

## VIP 회원 관리

`apps/api/src/routes/admin-vip.ts`, 콘솔은 회원 상세의 "VIP 회원 관리" 패널(`apps/admin/src/pages/MemberVip.tsx`)과 회원 목록의 VIP 열·필터. 메뉴는 새로 만들지 않았다.

- **무엇인가**: 일반 회원의 이름 색과 VIP 표시(`users.vip_color`, 팔레트 6색 `gold`·`rose`·`sapphire`·`amethyst`·`emerald`·`cyan`)뿐이다. `users.role`이 아니고, 서버의 어떤 권한 검사·칩·원장·좌석·대기·토너먼트·게임 규칙·푸시에도 쓰이지 않는다. 만료가 없고, 바꿀 때마다 `vip_version`이 오르며 바꾼 사람·시각(`vip_changed_by`·`vip_changed_at`)을 남긴다(마이그레이션 0031).
- **권한**: 기능 `vip`. 최고 관리자는 항상, 관리자는 최고 관리자가 스위치를 켰을 때만(꺼져 있으면 조회·미리보기·변경 모두 403 `permission_off`, `user.vip_view.failed`·`user.vip.failed`). 회원은 관리자 콘솔에 들어올 수 없고, 회원 API(`PATCH /api/auth/me` 등)는 VIP 필드를 읽지 않는다. 콘솔이 버튼을 숨기는 것과 관계없이 서버가 판정한다.
- **대상**: 활동 중이거나 정지된 일반 회원만. 테이블 봇 409 `bot_account`, 관리자·최고 관리자 409 `vip_staff`(자기 자신 포함), 탈퇴 409 `vip_deleted`. 이런 계정에 남은 색은 해제할 수 있다. 정지된 회원은 색을 유지하되 정지가 풀릴 때까지 다른 회원에게 보이지 않고, 탈퇴하면 색이 지워진다. 회원을 관리자로 바꾸면 VIP가 끝나고(역할 변경 미리보기에 `vipCleared`, 감사 `user.vip` `cause: 'role'`), 다시 회원으로 바꿔도 돌아오지 않는다.
- **미리보기·재확인·사유·동시 수정**: 지정(색을 고르지 않으면 금색)·색 변경·해제 모두 먼저 서버 미리보기(전 → 후 색, 이름이 다시 그려질 테이블 수)를 보이고, 저장은 비밀번호 재확인과 사유(2–200자)를 받는다. 요청은 패널이 보던 `expectedVersion`을 담고, 그 사이 다른 관리자가 바꿨으면 409 `vip_conflict`(지금 상태를 `details.vip`로)로 거절해 패널이 지금 상태를 다시 보여 준다. 쓰기는 "버전이 그대로일 때만" 바꾸는 한 문장이라 동시에 눌러도 하나만 된다. 이미 그 상태인 요청은 아무것도 바꾸지 않고 `changed: false`로 답한다.
- **반영**: 회원이 보는 응답은 다음 요청부터(이름과 같은 JOIN에서 읽어 목록 길이만큼 쿼리가 늘지 않는다). 그 회원이 앉아 있는 테이블의 룸은 저장 직후 좌석 표시만 바꿔 다시 보낸다: 연결을 끊거나 핸드·차례·마감·스택을 건드리지 않는다. 같은 회원의 다른 기기는 다음 내 정보 요청·테이블 연결·목록 새로고침에서 받는다(새 푸시나 알림은 보내지 않는다). 지난 핸드 기록·리플레이는 바꾸지 않는다. 이미 보낸 채팅 줄은 보낸 때의 색을 유지한다.
- **감사 기록**: `user.vip` `{from, to, reason, change: assign|color|remove, version}`(바뀐 것이 없으면 `changed: false`), 역할 변경으로 끝난 VIP는 `{from, to: null, reason, cause: 'role', role, version}`. 거절(400·403·409)은 `user.vip.failed`(사유 본문 없음). 조회(`GET /users/:id/vip`)는 거절만 남긴다.
- **되돌리기(0031)**: 새 열 4개와 인덱스 1개만 더하므로, 되돌릴 때는 `DROP INDEX users_vip_idx` 뒤 `users`의 `vip_color`·`vip_version`·`vip_changed_by`·`vip_changed_at`를 지우면 된다. 다른 테이블·원장은 건드리지 않는다.

## 권한 매트릭스

- 모든 관리자 API(`/api/admin/*`, 로그인·재확인 `/auth` 제외)는 `apps/api/src/lib/permissions.ts`의 `ROUTE_RULES`에 규칙이 하나씩 있다. 규칙은 기능(32개), 감사 이름, 최소 역할(ADMIN 또는 SUPER_ADMIN), 재확인 여부, 미리보기 지원 여부를 정한다. `requirePermission`이 라우트 실행 전에 역할 → 기능 스위치(아래 "관리자별 기능 권한") → 재확인 순서로 적용하고, **규칙이 없는 라우트는 403 `no permission rule for this action`으로 닫힌다**(새 라우트를 만들고 규칙을 빠뜨리면 열리지 않는다). 단위 테스트가 실제 라우트 목록과 표를 맞춰 본다.
- 요청 내용에 따라 달라지는 권한은 능력(capability)으로 이름을 붙였고, 지금은 모두 슈퍼관리자 전용이다.

| 능력 | 뜻 |
|---|---|

- 역할별 표는 코드에 있다. 역할이 허용하는 범위를 바꾸려면 검토를 거친 코드 변경이 필요하다. 콘솔의 "보안" 화면은 표를 읽기 전용으로 보여 준다(`GET /api/admin/security/permissions`, 내 능력·기능별 일반 관리자 가능 여부·재확인 여부·기능이 기대는 스위치, 내 스위치와 기능별로 실제 쓸 수 있는 작업 수 `effective`).
- 콘솔은 `GET /api/admin/auth/me`의 `permissions`(능력)와 `grants`(켜진 스위치)로 할 수 없는 메뉴·버튼을 숨기거나 막고 이유를 보여 주지만(예: 내보내기), 판정은 언제나 서버가 한다. 주소를 직접 열어도 서버가 거절한다.
- 역할을 바꾸면 그 회원의 관리자 콘솔 세션을 모두 지운다. 다른 관리자의 권한이 바뀌거나 세션이 지워져도, 그 콘솔은 다음 요청부터 바로 바뀐 권한으로 판정되거나 로그인 화면으로 돌아간다(콘솔은 `not an administrator`·`super admin only`·`permission_off`를 받으면 내 정보를 다시 읽는다).

## 관리자별 기능 권한

- **유효 권한 = 역할이 허용하는 범위(위 표) ∩ 최고관리자가 켜 둔 기능 스위치.** 스위치는 관리자마다 D1 `admin_permissions`(관리자 ID, 켜진 스위치 JSON, 버전, 바꾼 사람·시각)에 저장하고, 서버가 요청마다 읽는다(요청 안에서 한 번). 최고관리자는 모든 스위치가 켜진 것으로 보고 스위치가 없다. 일반 관리자는 행이 없거나 목록에 없는 기능이 모두 꺼져 있다(**기본 거부**). 나중에 코드에 더하는 스위치도 최고관리자가 켜기 전까지 꺼져 있다.
- **스위치(24개, `GRANTS`)**: VIP 회원 지정·색 변경·해제(`vip`, 0031에서 추가, 기존 관리자에게는 꺼진 채로 시작), 대시보드 조회(`dashboard`), 회원 조회(`members`, 회원 메모 포함), 회원 정지·해제(`sanctions`), 회원 강제 연결 종료(`disconnect`), 신고 조회·처리(`reports`), 게시판 관리(`board`), 공지 발송(`notices`), 쪽지 발송(`messages`), 테이블 생성·수정(`tables`, 소셜 정책 조회 포함), 테이블 긴급 제어(`tableControl`, 종료·타이머 복구 포함), 소액 칩 조정(`chips`), 원장 조회(`ledger`), 경제 통계(`economy`), 운영 통계(`stats`, 아카데미 통계 포함), 추천인 운영(`referral`), 봇 운영(`bots`), 그리고 기존 기능인 대회 진행(`tournaments`), 무료 칩 보충(`refill`), 핸드 기록(`hands`, 종료 핸드 카드 열람 포함), 정합성 점검(`reconcile`), 계정 설정 진단(`settings`), 재설정 링크(`resetLinks`), 점검 공지(`maintenance`, 브랜드 상태 조회 포함). 0028에서 기능 `social`·`brand`를 더했지만 새 스위치는 만들지 않고 같은 업무의 스위치에 붙였다(기존 관리자는 스위치를 다시 켜지 않아도 배포 직후 새 화면을 본다).
- **넘겨줄 수 없는 것**: 관리자 권한 설정(`admins.grants`), 최고관리자 지정·강등(`roles.change`), 관리자·최고관리자 제재(`admins.manage`), 고액 칩 조정(`chips.large`), 원장 정합성 직접 보정(`ledger.correct`), 회원 정보 대량 내보내기(`members.export`), 각종 정책 변경(`*.policy`, `tournament.structure`)은 능력(역할)으로만 정해지고 스위치가 없다. 시스템 비밀(Cloudflare secret, 메일 키 등)은 콘솔 API가 아예 없다. 감사 로그(자기 기록)와 보안 화면(자기 세션·권한)은 모든 관리자에게 항상 열려 있다.
- **거절**: 역할 밖이면 403 `forbidden`(`super admin only`), 역할은 되지만 스위치가 꺼져 있으면 403 `permission_off`(`this feature is turned off for your account`). 미리보기도 똑같이 거절하고, 둘 다 `<action>.failed`로 실패 감사에 남는다(요청 본문은 남기지 않는다). 한 라우트가 여러 기능의 정보를 돌려주면 라우트가 직접 나눈다: 회원 상세는 `ledger`가 꺼지면 원장, `reports`가 꺼지면 최근 신고를 빼고 `hidden`에 적으며, 회원 이력은 신고 항목을 뺀다. 테이블 수정으로 입장을 막는 것(`entryBlocked`)은 긴급 제어와 같아서 `tableControl`과 재확인을 함께 요구한다.
- **바꾸기(최고관리자만)**: `GET /api/admin/security/admins`(닉네임·ID 검색, 역할 필터, 서버 페이지, 이메일 없음), `GET /api/admin/security/admins/:id`(스위치·버전·기능별 실제 권한·변경 이력, 이력에 IP 없음), `PUT /api/admin/security/admins/:id/grants` `{grants, baseVersion, reason, preview?}`. 본인(400 `cannot change your own permissions`), 최고관리자·회원(409 `not_plain_admin`), 그 사이 다른 최고관리자가 저장한 경우(409 `admin_grants_conflict`, 지금 스위치·버전을 `details`로), 바뀐 것이 없는 경우(400 `admin_grants_no_change`)는 거절한다. 미리보기는 켜지고 꺼지는 스위치와 쓸 수 있는 작업 수 전 → 후를 보여 주고 아무것도 쓰지 않는다. 저장은 비밀번호 재확인과 사유(2–200자)를 받고, "아직 일반 관리자이고 버전이 그대로일 때만" 쓰는 한 문장이라 동시에 저장해도 하나만 된다.
- **적용 시점**: 저장 즉시, 그 관리자의 **다음 요청부터**(세션은 그대로). 콘솔은 `permission_off`를 받으면 내 정보를 다시 읽어 메뉴를 고친다.
- **역할 변경과의 관계**: 역할을 바꾸면(관리자 ↔ 최고관리자 ↔ 회원) 같은 batch에서 스위치 행을 지운다. 최고관리자를 관리자로 내리거나 회원을 관리자로 올리면 스위치가 모두 꺼진 채로 시작하고, 권한 변경 미리보기가 `grantsCleared`로 이를 알린다. 감사 `admin.grants.reset` `{before, after: [], reason, cause: 'role', from, to}`.
- **감사**: `admin.grants.update` `{before, after, gained, lost, reason, version}`, `admin.grants.reset`, 실패는 `admin.grants.update.failed`·`admin.grants.list.failed`·`admin.grants.view.failed`. 목록·상세 조회 성공은 개인정보가 없어 남기지 않는다.
- **스위치끼리의 관계**: 서버는 스위치를 서로 묶지 않는다(각 라우트는 자기 스위치만 본다). 다만 회원 제재·연결 종료·칩 조정·재설정 링크·계정 설정은 회원 상세 화면에서, 긴급 제어는 테이블 화면에서 쓰므로 `members`·`tables` 없이 켜면 콘솔에서 찾아 쓸 수 없다. 편집기가 이를 경고한다.
- **콘솔**: "보안" 화면의 "내 권한"에 내 스위치(켜짐·꺼짐)와 실제로 쓸 수 있는 작업 수, 권한 표에 기능별 스위치 열(스위치 이름·항상·최고관리자 전용), 최고관리자에게만 "관리자별 권한" 패널(검색·역할 필터·페이지, 메뉴별로 묶은 스위치, 스위치가 여는 기능과 작업 수, 빠진 스위치 경고, 저장하면 쓸 수 있는 작업 수, 사유, 미리보기, 충돌 시 최신 상태 다시 읽기, 변경 이력과 더 보기)이 있다. 메뉴는 켜진 스위치에 맞춰 보이고, 대시보드가 꺼진 관리자의 첫 화면은 안내로 바뀐다.
- **배포 전 관리자**: 마이그레이션 `0027_admin_permissions`가 그때 있던 모든 일반 관리자에게 스위치 23개를 모두 켜 두므로, 배포 직후 기존 관리자가 할 수 있는 일은 그대로다. 마이그레이션과 API 배포 사이에 새로 관리자가 된 계정은 행이 없어 모든 기능이 꺼진 채로 시작한다(최고관리자가 켜면 된다).

## 변경 미리보기

회원 정지·해제·강제 연결 종료·권한 변경·칩 조정, 테이블 종료와 신고 처리(B9), 무료 칩 보충 정책 변경, 테이블 봇 정책 변경, 추천 보상 정책 변경, 시간 은행 정책 변경, 소셜 정책 변경, 회원 계정 설정 초기화·복구는 실행 전에 무엇이 바뀌는지 먼저 보여 준다. 같은 라우트에 `preview: true`를 보내면 아무것도 쓰지 않고 다음을 돌려준다.

| 작업 | 미리보기 |
|---|---|
| 정지 | 회원 상태·권한, 끝나는 로그인 세션 수(게임·관리자 콘솔), 일어나게 되는 좌석(테이블·바이인) |
| 강제 연결 종료 | 위와 같고, 테이블에서 내보낼지 여부 |
| 정지 해제 | 상태 변경 전 → 후, 현재 정지 사유 |
| 권한 변경 | 권한 전 → 후, 관리자 콘솔 접속 가능 여부 전 → 후, 끝나는 관리자 콘솔 세션 수, 얻고 잃는 능력 |
| 칩 조정 | 잔액 전 → 후, 큰 금액 여부, 같은 요청을 이미 처리했는지(중복이면 실행 버튼이 막힌다) |
| 테이블 종료 | 앉은 회원과 스택(룸이 답하면), 바이인, 테이블 위 칩, 진행 중 핸드 여부, 대기자 수 |
| 무료 칩 보충 정책 | 정책 전 → 후, 적용 시점(다음 청구부터, 이미 시작된 대기 시간은 그대로), 지금 대기 중인 회원 수 |
| 테이블 봇 정책 | 정책 전 → 후, 적용 시점(테이블마다 핸드 사이, 진행 중 핸드는 그대로), 봇을 허용한 테이블 수, 지금 앉은 봇 수, 발행한 기금과 남는 한도 |
| 추천 보상 정책 | 정책 전 → 후, 적용 시점(보상액·필요 핸드 수는 다음 가입부터, 한도는 다음 지급부터, 이미 받아들인 추천은 가입 당시 약속대로), 지금 지급·검토 대기 중인 추천 수 |
| 시간 은행 정책 | 정책 전 → 후, 적용 경계(각 테이블의 다음 핸드부터, 진행 중인 턴의 마감 시각은 그대로), 바뀌는 테이블 수와 그중 지금 핸드를 진행 중인 수, 최대를 낮춰 줄어들 남은 시간이 있는지 |
| 소셜 정책 | 정책 전 → 후, 회원에게 바뀌는 것(반응 켜짐·꺼짐, 간격·횟수 변경, 새로 보이거나 숨는 운영진 표시), 적용 시점(api는 다음 요청부터, 룸은 저장 직후 다시 읽음), 다시 읽힐 테이블 수(100곳 초과 여부) |
| 계정 설정 초기화 | 기본값으로 돌아갈 설정 수(7개 중)와 즐겨찾기 수, 복구 가능 기간(되돌릴 것이 없으면 복구 불가 안내), 기기별 설정은 그대로, 회원 쪽지 |
| 계정 설정 복구 | 언제의 초기화를 되돌리는지, 돌아올 설정 수와 즐겨찾기 수, 착석한 테이블 수, 다시 복구할 수 없음 |
| 신고 처리 | 함께 닫힐 같은 대상의 열린 신고 수, 결과 쪽지를 받을 신고자 수(탈퇴 제외)와 대상 회원 안내 여부, 실제로 숨겨질 공개 글·댓글이 있는지 |
| 관리자 기능 권한 | 켜지는·꺼지는 스위치, 쓸 수 있는 작업 수 전 → 후, 새 버전, 적용 시점(다음 요청부터) |

- 미리보기는 비밀번호 재확인을 묻지 않는다(실제 변경이 묻는다). **역할 검사는 미리보기에도 그대로** 적용된다. 일반 관리자가 관리자 계정을 정지하려 하면 미리보기 단계에서 403으로 거절되고, 거절은 실패 감사에 남는다.
- 미리보기에 담기는 내용은 회원·테이블 상세에서 관리자가 이미 보는 정보뿐이다. 카드 정보는 없다.
- 미리보기 수치는 그 순간의 값이다. 실행 시점에 다시 계산해 처리한다(예: 칩 조정은 실행 때 다시 잔액·멱등 키를 본다).
- 성공한 미리보기는 감사 로그에 남기지 않는다. 미리보기 라우트로 표시된 곳만 `preview`를 받아 주고, 다른 라우트에 `preview: true`를 보내도 재확인을 건너뛰지 않는다.

## 관리자 세션 관리

- 콘솔의 "보안" 화면에서 열린 관리자 콘솔 세션(시작·마지막 사용·유휴 만료·최대 만료·IP·브라우저·재확인 유효 시각)을 본다. 일반 관리자는 자기 세션만, 슈퍼관리자는 모든 관리자의 세션을 본다(최대 200개).
- 세션 하나 종료(`DELETE /api/admin/security/sessions/:id`), 이 브라우저를 뺀 내 세션 모두 종료(`POST /api/admin/security/sessions/end-others`). 다른 관리자의 세션은 슈퍼관리자만 끝낸다. 지운 세션은 다음 요청부터 401이라 그 콘솔은 로그인 화면으로 돌아간다.
- 세션 종료는 계정을 지키는 조치라 재확인을 묻지 않는다. `admin.session.end`(세션 ID, 자기 세션 여부), `admin.session.end_others`(끝낸 수)로 남는다.
- 회원(게임) 세션은 이 화면이 아니라 회원 상세의 강제 연결 종료로 끝낸다.

## 비공개 정보 원칙

- 진행 중인 핸드의 홀카드, 덱, 시드는 관리자 실시간 상태에도 포함하지 않는다. 테스트로 검증했다.
- 모든 카드 정보는 핸드가 끝나 D1에 기록된 뒤에만, 위 재확인을 거쳐 열람할 수 있다. 진행 중인 다른 회원의 홀카드나 아직 나오지 않은 덱을 보여 주는 관리자 기능은 없고 만들지 않는다(B7 검토에서 유지). 핸드 기록은 정산된 뒤에만 쓰이므로 진행 중 핸드는 `GET /api/admin/hands/:id`로도 읽을 수 없다.
- 종료된 핸드의 전체 카드 열람은 권한 표에서 `handRecords` 기능으로, 모든 관리자가 재확인을 거쳐 열고 `hand.view_sensitive`로 남는다(재확인이 없어 거절된 요청은 401이라 실패 감사에는 남지 않는다).
- 테이블 상태 진단(`GET /api/admin/tables/:id`의 `diagnosis`)는 카드 없이 좌석·스택·단계·차례·마감·대기 중 충전 같은 운영 정보와 D1 기록 비교만 담는다. 긴급 조치는 카드나 결과를 바꾸지 않고, 퇴장도 엔진의 폴드와 정상 정산을 쓴다.

## 가상 칩 조정과 정합성 정정

- 큰 금액 조정: 절대값 100,000칩 이상 지급·차감은 슈퍼관리자만 할 수 있다(그 밖은 403 `large_adjustment`). 콘솔은 금액을 입력할 때 미리 알린다.
- 별도 승인(두 사람 확인)은 검토했지만 도입하지 않았다. 운영자가 적어 요청·승인 대기 상태를 따로 두면 처리만 늦어지고, 승인 대기 중인 조정의 멱등성·만료를 새로 관리해야 한다. 대신 (1) 금액 기준으로 슈퍼관리자에게만 열고, (2) 모든 조정·거절·중복 요청을 감사 로그에 남기며(`user.chips`, `user.chips_refused`, `user.chips_duplicate`), (3) 칩 경제 화면이 큰 금액 조정, 하루 안에 같은 회원에게 3회 이상 지급, 거절·중복 요청을 특이 거래로 보여 준다. 운영자가 늘면 다시 검토한다.
- 기존 원장의 멱등성은 그대로다. 같은 `idempotencyKey`로 다시 보낸 조정은 원장과 잔액을 바꾸지 않고, 중복 요청으로만 기록된다.
- 잘못 지급한 무료 칩 보충은 지급 기록을 고치거나 지우지 않고, 이 칩 조정에 원 거래(`refLedgerId`)를 연결해 회수한다(같은 회원의 원장이 아니면 400 `ref_not_found`). 원장 `ref_id`와 감사 기록 `user.chips`의 `refLedgerId`·`refType`에 남고, 회원 상세의 보충 이력에 그 보충의 회수로 보인다. 일반 조정과 같은 재확인·금액 한도·멱등 키가 적용된다.
- 원장 불일치는 자동으로 고치지 않는다. 정합성 검사는 이상을 기록만 하고, 관리자가 증거(원장 행마다 직전 잔액과 기록 잔액의 연결, 마지막 원장 기록 뒤 원장 밖에서 바뀐 금액, 열린 착석, 지금 차이)를 본 뒤 셋 중 하나를 고른다. 메모만 남기기(모든 관리자), 차이를 원장에 기록(잔액 유지), 잔액 되돌리기(원장에 맞춤). 기록·되돌리기는 슈퍼관리자만, 재확인을 거쳐, 실행 전에 잔액 변경 전 → 후를 확인한 뒤 실행된다. 검사 뒤 잔액·원장이 바뀌었으면 409 `reconcile_stale`로 거절해 오래된 증거로 고치지 않는다. 정정은 이벤트마다 한 번만 원장에 반영된다(원장 키 `reconcile:<id>:record|revert`). 되돌리면 회원에게 계정 언어로 쪽지를 보내고, 관리자 메모는 보내지 않는다.

## 서비스 점검

- 점검 중에는 모든 테이블이 새 착석·대기 등록과 새 핸드를 멈춘다. 진행 중 핸드는 지우거나 중단하지 않고 끝까지 진행해 정상 정산하며, 원장은 건드리지 않는다. 회원은 점검 중에도 자리에서 일어나 칩을 지갑으로 돌려받을 수 있다. 테이블 종료·테이블별 새 핸드 중단·입장 차단은 점검과 따로 그대로 동작한다(점검이 끝나도 관리자가 멈춘 테이블은 멈춘 채로 남는다).
- "새 로그인 제한"을 고르면 회원 로그인과 가입이 503 `maintenance`로 거절된다. 거절은 비밀번호를 확인한 뒤에 하므로, 비밀번호가 틀리면 평소와 같은 401이 나가 점검 거절로 계정 존재를 알아낼 수 없다(점검 여부 자체는 공개 상태 API로 누구나 본다). 이미 열린 세션은 유지한다. 관리자·슈퍼관리자 계정은 게임 사이트에도 로그인할 수 있고(재개 전 확인용), 관리자 콘솔은 별도 로그인이라 점검과 상관없이 쓸 수 있다.
- 점검 예약·변경·종료는 모든 관리자가 재확인을 거쳐 할 수 있다(B7 권한 매트릭스에서 검토: 당번 관리자가 긴급하게 서비스를 멈출 수 있어야 해서 슈퍼관리자 전용으로 올리지 않았다). 한 번에 하나만 예약할 수 있고(동시 예약도 한 문장 조건으로 하나만 성공), 최대 48시간, 최대 90일 뒤까지다. 진행 중 점검은 시작을 바꿀 수 없고 종료만 늘이거나 줄인다.
- 관리자가 바꾸면 api가 사용 중인 테이블 룸(최대 60곳)에 바로 다시 읽게 하고, 결과(물은 곳·답한 곳·답하지 않은 곳)를 감사 기록과 화면에 남긴다. 답하지 않은 룸도 다음 점유 기록 때와 핸드를 기록할 때(같은 D1 batch에서 점검을 함께 읽음) 알게 되고, 그 뒤로는 점검 시작·종료 시각의 알람으로 D1을 다시 읽는다. 그래서 점검 시작을 알지 못한 채 핸드를 계속하는 룸은 핸드 하나를 더 마칠 때까지만 진행한다.

## 관리자 내부 메모

- 목적: 운영자끼리 조치 근거와 주의할 점을 넘겨주는 인수인계용이다. 회원에게는 보이지 않고, 모든 관리자(ADMIN·SUPER_ADMIN)가 회원 상세에서 읽는다. 새 역할은 만들지 않았다.
- 개인정보를 받지 않는다: 이메일, 전화번호(국내·국제), 주민등록번호, 카드 번호처럼 보이는 본문은 400 `note_pii`로 거절한다. 패턴 검사라 모든 개인정보를 잡지는 못하므로 콘솔 안내문에도 적지 말라고 쓴다. 길이는 2–500자.
- 삭제: 작성자나 슈퍼관리자만. 본문은 바로 지우고, 감사 기록(`note.delete`)에는 누가 누구의 메모를 언제 지웠는지만 남는다. 작성 기록(`note.create`)에도 본문은 없다(메모 ID와 길이).
- 회원이 탈퇴하면 그 회원에 대한 메모를 함께 지운다(`docs/PRIVACY_OPERATIONS.md`).

## 회원 정보 내보내기

- 회원 목록에서 체크한 회원(한 번에 최대 1,000명)만 CSV로 내려받는다. 표시된 회원 전체 선택을 지원한다.
- 담기는 항목: ID, 이메일, 닉네임, 계정 언어, 권한, 상태, 잔액, 가입 시각, 생년월일, 이메일 인증 시각, 개인정보 동의 버전·시각, 정지 사유. 비밀번호 해시와 세션 정보는 담지 않는다.
- 근거: 가입 때 받는 개인정보 수집·이용 동의(`apps/web/src/legal/privacyNotice.ts`)의 "3. 관리자 조회와 파일 내보내기" 항목에 근거를 적었다. 문구를 바꾸면 `PRIVACY_NOTICE_VERSION`을 올린다.
- 스프레드시트 수식 실행을 막기 위해 `=`·`+`·`-`·`@`로 시작하는 칸 앞에 `'`를 붙인다. 파일은 UTF-8(BOM)이라 Excel에서 한글이 깨지지 않는다.
- 내보낸 파일은 목적을 달성하면 바로 삭제한다. 모든 내보내기는 행위자, 대상 회원 ID, 건수와 함께 감사 로그에 남는다.

조회도 남긴다. `user.list`(회원 목록·검색: 검색어, 필터, 정렬, 건수), `user.view`(회원 상세: 생년월일·동의 기록 포함), `report.view`(신고 목록: 1:1 메시지 신고 ID 포함)는 화면을 열 때마다 1행씩 쌓인다. 1:1 대화를 읽는 관리자 API는 없고, 관리자가 보는 1:1 메시지는 신고 증거뿐이다. 보관 기간은 정하지 않았다(`docs/PRIVACY_OPERATIONS.md` 5·9절). 회원 상세의 "관리 이력·메모"는 이 감사 로그(그 회원 대상의 제재·권한·칩·재설정 링크·메모 삭제와 그 회원에 대한 신고 결정)와 메모를 시간순으로 보여 준다. 최근 참여 테이블과 신고 건수는 상세 조회(`user.view`)에 함께 담기고, 기간별 활동(`/activity`)과 이력(`/timeline`) 조회는 따로 기록하지 않는다(콘솔은 상세를 연 뒤에만 부른다).

신고 처리: 심각도·담당자 변경은 `report.severity`·`report.assign`(변경 전후), 내부 메모는 `report.note`(메모 ID와 길이, 본문 없음)로 남는다. 신고에서 준 정지는 `user.suspend` 상세에 `reportId`가 들어간다. 신고 통계(`/reports/stats`: 건수와 회원 ID·닉네임만, 증거·본문 없음), 담당자 후보 목록, 신고별 처리 기록(`/reports/:id/events`: 목록 조회 `report.view` 뒤에만 연다) 조회는 기록하지 않는다. 심각도·담당자·처리는 감사 행을 먼저 쓰고 그 행이 있을 때만 변경을 반영하는 한 batch라, 동시에 같은 신고를 맡거나 닫아도 감사 행과 변경은 하나뿐이다. 실패한 시도(409·400)도 B7부터 아래 "실패 감사"로 남는다. 신고 수·통계로 자동 정지하는 경로는 없다.

이상 플레이 신호(`/integrity`, 신고 관리의 "이상 신호" 탭, `reports` 스위치): 캐시 테이블 핸드에서 두 회원 사이 칩이 한쪽으로 넘어간 쌍을 위험도 순으로 보여 주는 운영자 검토 후보다. 목록은 어떤 회원이 쌍으로 게임했고 같은 네트워크였는지 드러내므로 열 때마다 `integrity.view`로 남는다. 같은 네트워크는 세션 IP를 D1 안에서 비교한 결과(예/아니오)뿐이고 IP는 응답에 없으며, 다른 신호와 함께일 때만 붙는다(공유기·회사·카페 때문에 같은 IP만으로는 아무 의미도 두지 않는다). 새 기기 지문은 모으지 않는다. "검토 시작"(`integrity.review`)은 서버가 그 쌍을 다시 계산해 칩을 받은 회원에게 운영자 이름의 `cheating` 신고를 신호·핸드 증거와 함께 여는 것뿐이고, 정지는 그 신고를 보고 기존처럼 `reportId`를 붙여 따로 준다. 칩 동결은 만들지 않았다: 잔액을 고쳐 흉내 내지 않고, 필요하면 기존 정지(바이인·리바이 차단)로 막는다.

원장·핸드 목록(B9): 원장은 모든 회원의 잔액 이력이라 `ledger.view`를 쪽마다 1행씩 남긴다(검색어, 회원을 찾았는지, 종류·기간 필터, 첫 쪽·다음 쪽, 건수; 회원을 찾으면 그 회원이 대상). 찾지 못한 검색어도 남겨 누구를 찾아보려 했는지 알 수 있다. 핸드 목록은 카드 없이 테이블·보드·팟만 담지만, 회원으로 좁히면 그 회원이 언제 어디서 게임했는지가 드러나므로 그 조회만 `hand.list`로 남긴다. 테이블로만 좁히거나 전체를 넘겨 보는 핸드 목록과 테이블 목록은 회원을 가리키지 않는 운영 정보라 남기지 않는다(관리자가 화면을 넘길 때마다 쓰기가 생기지 않게). 카드를 담은 핸드 상세는 지금처럼 재확인과 `hand.view_sensitive`를 거친다.

운영 통계(`GET /api/admin/stats`, 기능 `stats`, 모든 관리자): 날짜별 합계만 돌려주고 회원 ID·닉네임·이메일을 담지 않으므로 조회를 감사 로그에 남기지 않는다. 화면을 열 때 빠진 날을 먼저 집계하는 쓰기(`daily_stats`)는 같은 날을 다시 집계해도 같은 값이 되는 작업이라 감사 대상으로 보지 않는다. 핸드 노트 패널(`handNotes`, `handNotesNow`)과 계정 설정 동기화 패널(`settings`)도 같은 원칙으로 개수만 보인다.

### 실패 감사

- 관리자 요청이 거절되거나 실패하면 `<권한 표의 조치 이름>.failed`(예: `user.suspend.failed`), 관리자 권한이 없어 거절되면 `admin.access_denied`로, `outcome = 'failed'`인 한 행을 남긴다. 상세에는 상태 코드, 오류 코드·메시지, 라우트, 미리보기였는지만 담는다. **요청 본문은 남기지 않는다**(사유·메모·금액에 개인정보가 섞일 수 있다).
- 남기는 것: 모든 403(역할 부족, 규칙 없는 라우트, 관리자가 아닌 계정), 변경 요청(GET 외)의 400 이상. 남기지 않는 것: 401(세션 없음·재확인 필요: 콘솔이 비밀번호 창을 띄운다), 조회의 404 같은 403 외 실패, 라우트가 이미 자기 행을 쓴 요청(`user.chips_refused`처럼).
- 로그인·재확인 실패(`admin.login.failed`, `admin.reauth.failed`)와 칩 거절(`user.chips_refused`)도 `failed`로 표시된다(마이그레이션 0018이 기존 행도 바꾼다).
- 행을 쓰다 실패해도 응답은 바뀌지 않는다. 실패한 요청마다 D1 쓰기가 1회 늘어난다.
- 미리보기도 같다. 신고 처리 미리보기가 400(예: 기각에 대상 회원 안내)이나 409(이미 처리됨)로 거절되면 `report.resolve.failed`(상세 `preview: true`)로 남는다. 성공한 미리보기는 남지 않는다.

### 감사 로그 검색

- 콘솔 "관리 이력" 화면(`GET /api/admin/audit?paged=1`): 행위자, 조치(정확히 또는 `user.*` 같은 묶음), 결과, 대상 종류·ID, 기간, 본문 검색(2–50자: 상세 JSON 안의 글자나 대상 ID)으로 거르고 최신순 50개씩(최대 100) 넘긴다. 같은 밀리초 행은 ID로 이어 붙여 빠지거나 겹치지 않는다. 필터는 주소에 남아 링크로 공유할 수 있다. 회원·테이블 상세의 "관리 이력" 링크는 그 대상으로 좁힌 화면을 연다.
- 첫 페이지에서만 일치 건수를 센다. 10,000건까지 세고 넘으면 "10,000건 이상"으로 표시한다(로그 전체를 읽지 않기 위해).
- 행위자·조치·실패·대상·시각 필터는 각각 인덱스를 탄다(`audit_actor_idx`, `audit_action_idx`, 부분 인덱스 `audit_failed_idx`, 기존 대상·시각 인덱스). 이 다섯은 인덱스 순서가 곧 시간순이라 목록은 한 페이지만 읽는다(첫 페이지의 건수는 인덱스에서 최대 10,001개를 센다). 조치 묶음(`user.*`)은 인덱스로 범위를 좁히지만 묶음에 든 행을 모두 읽어 시간순으로 정렬하고, 본문 검색은 다른 필터 범위 안의 행을 모두 읽는다. 합성 데이터 20만 행(`node:sqlite`, 실행 계획 확인)에서 페이지와 건수 한 번에 한 조치 0.6 ms, 실패만 0.2 ms, 대상 하나 0.1 ms, `user.*`(8만 행) 39.6 ms, 본문 검색 53.1 ms였다. 로그가 커지면 묶음·본문 검색은 기간을 함께 좁혀 쓴다.
- **일반 관리자는 자기 기록만** 본다(`audit.all`이 없으면 행위자가 자기로 고정된다). 슈퍼관리자는 모든 관리자의 기록을 본다. `paged=1` 없는 기존 목록 응답도 같은 범위다.

## 최초 관리자 생성(부트스트랩)

1. 배포 시크릿을 설정한다: `wrangler secret put ADMIN_BOOTSTRAP_TOKEN --env production -c apps/api/wrangler.jsonc` (16자 이상 무작위 값).
2. 플레이어 사이트에서 관리자로 쓸 계정을 가입한다.
3. `POST https://admin.<domain>/api/admin/auth/bootstrap {token, email}`을 호출한다. 슈퍼관리자가 하나도 없을 때만 성공한다.
4. 끝나면 시크릿을 삭제한다: `wrangler secret delete ADMIN_BOOTSTRAP_TOKEN ...`
5. 이후 관리자는 슈퍼관리자가 콘솔에서 권한을 부여한다.

## 비밀번호 분실

- **관리자**: 다른 슈퍼관리자가 "재설정 링크 발급"을 한다.
- **유일한 슈퍼관리자**: 재설정 메일이 켜져 있으면 사용자 사이트의 비밀번호 찾기를 쓴다(`docs/DEPLOYMENT.md` 2절). 꺼져 있으면 D1 콘솔에서 직접 조치해야 한다.

## 운영 권장 사항

- **운영 선택사항: Cloudflare Access.** `admin.<domain>`에 Cloudflare Zero Trust Access(50명까지 무료)를 붙이면 관리자 로그인 화면 앞에서 회사 계정·이메일 일회용 코드·IP 범위로 한 번 더 막을 수 있다. 코드 변경이 필요 없다. 구성 순서: (1) Zero Trust 대시보드 → Access → Applications → Self-hosted로 `admin.<domain>`을 추가, (2) 정책에 허용할 관리자 이메일(또는 IdP 그룹)·필요하면 국가/IP 조건을 넣는다, (3) 세션 시간을 콘솔 최대 세션(8시간) 이하로 둔다, (4) 플레이어 사이트(`<domain>`)와 공개 API에는 걸지 않는다. Access를 붙여도 콘솔 자체의 로그인·재확인·권한 표는 그대로 동작한다. 이 프로젝트는 Access 구성을 강제하지 않는다.
- WebAuthn·USB 보안 키 인증은 프로젝트 결정(맨 위)에 따라 다시 도입하지 않았다. 추가 인증 수단이 필요하면 위 Access에서 IdP의 다단계 인증을 쓰는 것을 먼저 검토한다.
- 관리자 비밀번호는 다른 서비스와 같이 쓰지 않는다. 감사 로그를 주기적으로 검토한다.
