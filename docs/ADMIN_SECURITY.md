# 관리자 보안 구성

> 2026-10-14 프로젝트 오너 결정에 따라 지시서 §12의 WebAuthn/FIDO2 보안 키 인증은 **구현하지 않는다**(FIDO 장치 없음). 아래 통제로 대체한다.

## 인증과 세션

| 통제 | 구현 |
|---|---|
| 분리된 콘솔 | `admin.<domain>`에서 별도 Worker가 서빙한다. 플레이어 사이트에는 관리자 화면이 없다 |
| 별도 세션 | 쿠키 `jc_asid`(HttpOnly, Secure, **SameSite=Strict**). 플레이어 쿠키(`jc_sid`)로는 관리자 API에 접근할 수 없다 |
| 세션 수명 | 유휴 30분, 최대 8시간. 토큰은 D1에 SHA-256 해시로만 저장한다 |
| 권한 판정 | 매 요청마다 D1의 `users.role`을 다시 읽는다(클라이언트 값은 쓰지 않음). 그 역할로 아래 "권한 매트릭스"의 규칙을 적용한다. 강등되면 관리자 세션을 즉시 폐기한다 |
| 출처 검사 | `/api/admin/*` 요청의 Origin은 `ADMIN_ORIGIN`과 같아야 한다 |
| 시도 제한 | 로그인은 계정당 15분에 5회, IP당 15분에 20회. 재확인은 15분에 10회. 실패는 감사 로그에 남긴다 |
| 비밀번호 저장 | PBKDF2-SHA256 100,000회, 솔트 16바이트, 상수 시간 비교 |

## 민감 작업 재확인

다음 작업은 최근 5분 안에 비밀번호를 다시 입력해야 한다(`POST /api/admin/auth/reauth`). 콘솔이 자동으로 비밀번호 창을 띄운다.

- 회원 정지·해제, 권한 변경(슈퍼관리자만). 해제와 권한 변경도 사유(2–200자)가 필요하다. 콘솔은 실행 전에 변경 전 → 후(상태·권한)와 현재 정지 사유를 보여 주고, 감사 기록에 사유와 변경 전후를 남긴다(`user.suspend` `{reason, from, to, previousReason}`, `user.unsuspend` `{reason, from, to, suspendedReason}`, `user.role` `{from, to, reason}`). 정지는 활성 회원에만 한 번 적용된다: 이미 정지된 회원은 409 `already_suspended`로 거절해 사유를 덮어쓰거나 제재 쪽지를 다시 보내지 않고, 두 관리자가 동시에 눌러도 조건부 갱신이라 하나만 반영된다. 탈퇴한 계정은 404로, 정지 뒤 해제로 `active`가 되살아나는 경로를 막았다(PART C 전에는 탈퇴 계정도 정지·해제되어 `active`로 돌아갔다)
- 회원 강제 연결 종료(로그인 세션 삭제와 테이블 연결 종료, `user.disconnect` 감사 기록에 사유·결과)
- 가상 칩 지급·차감(멱등 키, 음수 잔액 불가, 절대값 100,000 이상은 슈퍼관리자만: 아래 "가상 칩 조정과 정합성 정정")
- 비밀번호 재설정 링크 발급(자기 계정은 불가, 비밀번호 변경 사용)
- 회원 정보 CSV 내보내기(슈퍼관리자만, `user.export` 감사 기록)

대상이 관리자(ADMIN·SUPER_ADMIN)일 때 정지·해제, 강제 연결 종료, 칩 조정, 재설정 링크 발급은 슈퍼관리자만 할 수 있다. 재설정 링크는 계정을 넘겨받을 수 있는 토큰이기 때문이다.
- 테이블 종료(진행 중 핸드가 끝난 뒤 전원 환급)
- 테이블 긴급 제어: 새 핸드 중단·재개, 신규 입장 차단·해제(사유 필수, `table.control` 감사 기록에 사유와 룸 반영 여부)
- 종료된 핸드의 전체 카드 열람(`hand.view_sensitive` 감사 기록)
- 정합성 이벤트 해결 처리(메모만 남기기, 차이를 원장에 기록, 잔액 되돌리기: 기록·되돌리기는 슈퍼관리자만)
- 무료 칩 보충 정책 변경(최고 관리자만), 새 보충 긴급 중지(관리자)·재개(최고 관리자만). 모두 사유가 필요하고 `refill.policy`(변경 전후)·`refill.pause`·`refill.resume`으로 남는다
- 테이블 봇 정책 변경(켜기·기금 한도·최대 봇 수, 최고 관리자만, 다시 켜기도 여기서만)과 긴급 중지(기능 `bots`가 있는 관리자). 둘 다 사유가 필요하고 `bots.policy`(변경 전후, 반영한 룸 수)·`bots.stop`으로 남는다. 봇 계정에는 회원 관리 조치(정지·칩 조정·권한·재설정 링크 등)를 할 수 없다(409 `bot_account`)
- 추천 보상 정책 변경(켜기·양쪽 보상액·하루/누적 한도·필요 핸드 수·검토 기준, 최고 관리자만)과 지급 일시중지(기능 `referral`이 있는 관리자)·재개(최고 관리자만), 검토 대기 추천의 승인, 대기·검토 추천의 거절. 모두 사유가 필요하고 `referral.policy`(변경 전후)·`referral.pause`·`referral.resume`·`referral.approve`·`referral.reject`로 남는다. 다시 정산(`referral.settle`)은 재확인 없이 감사 기록만 남는다(한쪽에 한 번 넘게 지급하지 않음). 감사 기록에는 추천 상태·실패 코드·지급액만 담고 이메일·네트워크 같은 회원 정보는 담지 않는다. 거절은 이미 지급한 칩을 회수하지 않으며, 회수는 회원 칩 조정(`refLedgerId`)으로 한다
- 서비스 점검 예약·변경·지금 종료·취소(사유 필수, `maintenance.*` 감사 기록에 사유와 룸 반영 결과). 공지 작성·수정·내리기·삭제는 재확인 없이 감사 기록만 남는다(`service.notice.*`)
- 회원 계정 설정 초기화·복구(기능 `settings`, 아래 "계정 설정 동기화 관리")

## 계정 설정 동기화 관리

`apps/api/src/routes/admin-settings.ts`, 콘솔은 회원 상세의 "계정 설정" 패널(`apps/admin/src/pages/MemberSettings.tsx`).

- **보는 것(진단에 필요한 최소)**: 저장 여부, 버전(`rev`), 초기화 세대(`epoch`), 저장 형식 버전, 값이 있는 설정 수(7개 중), 즐겨찾기 수, 마지막 변경 시각, 회원 기기의 마지막 동기화 시각(10분 단위), 마지막 초기화(시각·관리자·복구 가능 기한·복구 시각). **설정 값과 즐겨찾기 테이블은 응답에 없다.** 조회는 회원 ID·닉네임과 개수만 담아 감사 로그에 남기지 않는다(회원 상세 `user.view`가 이미 남음).
- **편집 없음**: 관리자가 회원의 설정을 특정 값으로 바꾸는 API·화면은 만들지 않았다. 할 수 있는 것은 초기화와 그 초기화의 복구뿐이다.
- **초기화**: 동기화 대상 7개 설정과 즐겨찾기를 기본값으로 되돌리고 `epoch`을 올린다. 회원 기기는 다음 동기화 때(저장은 409 `settings_reset`, 불러오기는 바뀐 `epoch`) 아직 저장하지 못한 변경을 버리고 계정 값을 받는다. 동기화 이전 기기 설정(`legacy`)은 `epoch` 0일 때만 받으므로, **서버 설정을 지워도 기존 기기의 로컬 설정이 다시 올라오지 않는다.** 저장한 적 없는 계정도 초기화할 수 있다(기기에 남은 이전 설정이 올라오지 않게 막는 용도, 되돌릴 것은 없음). 기기마다 남는 설정(사운드·최근 테이블·설치 안내)은 건드리지 않는다. 회원의 자동 머크가 켜져 있었으면 착석한 테이블 좌석에도 꺼짐을 보낸다(결과 `muck{tables, reached}`).
- **복구**: 초기화 직전 값(값과 변경 시각)을 그 행에 보관해 두고, 7일(`SETTINGS_RESTORE_MS`) 안에 회원이 아무것도 바꾸지 않았을 때만 한 번 되돌린다(`epoch`을 다시 올림). 회원이 그 사이 바꿨거나 기한이 지났거나 이미 복구했으면 409 `settings_not_restorable`.
- **미리보기·재확인·사유**: 둘 다 `preview: true`로 범위(지울·되돌릴 설정 수와 즐겨찾기 수, 착석한 테이블 수, 복구 가능 기간)를 먼저 보여 주고, 실행은 비밀번호 재확인과 사유(2–200자)를 받는다. 미리보기도 아래 역할 검사를 거친다.
- **동시 수정**: 요청은 관리자가 보던 `rev`를 담는다. 그 사이 회원·다른 관리자가 바꿨으면 409 `settings_changed`(지금 상태를 `details.settings`로), 이미 초기화된 뒤 바뀐 것이 없으면 409 `settings_already_reset`. 쓰기 자체도 같은 `rev`·`epoch` 조건을 건 한 문장이라 두 관리자가 동시에 눌러도 하나만 성공한다.
- **대상 제한**: 자기 계정 400, 탈퇴 회원 404, 테이블 봇 409 `bot_account`, 관리자 계정은 `admins.manage`(최고 관리자)만(그 밖은 403).
- **회원 안내**: 초기화·복구가 실제로 쓰인 경우에만 같은 D1 batch에서 쪽지 한 통(카테고리 `admin`, 계정 언어 ko·en)을 쓴다. 쪽지에 관리자의 사유는 넣지 않는다.
- **감사 기록**: `settings.reset` `{reason, before{rev, epoch, fields, favourites}, after{…}, restorable, muck}`, `settings.restore` `{reason, resetAt, before, after, muck}`. 개수만 담고 설정 값·즐겨찾기 테이블은 담지 않는다. 거절은 `settings.reset.failed`·`settings.restore.failed`.
- **운영 통계**: 날짜별 저장·병합 충돌·밀린 변경·초기화 뒤 거절·실패 이유별(입력·요청 제한·경합·오류·불러오기·기기에서 실패)·초기화·복구 횟수(`ss_*`, 운영 통계의 "계정 설정 동기화" 카드). 회원별 수치는 없다.

## 권한 매트릭스

- 모든 관리자 API(`/api/admin/*`, 로그인·재확인 `/auth` 제외)는 `apps/api/src/lib/permissions.ts`의 `ROUTE_RULES`에 규칙이 하나씩 있다. 규칙은 기능(28개), 감사 이름, 최소 역할(ADMIN 또는 SUPER_ADMIN), 재확인 여부, 미리보기 지원 여부를 정한다. `requirePermission`이 라우트 실행 전에 적용하고, **규칙이 없는 라우트는 403 `no permission rule for this action`으로 닫힌다**(새 라우트를 만들고 규칙을 빠뜨리면 열리지 않는다). 단위 테스트가 실제 라우트 목록과 표를 맞춰 본다.
- 요청 내용에 따라 달라지는 권한은 능력(capability)으로 이름을 붙였고, 지금은 모두 슈퍼관리자 전용이다.

| 능력 | 뜻 |
|---|---|
| `members.export` | 회원 정보 CSV 내보내기(이메일·생년월일·동의 기록). B7부터 일반 관리자는 403 |
| `roles.change` | 회원을 관리자로 만들거나 관리자의 권한 변경 |
| `admins.manage` | 관리자 계정의 정지·해제·강제 연결 종료·칩 조정·재설정 링크 발급 |
| `chips.large` | 절대값 100,000칩 이상 조정 |
| `ledger.correct` | 정합성 이벤트에서 원장 기록·잔액 되돌리기 |
| `notes.delete_any` | 다른 관리자의 내부 메모 삭제 |
| `audit.all` | 모든 관리자의 감사 기록 조회(일반 관리자는 자기 기록만) |
| `sessions.all` | 다른 관리자의 콘솔 세션 보기·종료(자기 세션은 누구나) |
| `refill.policy` | 무료 칩 보충 정책(켜기·기준·금액·대기 시간) 변경과 긴급 중지 해제(중지는 기능 `refill`이 있는 관리자 누구나) |
| `bots.policy` | 테이블 봇 정책(켜기·기금 한도·최대 봇 수) 변경과 긴급 중지 뒤 다시 켜기(중지는 기능 `bots`가 있는 관리자 누구나). 테이블별 봇 설정은 테이블 수정 권한을 따른다 |
| `referral.policy` | 추천 보상 정책(켜기·보상액·한도·필요 핸드 수·검토 기준) 변경과 지급 일시중지 해제(중지·승인·거절·다시 정산은 기능 `referral`이 있는 관리자 누구나) |

- 표는 코드에 있다. 관리자가 화면에서 바꾸는 설정이 아니라, 누가 무엇을 할지 바꾸려면 검토를 거친 코드 변경이 필요하다. 콘솔의 "보안" 화면은 표를 읽기 전용으로 보여 준다(`GET /api/admin/security/permissions`, 내 능력·기능별 일반 관리자 가능 여부·재확인 여부).
- 콘솔은 `GET /api/admin/auth/me`의 `permissions`로 할 수 없는 버튼을 숨기거나 막고 이유를 보여 주지만(예: 내보내기), 판정은 언제나 서버가 한다.
- 역할을 바꾸면 그 회원의 관리자 콘솔 세션을 모두 지운다. 다른 관리자의 권한이 바뀌거나 세션이 지워져도, 그 콘솔은 다음 요청부터 바로 바뀐 권한으로 판정되거나 로그인 화면으로 돌아간다(콘솔은 `not an administrator`·`super admin only`를 받으면 내 정보를 다시 읽는다).

## 변경 미리보기

회원 정지·해제·강제 연결 종료·권한 변경·칩 조정, 테이블 종료와 신고 처리(B9), 무료 칩 보충 정책 변경, 테이블 봇 정책 변경, 추천 보상 정책 변경, 회원 계정 설정 초기화·복구는 실행 전에 무엇이 바뀌는지 먼저 보여 준다. 같은 라우트에 `preview: true`를 보내면 아무것도 쓰지 않고 다음을 돌려준다.

| 작업 | 미리보기 |
|---|---|
| 정지 | 회원 상태·권한, 끝나는 로그인 세션 수(게임·관리자 콘솔), 일어나게 되는 좌석(테이블·바이인) |
| 강제 연결 종료 | 위와 같고, 테이블에서 내보낼지 여부 |
| 정지 해제 | 상태 변경 전 → 후, 현재 정지 사유 |
| 권한 변경 | 권한 전 → 후, 관리자 콘솔 접속 가능 여부 전 → 후, 끝나는 관리자 콘솔 세션 수, 얻고 잃는 능력 |
| 칩 조정 | 잔액 전 → 후, 큰 금액 여부, 같은 요청을 이미 처리했는지(중복이면 실행 버튼이 막힌다) |
| 테이블 종료 | 앉은 회원과 스택(룸이 답하면), 바이인, 테이블 위 칩, 진행 중 핸드 여부, 대기자 수 |
| 무료 칩 보충 정책 | 정책 전 → 후, 적용 시점(다음 청구부터, 이미 시작된 대기 시간은 그대로), 지금 대기 중인 회원 수 |
| 테이블 봇 정책 | 정책 전 → 후, 적용 시점(테이블마다 핸드 사이, 진행 중 핸드는 그대로), 봇을 허용한 테이블 수, 지금 앉은 봇 수, 발행한 기금과 남는 한도 |
| 추천 보상 정책 | 정책 전 → 후, 적용 시점(보상액·필요 핸드 수는 다음 가입부터, 한도는 다음 지급부터, 이미 받아들인 추천은 가입 당시 약속대로), 지금 지급·검토 대기 중인 추천 수 |
| 계정 설정 초기화 | 기본값으로 돌아갈 설정 수(7개 중)와 즐겨찾기 수, 착석한 테이블 수(자동 머크 반영), 복구 가능 기간(되돌릴 것이 없으면 복구 불가 안내), 기기별 설정은 그대로, 회원 쪽지 |
| 계정 설정 복구 | 언제의 초기화를 되돌리는지, 돌아올 설정 수와 즐겨찾기 수, 착석한 테이블 수, 다시 복구할 수 없음 |
| 신고 처리 | 함께 닫힐 같은 대상의 열린 신고 수, 결과 쪽지를 받을 신고자 수(탈퇴 제외)와 대상 회원 안내 여부, 실제로 숨겨질 공개 글·댓글이 있는지 |

- 미리보기는 비밀번호 재확인을 묻지 않는다(실제 변경이 묻는다). **역할 검사는 미리보기에도 그대로** 적용된다. 일반 관리자가 관리자 계정을 정지하려 하면 미리보기 단계에서 403으로 거절되고, 거절은 실패 감사에 남는다.
- 미리보기에 담기는 내용은 회원·테이블 상세에서 관리자가 이미 보는 정보뿐이다. 카드 정보는 없다.
- 미리보기 수치는 그 순간의 값이다. 실행 시점에 다시 계산해 처리한다(예: 칩 조정은 실행 때 다시 잔액·멱등 키를 본다).
- 성공한 미리보기는 감사 로그에 남기지 않는다. 미리보기 라우트로 표시된 곳만 `preview`를 받아 주고, 다른 라우트에 `preview: true`를 보내도 재확인을 건너뛰지 않는다.

## 관리자 세션 관리

- 콘솔의 "보안" 화면에서 열린 관리자 콘솔 세션(시작·마지막 사용·유휴 만료·최대 만료·IP·브라우저·재확인 유효 시각)을 본다. 일반 관리자는 자기 세션만, 슈퍼관리자는 모든 관리자의 세션을 본다(최대 200개).
- 세션 하나 종료(`DELETE /api/admin/security/sessions/:id`), 이 브라우저를 뺀 내 세션 모두 종료(`POST /api/admin/security/sessions/end-others`). 다른 관리자의 세션은 슈퍼관리자만 끝낸다. 지운 세션은 다음 요청부터 401이라 그 콘솔은 로그인 화면으로 돌아간다.
- 세션 종료는 계정을 지키는 조치라 재확인을 묻지 않는다. `admin.session.end`(세션 ID, 자기 세션 여부), `admin.session.end_others`(끝낸 수)로 남는다.
- 회원(게임) 세션은 이 화면이 아니라 회원 상세의 강제 연결 종료로 끝낸다.

## 비공개 정보 원칙

- 진행 중인 핸드의 홀카드, 덱, 시드는 관리자 실시간 상태에도 포함하지 않는다. 테스트로 검증했다.
- 모든 카드 정보는 핸드가 끝나 D1에 기록된 뒤에만, 위 재확인을 거쳐 열람할 수 있다. 진행 중인 다른 회원의 홀카드나 아직 나오지 않은 덱을 보여 주는 관리자 기능은 없고 만들지 않는다(B7 검토에서 유지). 핸드 기록은 정산된 뒤에만 쓰이므로 진행 중 핸드는 `GET /api/admin/hands/:id`로도 읽을 수 없다.
- 종료된 핸드의 전체 카드 열람은 권한 표에서 `handRecords` 기능으로, 모든 관리자가 재확인을 거쳐 열고 `hand.view_sensitive`로 남는다(재확인이 없어 거절된 요청은 401이라 실패 감사에는 남지 않는다).
- 테이블 상태 진단(`GET /api/admin/tables/:id`의 `diagnosis`)는 카드 없이 좌석·스택·단계·차례·마감·대기 중 충전 같은 운영 정보와 D1 기록 비교만 담는다. 긴급 조치는 카드나 결과를 바꾸지 않고, 퇴장도 엔진의 폴드와 정상 정산을 쓴다.

## 가상 칩 조정과 정합성 정정

- 큰 금액 조정: 절대값 100,000칩 이상 지급·차감은 슈퍼관리자만 할 수 있다(그 밖은 403 `large_adjustment`). 콘솔은 금액을 입력할 때 미리 알린다.
- 별도 승인(두 사람 확인)은 검토했지만 도입하지 않았다. 운영자가 적어 요청·승인 대기 상태를 따로 두면 처리만 늦어지고, 승인 대기 중인 조정의 멱등성·만료를 새로 관리해야 한다. 대신 (1) 금액 기준으로 슈퍼관리자에게만 열고, (2) 모든 조정·거절·중복 요청을 감사 로그에 남기며(`user.chips`, `user.chips_refused`, `user.chips_duplicate`), (3) 칩 경제 화면이 큰 금액 조정, 하루 안에 같은 회원에게 3회 이상 지급, 거절·중복 요청을 특이 거래로 보여 준다. 운영자가 늘면 다시 검토한다.
- 기존 원장의 멱등성은 그대로다. 같은 `idempotencyKey`로 다시 보낸 조정은 원장과 잔액을 바꾸지 않고, 중복 요청으로만 기록된다.
- 잘못 지급한 무료 칩 보충은 지급 기록을 고치거나 지우지 않고, 이 칩 조정에 원 거래(`refLedgerId`)를 연결해 회수한다(같은 회원의 원장이 아니면 400 `ref_not_found`). 원장 `ref_id`와 감사 기록 `user.chips`의 `refLedgerId`·`refType`에 남고, 회원 상세의 보충 이력에 그 보충의 회수로 보인다. 일반 조정과 같은 재확인·금액 한도·멱등 키가 적용된다.
- 원장 불일치는 자동으로 고치지 않는다. 정합성 검사는 이상을 기록만 하고, 관리자가 증거(원장 행마다 직전 잔액과 기록 잔액의 연결, 마지막 원장 기록 뒤 원장 밖에서 바뀐 금액, 열린 착석, 지금 차이)를 본 뒤 셋 중 하나를 고른다. 메모만 남기기(모든 관리자), 차이를 원장에 기록(잔액 유지), 잔액 되돌리기(원장에 맞춤). 기록·되돌리기는 슈퍼관리자만, 재확인을 거쳐, 실행 전에 잔액 변경 전 → 후를 확인한 뒤 실행된다. 검사 뒤 잔액·원장이 바뀌었으면 409 `reconcile_stale`로 거절해 오래된 증거로 고치지 않는다. 정정은 이벤트마다 한 번만 원장에 반영된다(원장 키 `reconcile:<id>:record|revert`). 되돌리면 회원에게 계정 언어로 쪽지를 보내고, 관리자 메모는 보내지 않는다.

## 서비스 점검

- 점검 중에는 모든 테이블이 새 착석·대기 등록과 새 핸드를 멈춘다. 진행 중 핸드는 지우거나 중단하지 않고 끝까지 진행해 정상 정산하며, 원장은 건드리지 않는다. 회원은 점검 중에도 자리에서 일어나 칩을 지갑으로 돌려받을 수 있다. 테이블 종료·테이블별 새 핸드 중단·입장 차단은 점검과 따로 그대로 동작한다(점검이 끝나도 관리자가 멈춘 테이블은 멈춘 채로 남는다).
- "새 로그인 제한"을 고르면 회원 로그인과 가입이 503 `maintenance`로 거절된다. 거절은 비밀번호를 확인한 뒤에 하므로, 비밀번호가 틀리면 평소와 같은 401이 나가 점검 거절로 계정 존재를 알아낼 수 없다(점검 여부 자체는 공개 상태 API로 누구나 본다). 이미 열린 세션은 유지한다. 관리자·슈퍼관리자 계정은 게임 사이트에도 로그인할 수 있고(재개 전 확인용), 관리자 콘솔은 별도 로그인이라 점검과 상관없이 쓸 수 있다.
- 점검 예약·변경·종료는 모든 관리자가 재확인을 거쳐 할 수 있다(B7 권한 매트릭스에서 검토: 당번 관리자가 긴급하게 서비스를 멈출 수 있어야 해서 슈퍼관리자 전용으로 올리지 않았다). 한 번에 하나만 예약할 수 있고(동시 예약도 한 문장 조건으로 하나만 성공), 최대 48시간, 최대 90일 뒤까지다. 진행 중 점검은 시작을 바꿀 수 없고 종료만 늘이거나 줄인다.
- 관리자가 바꾸면 api가 사용 중인 테이블 룸(최대 60곳)에 바로 다시 읽게 하고, 결과(물은 곳·답한 곳·답하지 않은 곳)를 감사 기록과 화면에 남긴다. 답하지 않은 룸도 다음 점유 기록 때와 핸드를 기록할 때(같은 D1 batch에서 점검을 함께 읽음) 알게 되고, 그 뒤로는 점검 시작·종료 시각의 알람으로 D1을 다시 읽는다. 그래서 점검 시작을 알지 못한 채 핸드를 계속하는 룸은 핸드 하나를 더 마칠 때까지만 진행한다.

## 관리자 내부 메모

- 목적: 운영자끼리 조치 근거와 주의할 점을 넘겨주는 인수인계용이다. 회원에게는 보이지 않고, 모든 관리자(ADMIN·SUPER_ADMIN)가 회원 상세에서 읽는다. 새 역할은 만들지 않았다.
- 개인정보를 받지 않는다: 이메일, 전화번호(국내·국제), 주민등록번호, 카드 번호처럼 보이는 본문은 400 `note_pii`로 거절한다. 패턴 검사라 모든 개인정보를 잡지는 못하므로 콘솔 안내문에도 적지 말라고 쓴다. 길이는 2–500자.
- 삭제: 작성자나 슈퍼관리자만. 본문은 바로 지우고, 감사 기록(`note.delete`)에는 누가 누구의 메모를 언제 지웠는지만 남는다. 작성 기록(`note.create`)에도 본문은 없다(메모 ID와 길이).
- 회원이 탈퇴하면 그 회원에 대한 메모를 함께 지운다(`docs/PRIVACY_OPERATIONS.md`).

## 회원 정보 내보내기

- 회원 목록에서 체크한 회원(한 번에 최대 1,000명)만 CSV로 내려받는다. 표시된 회원 전체 선택을 지원한다.
- 담기는 항목: ID, 이메일, 닉네임, 계정 언어, 권한, 상태, 잔액, 가입 시각, 생년월일, 이메일 인증 시각, 개인정보 동의 버전·시각, 정지 사유. 비밀번호 해시와 세션 정보는 담지 않는다.
- 근거: 가입 때 받는 개인정보 수집·이용 동의(`apps/web/src/legal/privacyNotice.ts`)의 "3. 관리자 조회와 파일 내보내기" 항목에 근거를 적었다. 문구를 바꾸면 `PRIVACY_NOTICE_VERSION`을 올린다.
- 스프레드시트 수식 실행을 막기 위해 `=`·`+`·`-`·`@`로 시작하는 칸 앞에 `'`를 붙인다. 파일은 UTF-8(BOM)이라 Excel에서 한글이 깨지지 않는다.
- 내보낸 파일은 목적을 달성하면 바로 삭제한다. 모든 내보내기는 행위자, 대상 회원 ID, 건수와 함께 감사 로그에 남는다.

## 감사 로그

`admin_audit_log`에 행위자, 조치, 대상, 상세(JSON), IP, 시각, 결과(`outcome`: `ok`·`failed`)를 남긴다. 기록하는 조치는 다음과 같다.

```
admin.bootstrap, admin.login, admin.login.failed, admin.reauth, admin.reauth.failed,
admin.session.end, admin.session.end_others, admin.access_denied, <조치>.failed,
user.list, user.view, user.suspend, user.unsuspend, user.disconnect, user.role, user.chips, user.chips_refused, user.chips_duplicate, user.reconcile, user.reset_link, user.export,
note.create, note.delete,
table.create, table.update, table.control, table.close, hand.list, hand.view_sensitive, ledger.view,
reconcile.run, reconcile.resolve, board.notice.create/update,
service.notice.create, service.notice.update, service.notice.end, service.notice.delete,
maintenance.schedule, maintenance.update, maintenance.end, maintenance.cancel,
board.post.status, board.comment.status, message.send,
report.view, report.resolved, report.dismissed, report.severity, report.assign, report.note,
settings.reset, settings.restore
```

조회도 남긴다. `user.list`(회원 목록·검색: 검색어, 필터, 정렬, 건수), `user.view`(회원 상세: 생년월일·동의 기록 포함), `report.view`(신고 목록: 1:1 메시지 신고 ID 포함)는 화면을 열 때마다 1행씩 쌓인다. 1:1 대화를 읽는 관리자 API는 없고, 관리자가 보는 1:1 메시지는 신고 증거뿐이다. 보관 기간은 정하지 않았다(`docs/PRIVACY_OPERATIONS.md` 5·9절). 회원 상세의 "관리 이력·메모"는 이 감사 로그(그 회원 대상의 제재·권한·칩·재설정 링크·메모 삭제와 그 회원에 대한 신고 결정)와 메모를 시간순으로 보여 준다. 최근 참여 테이블과 신고 건수는 상세 조회(`user.view`)에 함께 담기고, 기간별 활동(`/activity`)과 이력(`/timeline`) 조회는 따로 기록하지 않는다(콘솔은 상세를 연 뒤에만 부른다).

신고 처리: 심각도·담당자 변경은 `report.severity`·`report.assign`(변경 전후), 내부 메모는 `report.note`(메모 ID와 길이, 본문 없음)로 남는다. 신고에서 준 정지는 `user.suspend` 상세에 `reportId`가 들어간다. 신고 통계(`/reports/stats`: 건수와 회원 ID·닉네임만, 증거·본문 없음), 담당자 후보 목록, 신고별 처리 기록(`/reports/:id/events`: 목록 조회 `report.view` 뒤에만 연다) 조회는 기록하지 않는다. 심각도·담당자·처리는 감사 행을 먼저 쓰고 그 행이 있을 때만 변경을 반영하는 한 batch라, 동시에 같은 신고를 맡거나 닫아도 감사 행과 변경은 하나뿐이다. 실패한 시도(409·400)도 B7부터 아래 "실패 감사"로 남는다. 신고 수·통계로 자동 정지하는 경로는 없다.

원장·핸드 목록(B9): 원장은 모든 회원의 잔액 이력이라 `ledger.view`를 쪽마다 1행씩 남긴다(검색어, 회원을 찾았는지, 종류·기간 필터, 첫 쪽·다음 쪽, 건수; 회원을 찾으면 그 회원이 대상). 찾지 못한 검색어도 남겨 누구를 찾아보려 했는지 알 수 있다. 핸드 목록은 카드 없이 테이블·보드·팟만 담지만, 회원으로 좁히면 그 회원이 언제 어디서 게임했는지가 드러나므로 그 조회만 `hand.list`로 남긴다. 테이블로만 좁히거나 전체를 넘겨 보는 핸드 목록과 테이블 목록은 회원을 가리키지 않는 운영 정보라 남기지 않는다(관리자가 화면을 넘길 때마다 쓰기가 생기지 않게). 카드를 담은 핸드 상세는 지금처럼 재확인과 `hand.view_sensitive`를 거친다.

운영 통계(`GET /api/admin/stats`, 기능 `stats`, 모든 관리자): 날짜별 합계만 돌려주고 회원 ID·닉네임·이메일을 담지 않으므로 조회를 감사 로그에 남기지 않는다. 화면을 열 때 빠진 날을 먼저 집계하는 쓰기(`daily_stats`)는 같은 날을 다시 집계해도 같은 값이 되는 작업이라 감사 대상으로 보지 않는다. 핸드 노트 패널(`handNotes`, `handNotesNow`)과 계정 설정 동기화 패널(`settings`)도 같은 원칙으로 개수만 보인다.

### 실패 감사

- 관리자 요청이 거절되거나 실패하면 `<권한 표의 조치 이름>.failed`(예: `user.suspend.failed`), 관리자 권한이 없어 거절되면 `admin.access_denied`로, `outcome = 'failed'`인 한 행을 남긴다. 상세에는 상태 코드, 오류 코드·메시지, 라우트, 미리보기였는지만 담는다. **요청 본문은 남기지 않는다**(사유·메모·금액에 개인정보가 섞일 수 있다).
- 남기는 것: 모든 403(역할 부족, 규칙 없는 라우트, 관리자가 아닌 계정), 변경 요청(GET 외)의 400 이상. 남기지 않는 것: 401(세션 없음·재확인 필요: 콘솔이 비밀번호 창을 띄운다), 조회의 404 같은 403 외 실패, 라우트가 이미 자기 행을 쓴 요청(`user.chips_refused`처럼).
- 로그인·재확인 실패(`admin.login.failed`, `admin.reauth.failed`)와 칩 거절(`user.chips_refused`)도 `failed`로 표시된다(마이그레이션 0018이 기존 행도 바꾼다).
- 행을 쓰다 실패해도 응답은 바뀌지 않는다. 실패한 요청마다 D1 쓰기가 1회 늘어난다.
- 미리보기도 같다. 신고 처리 미리보기가 400(예: 기각에 대상 회원 안내)이나 409(이미 처리됨)로 거절되면 `report.resolve.failed`(상세 `preview: true`)로 남는다. 성공한 미리보기는 남지 않는다.

### 감사 로그 검색

- 콘솔 "관리 이력" 화면(`GET /api/admin/audit?paged=1`): 행위자, 조치(정확히 또는 `user.*` 같은 묶음), 결과, 대상 종류·ID, 기간, 본문 검색(2–50자: 상세 JSON 안의 글자나 대상 ID)으로 거르고 최신순 50개씩(최대 100) 넘긴다. 같은 밀리초 행은 ID로 이어 붙여 빠지거나 겹치지 않는다. 필터는 주소에 남아 링크로 공유할 수 있다. 회원·테이블 상세의 "관리 이력" 링크는 그 대상으로 좁힌 화면을 연다.
- 첫 페이지에서만 일치 건수를 센다. 10,000건까지 세고 넘으면 "10,000건 이상"으로 표시한다(로그 전체를 읽지 않기 위해).
- 행위자·조치·실패·대상·시각 필터는 각각 인덱스를 탄다(`audit_actor_idx`, `audit_action_idx`, 부분 인덱스 `audit_failed_idx`, 기존 대상·시각 인덱스). 이 다섯은 인덱스 순서가 곧 시간순이라 목록은 한 페이지만 읽는다(첫 페이지의 건수는 인덱스에서 최대 10,001개를 센다). 조치 묶음(`user.*`)은 인덱스로 범위를 좁히지만 묶음에 든 행을 모두 읽어 시간순으로 정렬하고, 본문 검색은 다른 필터 범위 안의 행을 모두 읽는다. 합성 데이터 20만 행(`node:sqlite`, 실행 계획 확인)에서 페이지와 건수 한 번에 한 조치 0.6 ms, 실패만 0.2 ms, 대상 하나 0.1 ms, `user.*`(8만 행) 39.6 ms, 본문 검색 53.1 ms였다. 로그가 커지면 묶음·본문 검색은 기간을 함께 좁혀 쓴다.
- **일반 관리자는 자기 기록만** 본다(`audit.all`이 없으면 행위자가 자기로 고정된다). 슈퍼관리자는 모든 관리자의 기록을 본다. `paged=1` 없는 기존 목록 응답도 같은 범위다.

## 최초 관리자 생성(부트스트랩)

1. 배포 시크릿을 설정한다: `wrangler secret put ADMIN_BOOTSTRAP_TOKEN --env production -c apps/api/wrangler.jsonc` (16자 이상 무작위 값).
2. 플레이어 사이트에서 관리자로 쓸 계정을 가입한다.
3. `POST https://admin.<domain>/api/admin/auth/bootstrap {token, email}`을 호출한다. 슈퍼관리자가 하나도 없을 때만 성공한다.
4. 끝나면 시크릿을 삭제한다: `wrangler secret delete ADMIN_BOOTSTRAP_TOKEN ...`
5. 이후 관리자는 슈퍼관리자가 콘솔에서 권한을 부여한다.

## 비밀번호 분실

- **관리자**: 다른 슈퍼관리자가 "재설정 링크 발급"을 한다.
- **유일한 슈퍼관리자**: 재설정 메일이 켜져 있으면 사용자 사이트의 비밀번호 찾기를 쓴다(`docs/DEPLOYMENT.md` 2절). 꺼져 있으면 D1 콘솔에서 직접 조치해야 한다.

## 운영 권장 사항

- **운영 선택사항: Cloudflare Access.** `admin.<domain>`에 Cloudflare Zero Trust Access(50명까지 무료)를 붙이면 관리자 로그인 화면 앞에서 회사 계정·이메일 일회용 코드·IP 범위로 한 번 더 막을 수 있다. 코드 변경이 필요 없다. 구성 순서: (1) Zero Trust 대시보드 → Access → Applications → Self-hosted로 `admin.<domain>`을 추가, (2) 정책에 허용할 관리자 이메일(또는 IdP 그룹)·필요하면 국가/IP 조건을 넣는다, (3) 세션 시간을 콘솔 최대 세션(8시간) 이하로 둔다, (4) 플레이어 사이트(`<domain>`)와 공개 API에는 걸지 않는다. Access를 붙여도 콘솔 자체의 로그인·재확인·권한 표는 그대로 동작한다. 이 프로젝트는 Access 구성을 강제하지 않는다.
- WebAuthn·USB 보안 키 인증은 프로젝트 결정(맨 위)에 따라 다시 도입하지 않았다. 추가 인증 수단이 필요하면 위 Access에서 IdP의 다단계 인증을 쓰는 것을 먼저 검토한다.
- 관리자 비밀번호는 다른 서비스와 같이 쓰지 않는다. 감사 로그를 주기적으로 검토한다.
