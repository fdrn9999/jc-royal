## 미구현 / 범위 밖

- **운영 메일 도착 확인(가입 인증, 비밀번호 재설정)**: Resend 연동과 한/영 브랜드 템플릿(`apps/api/src/lib/mail.ts`), 운영 `MAIL_FROM`(`JC ROYAL <noreply@jc-royal.site>`)을 2026-10-15 운영에 배포했다. 배포 뒤 운영 `/api/auth/signup-options`가 `emailVerification: true`를 돌려주고, 비밀번호 재설정 요청 1건이 200으로 끝났다. 메일함 도착은 직접 확인하지 않았고 운영 로그도 보지 않았다(`docs/DEPLOYMENT.md` 2절, 배포 점검표).
- **개인정보 처리방침·이용약관 확정**: `/privacy`·`/terms` 페이지(한/영)와 가입 화면 링크는 있지만 **법무 검토 전 초안**이다(화면에 초안·"검토 필요" 표시). 보관 기한, 보호책임자, 국외 이전 고지, 약관 동의 방식, 등급·연령 등 검토 필요 항목은 `docs/PRIVACY_OPERATIONS.md` 9절. 이 상태로 `main`에 병합하면 운영에 그대로 배포된다.
- **테이블 봇의 운영 사용**: 코드와 관리자 화면은 있지만 마이그레이션 0021이 정책을 꺼진 상태(기금 한도 0)로 넣고 모든 테이블의 봇 설정도 꺼져 있어 배포만으로는 봇이 앉지 않는다. 운영 기금 한도·최대 봇 수·켤 테이블은 정하지 않았다(최고 관리자가 콘솔에서 정함). 운영 환경에서 봇을 켜고 확인한 적 없다.
- **추천 보상의 운영 사용**: 코드와 관리자 화면은 있지만 마이그레이션 0022가 정책을 꺼진 상태(양쪽 금액 0)로 넣어 배포만으로는 지급하지 않는다. 꺼진 동안 코드로 가입한 회원은 기록만 되고 나중에 켜도 지급하지 않으므로, 링크를 알리기 전에 최고 관리자가 금액·한도·핸드 조건을 정하고 켜야 한다. 운영 지급액은 정하지 않았다(개발·E2E 시드의 1,000칩은 예시). 운영 환경에서 켜고 확인한 적 없다.
- **테이블 채팅 푸시**: 만들지 않았다. 테이블 채팅은 룸(Durable Object)이 테이블별 최근 50줄만 두고 회원별 읽음 기록이 없어 무엇을 알릴지 정할 근거가 없고, 착석 중에는 화면에 바로 보이므로 푸시가 방해만 된다는 판단이다. 친구 접속 알림과 광고성 푸시도 만들지 않았다(`docs/PRESENCE.md`).
- **웹 푸시의 운영 사용**: 운영 VAPID 키는 2026-10-21에 오너의 요청으로 등록했다(`docs/DEPLOYMENT.md` 2절, `wrangler secret list`로 이름만 확인). 운영에서 실제 푸시가 오가는지는 아직 확인하지 않았다. 야간 기준(21:00~08:00)·두 동의 문구·푸시 서비스의 국외 이전 고지는 법무 검토 전이다(`docs/PRIVACY_OPERATIONS.md` 9절 14번). 실기기(Android Chrome, iOS 홈 화면 앱, 데스크톱 Safari·Firefox·Edge)에서 받기·누르기·배지를 확인하지 않았다.
- **프로필 이미지 업로드**: 이미지 파일 업로드(R2)는 없다. https URL만 지원.
- 리더보드, 업적: 없음. 토너먼트는 6인 한 테이블 SNG만 있다(35번).
- **부하·성능 테스트**: 로컬 `wrangler dev`에서만 수행했다(`pnpm test:load`, `docs/LOAD_TEST.md`). 최대 30테이블·소켓 300개, 10테이블 연속 30핸드까지 오류 0, 칩 보존 일치. Cloudflare 엣지·운영 환경 부하 테스트는 하지 않았다. 지속 실행의 꼬리 지연(최대 1.2초)은 로컬에서 분석했다. 게임 도중의 멈춤은 `wrangler dev`의 로컬 트레이스 저장소와 함께 자주 나타나 부하 하네스에서 껐다. 끈 뒤에도 3회 중 1회(PART A 회귀 실행, 최대 479 ms) 게임 도중 멈춤이 있었고, 테이블이 끝나며 일어서는 구간의 멈춤도 3회 중 1회(최대 1.05초) 있었다. 둘 다 원인을 찾지 못했다. 운영의 꼬리 지연은 재지 않았다(`docs/LOAD_TEST.md` 5절).
- **아카데미 칩 보상**: 지급하지 않는다(배지만). 필요해지면 서버 원장 트랜잭션·1회 한정·멱등성 키로 구현해야 한다.
- **영어 학습 문구**: 1차 자체 검토만 했고 원어민 감수는 받지 않았다.
- **실기기 검증**: iOS Safari·Android Chrome 실기기에서 확인하지 않았다. Instagram·KakaoTalk 앱 안의 가입도 실제 앱에서는 확인하지 않았다(Chrome·WebKit에 인앱 User-Agent를 준 에뮬레이션만, 59번). 터치 정렬, 핀치 차단, 바텀시트는 브라우저 자동화(Chrome 모바일 에뮬레이션)로만 검증했다.

## 알려진 문제와 제약

1. **poker-engine-ts 0.1.3 결함 보정**: 어댑터 보정 3건과 패치 1건(`docs/ENGINE_NOTES.md`). 엔진을 업그레이드할 때 재검증이 필요하다.
2. **무료 플랜 CPU 10ms**: PBKDF2 10만 회 해싱이 무료 플랜에서 CPU 한도를 넘을 수 있다. 운영은 Workers Paid를 권장한다.
3. **로컬 `wrangler dev`의 닫힌 소켓**: 서버가 닫은 소켓이 클라이언트에서 CLOSING 상태로 남는다. 서버 동작은 정상이다.
4. **레이트 리밋 카운터의 D1 쓰기**: 테이블 WebSocket 연결 1회마다 `rate_limits`에 1행을 쓴다(부하 시나리오에서 연결 수와 같음). Workers Rate Limiting 바인딩을 검토했지만 유지했다. 카운터가 위치별 근사치이고, 가격과 로컬 동작이 문서에 없어 비용이 줄어드는지 확인할 수 없으며, 아낄 수 있는 양도 작다(`docs/DEPLOYMENT.md` 5절).
5. **로비 실시간 현황**: DO가 상태가 바뀔 때 D1에 기록한다. 로비는 5초 폴링이라 최대 수 초 지연된다. 숨긴 탭에서는 부르지 않는다. 화면에 띄워 둔 로비 1개는 쓰는 동안 시간당 최대 720회, 1분 넘게 입력이 없으면 시간당 약 130회 요청한다(단위 테스트의 수, `docs/DEPLOYMENT.md` 5절). 늦춘 동안에는 현황이 최대 30초 늦을 수 있고, 손대는 즉시 갱신한다. 즐겨찾기·최근 방문은 기기(브라우저)별로 저장되어 다른 기기와 동기화되지 않는다.
6. **쇼다운 공개 정책**: 자동 머크는 2026-10-19부터 모든 좌석에 항상 적용된다(설정 없음). 진 패를 보이려면 핸드가 끝난 뒤 '보이기'를 누른다. 머크한 본인 화면에는 족보 이름이 나오지 않는다. 보인 카드는 그 핸드가 끝난 자리에서만 보이고 기록·리플레이에는 남지 않는다.
7. **개발 환경 표시 차이**: 테이블 화면 웹폰트(Pretendard, Cinzel)는 외부 CDN에서 불러온다. 오프라인이면 시스템 글꼴로 대체된다.
8. **앱 핑**: 웹 클라이언트는 서버 메시지가 25초 동안 없을 때만 `ping`을 보내고, 런타임 자동 응답(`setWebSocketAutoResponse`)이 DO를 깨우지 않고 답한다. 조용한 테이블의 실행 시간 절감 폭은 Cloudflare에서 측정하지 않았다(`docs/DEPLOYMENT.md` 5절). 배포는 game-worker를 먼저, 웹을 나중에 한다(`docs/WEBSOCKET_PROTOCOL.md`).
9. **방 복구 주기**: 룸은 실패한 환급·핸드 기록·종료를 15초 간격 알람으로 다시 시도한다. 재시도가 멈춘 방(15분 넘게 '종료 중')과 룸이 한 번도 깨지 않은 빈 회원 방(1시간 넘게)은 매일 18:30 UTC cron의 스윕이 깨운다(실행당 20·50개). 그런 드문 경우에는 다음 스윕까지 칩이 테이블에 남을 수 있다. 환급은 원장 키로 한 번만 지급된다. 방 생성 API의 503 `room_unavailable` 경로는 자동 테스트가 없다(`docs/TEST_REPORT.md` PART A).
10. **운영 대시보드 수치의 범위**: "온라인 회원"은 5분 안에 API를 쓴 회원 세션이라, 테이블에만 머문(API를 부르지 않은) 회원은 빠질 수 있다. 화면에 기준을 함께 표시한다. 착석·연결·핸드 수는 각 룸이 바뀔 때 기록한 마지막 값이라, 룸이 재시작·장애로 기록하지 못하면 그 테이블의 값이 오래될 수 있다(테이블별 갱신 시각 표시). 끊김·재연결·룸 오류 카운터는 다음 통계 기록(조용한 룸은 10초 타이머)에 함께 쓰므로, 그 전에 룸이 내려가면 잃는다. API 5xx는 D1 자체가 실패할 때 카운터도 쓰지 못해 Worker 로그에만 남는다. D1 장애 중에는 룸이 통계 기록 실패를 10초마다 재시도한다. 온라인 수 집계는 쓰기 비용을 늘리지 않으려고 `sessions`에 인덱스를 더하지 않아 세션 행 수만큼 읽는다(`docs/DEPLOYMENT.md` 5절).
11. **강제 연결 종료의 범위**: 정지·강제 연결 종료는 회원이 앉은 테이블 전부와 연결이 있는 열린 테이블(연결 많은 순 최대 60곳)의 룸에 묻는다. 그보다 많은 방에 관전 연결이 있거나 룸이 답하지 않으면 그 방의 연결은 남을 수 있고, 관리자 화면에 '답하지 않은 테이블'로 보인다(자동 재시도 없음). 정지 요청을 다시 보내면(409 `already_suspended`) 그 회원의 테이블에 다시 묻는다. 정지된 계정은 남은 연결로도 착석·충전을 할 수 없다(지갑이 거절). 룸은 종료 시각을 60초 기억하고 그 전에 인증한 핸드셰이크를 거절하므로, 강제 연결 종료 직후 약 2초 안에 다시 로그인하면 한 번 거절되고 새로 고침해야 한다. 배포 순서는 마이그레이션 0013 → game-worker → api → web·admin이다.
12. **회원 관리의 범위**: 관리자 메모의 개인정보 검사는 형태(이메일, 0·국가번호로 시작하는 전화번호, 주민등록번호, 카드 번호)만 보므로 주소·실명 같은 다른 개인정보는 막지 못하고, 숫자 형태가 비슷한 메모는 잘못 거절될 수 있다. 메모 본문은 모든 관리자가 읽는다. 최근 로그인은 회원 로그인(가입 포함)마다 `users` 행 하나를 같은 batch에서 갱신하며, 기존 회원은 다음 로그인 전까지 "기록 없음"이다. 기간별 활동의 날짜 경계는 관리자 브라우저 시간대를 따른다. 정지 해제·권한 변경 API가 사유를 요구하므로, 새 api와 이전 관리자 콘솔이 함께 있는 동안 이전 콘솔의 해제·권한 변경은 400이 된다.
13. **칩 경제 화면의 범위**: 화면을 열 때마다 `users`와 `chip_ledger` 전체를 한 번 읽는다(읽은 행 수를 화면 아래에 표시). 원장이 수십만 행을 넘으면 집계 테이블이나 날짜 인덱스를 검토해야 한다. 환급·룸·API 실패 수는 `ops_metrics`라 최근 14일만 있고, 관리자 조정은 기간당 2,000행까지 읽는다(넘으면 화면에 표시). 단시간 반복 지급은 고른 기간 안에서만 찾고, 12시간 넘은 착석은 실제로 오래 앉아 있는 회원일 수도 있다. 지갑 이상의 원장 연결 검사는 최근 1,000행만 본다. 원장에 기록한 정정은 회원 지갑 내역에도 '정합성 조정' 행으로 보인다. 정합성 목록에는 회원 ID만 나오고(닉네임은 증거를 열면 보임), 검사·정정 사이에 잔액이 바뀌면 다시 검사하라는 409로 거절된다.
14. **공지·점검의 범위**: 점검 변경은 사용 중인 테이블(연결 많은 순 최대 60곳)의 룸에만 바로 알리고, 그 밖이나 답하지 않은 룸은 다음 점유 기록 때나 핸드를 기록할 때 알게 되고(알고 난 뒤에는 점검 시작·종료 시각의 알람으로 다시 읽음), 그래서 점검 시작을 못 받은 룸도 진행 중이던 핸드 하나까지만 마친다. 점검을 일찍 끝냈는데 알림을 받지 못한 룸은 다음 접속자가 올 때 D1을 다시 읽기 전까지 잠깐 점검 중으로 보일 수 있다(그 사이 착석 한 번이 거절될 수 있음). 룸은 점검마다 시작·종료에 한 번씩 깨어나 D1을 읽는다. 게시판 글과 쪽지는 공지의 표시 시작 시각과 상관없이 바로 나가고, 공지를 고쳐도 이미 보낸 쪽지는 바뀌지 않는다. 쪽지는 모든 활성 회원에게 간다. 로그인 거절은 비밀번호 확인 뒤에 나간다. 점검 권한은 모든 관리자(재확인)로 둔다(B7 검토: 당번 관리자가 긴급하게 멈출 수 있어야 함). 로그인 전 화면은 상태를 주기적으로 다시 읽지 않고(점검 안내 페이지만 30초), 페이지를 열 때와 요청이 점검으로 거절될 때 읽는다. 공개 상태 API는 저장된 상태가 없는 방문마다 D1 batch 1회를 쓴다. 관리자 화면의 시각 입력은 관리자 기기 시간대·분 단위다. 상태 API는 공지를 20개까지(긴급·점검 안내 먼저) 주고, 잘렸으면 다음에 바뀔 시각(`refreshAt`)을 함께 줘 그때 다시 읽게 한다. 배포 순서는 마이그레이션 0016 → game-worker → api → web·admin이다.
15. **신고 워크플로의 범위**: 통계는 고른 기간에 접수된 신고 전부를 읽어 사유·대상 종류·회원별로 센다(신고가 수만 건을 넘으면 집계 테이블을 검토). 반복 피신고 회원은 기간 안에 2건 이상인 상위 20명이고, 정지 횟수는 전체 기간의 감사 로그를 센다. 신고 목록의 '다른 신고 수'도 전체 기간이다. 결과 안내 여부는 관리자가 고른 값을 기록하며, 탈퇴한 회원에게는 쪽지를 보내지 않는다(정지된 회원은 받는다). 같은 대상의 신고를 함께 닫을 때 대상 회원에게 가는 위반 안내는 누른 신고의 사유 하나로 쓴다. 처리 기록·내부 메모는 모든 관리자가 읽고, 신고와 함께 보관된다(탈퇴해도 지우지 않음). 실패한 담당·처리 시도(409·400)는 B7부터 실패 감사(`report.update.failed`·`report.resolve.failed`)로 남는다. 신고에서 정지해도 신고는 열린 채로 남고, 처리 결과는 관리자가 따로 정한다. 신고 처리는 B9부터 확인 창을 거친다(함께 닫힐 신고 수·안내 대상·숨김 여부를 서버가 미리 계산하고, 확인해야 처리). 배포 순서는 마이그레이션 0017 → api → admin이다.
16. **권한·감사의 범위**: 권한 표는 코드에 있어 관리자가 화면에서 바꿀 수 없다(바꾸려면 코드 변경). 일반 관리자는 B7부터 회원 정보 내보내기를 할 수 없고(403), 관리 이력에서 다른 관리자의 기록을 볼 수 없다. 실패 감사는 실패한 관리자 요청마다 D1 쓰기 1회를 더하고, 401(세션 없음·재확인 필요)과 403이 아닌 조회 실패는 남기지 않는다. 미리보기 수치는 그 순간의 값이라 실행 때 다시 계산하며, 미리보기는 비밀번호를 묻지 않지만 회원·테이블 상세에서 관리자가 이미 보는 정보만 담는다. 관리 이력의 본문 검색은 다른 필터 범위 안의 행을 모두 읽고, 일치 건수는 10,000건까지만 센다. 보안 화면의 세션 목록은 최근 사용 순 200개까지다. 이전 관리자 콘솔은 새 api에서 일반 관리자의 내보내기가 403으로 보이고, 미리보기 없이 기존처럼 바로 실행된다. 공용 모달 닫기 버튼의 접근성 이름(영어 `close`)과 관리 이력 표의 모바일 가로 스크롤은 B9에서 고쳤다(관리자 콘솔은 언어에 맞는 이름, 휴대폰에서는 행을 카드로 표시). WebAuthn·보안 키는 다시 도입하지 않았고, Cloudflare Access는 운영 선택사항으로 문서화했다(`docs/ADMIN_SECURITY.md`). 배포 순서는 마이그레이션 0018 → api → admin이다. 역할별 표 안에서 관리자마다 기능을 켜고 끄는 스위치는 36번.
17. **운영 통계의 범위**: 활동 회원 수는 회원이 로그인하거나 그날 처음 API를 쓸 때 남기는 '활동한 날' 기록(회원 ID·날짜, 하루 1행)으로 세므로, 배포한 날부터 쌓이고 그 전 날짜는 비어 있다(화면에 `*`와 안내). 배포한 날 자체도 배포 전 시간의 활동이 빠진다. 자정을 넘겨 테이블 WebSocket에만 머물고 API를 부르지 않은 회원은 그날 활동으로 남지 않는다. 동시접속은 사이트 접속이 아니라 게임 좌석(`table_sessions`)의 동시 착석이다(회원별 시간 단위 기록은 과도한 추적이라 두지 않았다). 아카데미 일별 카운터도 배포한 날부터다(누적 `academy_stats`는 그대로). 날짜 경계는 한국 시간 자정으로 고정이다. 하루 집계는 `users`·`tables`와 결정된 신고 전체를 한 번씩 읽는다(가입일·처리 시각 인덱스 없음, 회원이 수십만 명을 넘으면 검토). 첫 집계는 첫 가입일(최대 366일 전)부터 크론 한 번에 최대 372일, 화면을 열 때 31일씩 채운다. 활동한 날 기록은 회원마다 하루 D1 쓰기 1회를 더한다. 오늘은 내일 집계되어 화면에 나오지 않는다. 배포 순서는 마이그레이션 0019 → api → admin이다(마이그레이션 없이 api가 먼저 나가면 아카데미 기록·탈퇴·정리 크론이 실패한다).
18. **관리자 목록·확인 창의 범위(B9)**: 원장·핸드 목록은 전체 건수를 세지 않고 다음 쪽 여부만 안다(세면 볼 때마다 맞는 행을 모두 읽는다). 회원 없이 고른 원장 종류가 드물거나 기간이 오래되면 한 쪽을 채우기까지 원장의 많은 부분을 읽을 수 있다(합성 원장 100만 행에서 드문 종류 44 ms, 회원으로 좁히면 0.1 ms 이하). 회원 없는 원장·핸드 쪽은 기록된 순서(rowid)를 따르므로 복원·가져오기로 행 순서가 바뀌면 시각 순서와 어긋날 수 있다. 원장 조회는 쪽마다, 회원으로 좁힌 핸드 조회도 쪽마다 감사 로그 1행(D1 쓰기 1회)을 더한다. 회원과 테이블을 함께 고른 핸드 목록은 그 회원의 핸드를 읽으며 테이블로 거른다. 게시판·쪽지 이력·테이블 목록은 오프셋 페이지라 아주 뒤쪽 쪽은 앞 행을 건너뛰며 읽는다(대량 데이터에서 재지 않음). 게시판 목록은 작성 시각 순이라 같은 ms의 글은 순서가 정해지지 않는다. 신고 처리 확인 창은 D1 읽기 batch 1회(문장 3개)를 더하고 그 순간의 수라, 확인 사이에 새 신고가 오면 실제 처리 건수가 다를 수 있다(결과 안내에 실제 수가 나옴). 거절된 미리보기는 B7 실패 감사로 1행을 남긴다. 게시글 숨김·복원은 되돌릴 수 있어 확인 없이 바로 실행하고, 삭제만 확인한다. 연결 배너의 '서버 연결 실패'는 요청이 네트워크 오류로 끝날 때 켜지고 다음 응답에서 꺼진다. 새 관리자 콘솔은 새 api의 paged=1 응답이 필요하므로 배포 순서는 api → admin이다(마이그레이션 없음; 이전 콘솔은 새 api에서 그대로 동작).
19. **PART C 종합 검증에서 바꾼 것과 범위**: 회원 정지는 `active` 회원만 바꾼다. 이미 정지된 회원을 다시 정지하면 409 `already_suspended`(전에는 200으로 사유를 덮어쓰고 제재 쪽지를 또 보냈다), 탈퇴한 계정은 404(전에는 `suspended`가 됐고 해제하면 `active`로 돌아갔다). 두 관리자가 동시에 정지해도 상태 변경·쪽지·감사는 하나이고, 늦은 쪽 콘솔은 안내를 띄우고 회원 정보를 다시 불러온다. 신고에서 준 정지의 신고 처리 기록(`sanction`)은 정지가 반영된 뒤 따로 쓰므로, 그 사이에 실패하면 기록만 빠질 수 있다(감사 로그에는 `reportId`가 남는다). 해제를 동시에 두 번 보내면 둘 다 200이고 두 번째 감사의 `to`는 읽은 시점의 상태다(쪽지는 하나). 빈 테이블을 거의 동시에 두 번 닫을 때 늦은 요청이 이미 닫힌 테이블을 `closing`으로 되돌릴 수 있다는 가설은 128회 시도에서 재현되지 않아 코드를 바꾸지 않았다. 대량 목록 시간(회원 5,000명·원장 5만 행·감사 2.5만 행에서 쪽당 중앙값 14–28 ms)은 로컬 workerd·sqlite에서 잰 값이고 운영 D1에서는 재지 않았다. 배포는 api → admin(안내 문구), 마이그레이션 없음.
20. **Codex 리뷰 뒤 바꾼 것과 범위**: (1) 상태 API는 공지를 긴급 → 점검 안내 → 일반 순으로, 같은 종류 안에서는 표시 중인 공지는 최근 시작 순·예약 공지는 이른 시작 순으로 20개까지 주고, 잘렸으면 잘린 목록에서 가장 먼저 바뀌는 시각(`refreshAt`)을 함께 준다. 웹은 그 시각이 지나면 30초 주기 안에 다시 읽는다(잘리지 않았으면 전처럼 변경 번호로만 다시 읽음). (2) 닫은 기록은 일반 공지에만 적용해, 닫은 일반 공지가 긴급·점검 안내로 바뀌면 다시 보인다. (3) 정지는 상태를 바꾼 바로 다음에 테이블을 정리하고 그 뒤에 신고 기록·쪽지·감사를 쓴다. 이미 정지된 회원에게 정지를 다시 보내면(미리보기 아님) 409 `already_suspended`와 함께 그 회원의 연결·좌석을 다시 정리하고 결과를 `error.details.kick`으로 준다(콘솔은 결과를 보여 주고 회원 정보를 다시 불러옴). 콘솔은 정지된 회원에게 정지 버튼을 보이지 않으므로, 콘솔에서는 '연결 종료'(자리 비우기 포함)가 다시 정리하는 길이다. 정리 뒤 신고 기록·쪽지·감사가 실패하면 그 기록만 빠질 수 있다. (4) 룸은 핸드를 기록하는 D1 batch에서 점검을 함께 읽는다(SELECT 1개, 인덱스, 0–1행). 그래서 점검 알림을 받지 못한 채 사람이 그대로인 테이블도 진행 중이던 핸드 하나까지만 마친다. 점검을 취소·단축했는데 알림을 받지 못한 조용한 룸은 원래 종료 알람이나 다음 기록 때까지 멈춰 있을 수 있다. (5) 바이인 결과를 아직 모르는 좌석이나 충전 차감 중인 좌석에서 나가면 그 나가기를 바로 저장해(그 경우에만 DO 저장 1회 추가), 재시작 뒤 바이인이 확인되면 앉히지 않고 한 번 환급한다. 강제 퇴장(정지) 경로의 같은 경우는 끝까지 재현하지 못했고 나가기 경로로 확인했다. (6) 테이블 입장 제한(`entryBlocked`)을 바꾸는 PATCH /tables/:id도 비밀번호 재확인이 필요하다(전에는 /control만 요구). 이전 콘솔은 기존 재확인 창을 띄운다. 마이그레이션 없음, 배포 순서 제약 없음(새 web·admin은 이전 api의 응답에서도 동작).
21. **운영진 표시의 범위**: 역할은 지금 값으로 보인다. 핸드 기록·리플레이·게시판의 지난 글도 현재 역할을 따른다(당시 역할을 따로 저장하지 않음). 채팅은 보낸 순간의 역할이 줄에 실리므로 이미 보낸 줄은 권한을 바꿔도 그대로다. 권한 변경은 그 회원이 앉아 있는 테이블(`table_sessions`)의 룸에만 바로 알리고, 관전만 하는 연결은 다시 연결할 때 새 역할을 읽는다(그 전까지 보내는 채팅 줄도 이전 역할). 룸이 답하지 않으면 저장 응답의 `reached`가 `tables`보다 작고, 그 테이블은 회원이 다시 연결할 때 바뀐다. 문장 속 이름(친구 추가 결과 안내, 테이블 초대 목록의 방장, 쪽지의 보낸 관리자, 게시판 답글의 `@이름`)에는 표시를 넣지 않았다. 관리자 콘솔은 기존 권한 열을 그대로 쓴다. 웹의 `cx`는 클래스를 합치지 않고 이어 붙이므로 `MemberName`에 폭 제한을 넘기면 컴포넌트의 `max-w-full`이 이길 수 있다(좌석은 감싸는 요소에 제한을 둠). 배포 순서는 api·game-worker → web이다(마이그레이션 없음. 이전 웹은 `role`을 무시하고, 이전 룸은 즉시 반영 요청을 몰라 `reached`에서 빠진다). 소셜 정책으로 표시를 숨기는 것도 회원 화면의 현재 값만 바꾸며, 지난 기록에 남기지 않는다(37번).
22. **BB 표시의 범위**: 화면에 보이는 BB는 소수 둘째 자리에서 반올림한 값이라, 빅블라인드로 나누어떨어지지 않는 칩(예: BB 30에서 100칩 = 3.33 BB)은 칩과 정확히 같지 않다. 지갑에서 칩이 오가는 버튼에는 그래서 칩을 함께 쓴다. BB로 입력한 베팅은 가장 가까운 정수 칩으로 바뀌므로(BB 20에서 2.524 → 50칩) 보내기 전에 칸 옆의 칩 수가 기준이다. 설정은 기기(브라우저)별로 저장되고 계정과 동기화되지 않는다. 빅블라인드가 기록되지 않은 이전 핸드 기록은 BB를 골라도 칩으로 보인다. 금액이 문장 속에 들어간 안내(충전·리바이 결과 알림, "보유 칩" 같은 문구, 헤더의 블라인드 표시)는 칩으로 남겼다. 마이페이지 핸드 상세의 액션 목록에서 '레이즈' 금액은 지금처럼 그 액션에서 더 낸 칩이고, 리플레이의 단계 문장은 'N BB까지 레이즈'처럼 그 액션 뒤 좌석의 베팅 총액으로 읽는다(테이블에 보이는 베팅 칩과 같은 값. 목록은 칩이 오간 양이라 그대로 둠). 서버·DB·프로토콜 변경 없음(웹만 배포).
23. **점검 중 버튼의 범위**: 버튼은 받아 둔 점검 정보(시작·종료 시각)와 서버 시각으로 켜고 끈다. 관리자가 점검을 일찍 끝내면 안 읽음 폴링의 변경 번호가 바뀔 때 다시 읽으므로 그때까지 버튼이 꺼져 있을 수 있다(서버는 이미 받아 준다). 점검 중에는 로비의 입장 버튼이 꺼지므로, 관전 금지 테이블에 앉아 있다가 로비로 나온 회원은 로비에서 그 테이블로 돌아갈 수 없고 브라우저 뒤로 가기나 주소로 돌아가야 한다(로비 목록에 회원별 착석 정보가 없다). 관리자·슈퍼관리자도 게임 입장은 막히고(서버와 같음), 게시판 쓰기만 열려 있다.
24. **운영진 신고·차단 규칙의 범위**: 회원은 관리자·최고 관리자를 차단할 수 없고(403 `block_staff`), 최고 관리자는 신고할 수 없다(403 `report_super_admin`, 신고하는 사람이 운영진이어도 같음). 관리자는 신고할 수 있다. 규칙은 신고·차단하는 순간 대상의 현재 역할로 정한다. 운영진이 되기 전에 받은 차단과 이 규칙 전에 저장된 차단은 지우지 않고(회원 데이터를 지우는 운영 DB 변경을 피함) 운영진인 동안 효과만 없앤다. 다시 일반 회원이 되면 그 차단이 되살아난다. 최고 관리자가 되기 전에 접수된 신고는 그대로 남는다. 관리자에 대한 신고는 다른 신고처럼 관리자 콘솔의 신고 목록에 들어가며, 신고된 관리자 본인이 그 신고를 처리하는 것을 막는 규칙은 아직 없다. 테이블 채팅 뮤트는 차단이 아닌 기기 로컬 설정이라 운영진에게도 쓸 수 있다. 이전 웹은 버튼을 그대로 보이고, 누르면 서버 거절이 일반 오류 문장으로 보인다.
25. **빠른 반응의 범위**: 반응은 룸 메모리에서만 오가고 저장하지 않는다. 그래서 룸이 다시 시작되면(배포·유휴 후 깨어남) 보내는 속도 기록도 지워져, 그 직후에는 반응 제한이 처음부터 다시 센다(칩·카드·핸드에는 영향 없음). 제한과 켜기는 0028부터 소셜 정책이 정한다(37번). 연결이 끊긴 동안 온 반응과 숨긴 탭에서 받은 반응은 다시 보내지 않는다. 보낸 반응은 실패해도 다시 시도하지 않는다(늦게 뜨는 반응은 의미가 없음). 화면이 미리 막지만 그래도 룸이 거절하면 '요청이 너무 많습니다' 알림이 뜬다. 반응 설정은 이 기기에만 저장된다. 이전 웹은 반응을 받아도 무시하고, 새 웹이 이전 룸에 반응을 보내면 `bad_request`가 오므로 game-worker를 먼저 배포한다.
26. **무료 칩 보충의 범위**: 마이그레이션 0020이 정책 1판(켜짐, 합계 1,000칩 미만, 2,000칩, 대기 6시간)을 넣으므로 배포하면 바로 받을 수 있다. 개발용 기본값이라 운영 금액은 배포 직후 최고 관리자가 관리자 콘솔(경제 → 무료 칩 보충)에서 정해야 하고, 꺼 두려면 정책에서 끄거나 긴급 중지한다. 핸드 중에는 핸드 시작 때 스택을 세므로 그 핸드에서 잃을 수 있는 칩도 가진 칩으로 본다(핸드 중 받는 것은 막지 않음). 앉은 테이블마다 룸에 한 번씩 묻고(앉은 곳이 없거나 지갑만으로 기준 이상이면 묻지 않음), 이전 룸은 `holdings`를 몰라 '확인할 수 없음'으로 보류되므로 game-worker를 먼저 배포한다. 보류는 자동으로 다시 시도하지 않는다(회원이 다시 누르면 다시 확인). 거절 사유별 수는 일별 카운터(`daily_stats`의 `rf_*`)라 카운터 쓰기가 실패하면 빠질 수 있고, 같은 회원이 여러 번 눌러도 매번 센다. 자주 받는 회원은 기간 안 3회 이상이면서 대기 시간이 허락하는 최대 횟수의 절반 이상인 회원이며 검토용일 뿐이다. 정지된 회원은 받을 수 없다. 지급 기록은 정책 버전과 그때의 지갑·테이블 칩을 함께 남기고, 회원 상세는 보충 뒤 그 보충을 가리킨 관리자 조정만 회수로 보여 준다. 배포 순서는 마이그레이션 0020 → game-worker → api(web 포함) → admin(GitHub Actions 배포 순서와 같고, game-worker가 api보다 먼저면 된다)이다.
27. **테이블 봇의 범위**: 마이그레이션 0021은 정책 1판을 꺼짐(기금 한도 0, 최대 봇 0)으로 넣고 모든 테이블의 봇 설정도 꺼 두므로, 쓰려면 최고 관리자가 봇 운영에서 정책을 켜고 공식 테이블마다 봇을 켠다(개발 시드만 켜진 정책과 봇 테이블을 넣음). 봇은 규칙과 상대 레인지에 대한 몬테카를로 승률로 결정한다(봇 AI 2.0, 항목 47과 `docs/BOT_AI.md`). 보통 이상은 그 테이블에서 본 회원의 공개 액션과 쇼다운으로만 성향을 세어 적응하고(룸 저장소, 테이블이 닫히면 지움), 테이블 사이나 D1로는 옮기지 않는다. 봇 계정은 다시 쓰이고 지갑에 남은 칩은 다음 착석에 쓰여, 기금은 바이인보다 모자란 만큼만 발행한다. 봇은 늘 100 BB(바이인 범위 안)로 앉고, 일어났다 다시 앉을 때 칩을 제한하는 규칙은 없다. 회원 최소 인원은 자리 비움이 아닌 회원으로 세어 봇을 앉히고, 자리 비움 회원도 앉아 있는 동안은 봇을 일어나게 하지 않아서, 혼자 앉은 회원이 자리를 비우면 봇끼리 핸드를 칠 수 있다(자리 비움 10분 뒤 회원이 일어나면 봇도 일어남). 봇 착석이 실패하면(정책 꺼짐·기금 소진·최대 봇 수·오류) 60초부터 두 배씩 최대 30분 기다렸다 다시 시도하고, 테이블 설정이나 정책을 바꾸면 바로 다시 시도한다. 엔진이 봇의 결정을 거절하면 체크(낼 칩이 있으면 폴드)로 대신하고 실패 기록을 남긴다. 핸드 기록·리플레이에는 BOT 표시만 있고 그때의 난이도는 남기지 않는다. 봇이 한 명이라도 친 핸드는 운영 통계에서 공식·회원 방 핸드가 아니라 봇 핸드로 세고(배포 전 핸드는 그대로), 착석 수·착석 시간·동시 착석은 회원 좌석만 센다. 봇 바이인 도중 룸이 다시 시작된 경우(결과를 모르는 봇 좌석의 복구)는 코드로 처리하지만 자동 테스트는 없다(실패 뒤 60초 대기 때문에 통합 테스트로 재현하기 느림). 운영 환경에서 봇을 켜 본 적 없고 기금 한도·최대 봇 수의 운영 값도 정하지 않았다. 이전 웹은 `bot` 표시를 몰라 봇을 회원처럼 보여 주고, 봇에게 친구 신청 등을 누르면 409 `bot_account`가 일반 오류 문장으로 보인다. 휴대폰 세로 6인 테이블에서 이름 칸이 상한까지 찬 왼쪽 좌석 판이 화면 밖으로 7px 나가던 것은 좌석 배치를 좌석 판의 실제 크기로 계산하도록 바꿔 고쳤다(알려진 문제 29, 360·375·390px 6인 봇 테이블 E2E에서 모든 좌석이 화면 안). 배포 순서는 마이그레이션 0021 → game-worker → api(web 포함) → admin이다(`docs/DEPLOYMENT.md` 배포 점검표).
28. **추천 보상의 범위**: 정책은 마이그레이션 0022에서 꺼진 상태로 시작한다(위 미구현 항목). 가입 때의 금액·핸드 조건은 그 추천에 고정되고, 일일·총 한도와 지급 중지는 지급하는 순간의 정책을 따른다(일일 한도의 날짜 경계는 한국 시간 자정). 대기 중인 추천은 가입 직후, 둘 중 한 회원이 추천 카드를 열 때(한 번에 10건), 매일 cron(오래 확인하지 않은 순 50건), 관리자 정산에서만 지급되므로, 핸드 조건을 채운 뒤에도 두 회원이 카드를 열지 않으면 cron 차례까지 늦어질 수 있다. 핸드 조건은 어느 테이블의 핸드든 세므로 추천인과 새 회원이 같은 테이블에서 친 핸드도 들어간다(둘 사이에 칩을 몰아주는 플레이를 추천 기능이 따로 찾지는 않는다). 같은 메일함 판별은 소문자·`+태그`·Gmail 점만 정규화하므로 다른 별칭 규칙(예: `-` 별칭)이나 다른 메일 주소는 다른 사람으로 본다. 이메일 인증을 끈 환경에서는 인증하지 않은 주소도 지급 대상이다(인증이 켜진 운영은 가입 때 인증). 같은 IP 표시는 가입 때 IP가 추천인의 남아 있는 회원 세션 IP와 정확히 같은지만 보고(세션이 만료되면 모름), 다수 가입 검토는 한 추천인에게 하루 안에 같은 네트워크에서 온 가입만 세므로 여러 네트워크로 나뉜 가입은 잡지 못한다. 어느 것도 자동으로 거절하지 않는다. 검토 거절은 지급하지 않은 쪽만 닫고, 이미 준 칩은 관리자가 칩 조정에 원장 행을 연결해 회수한다. 해시는 `INTERNAL_SECRET`으로 만들므로 이 비밀을 바꾸면 그 전 가입과의 같은 메일함·같은 네트워크 비교가 끊긴다. 가입 이메일의 해시는 탈퇴 뒤에도 기한 없이 남는다(법무 검토 필요, `docs/PRIVACY_OPERATIONS.md`). 지급 쪽지가 실패해도 지급은 되돌리지 않는다. 매일 cron의 네트워크 해시 삭제와 관리자 현황의 기간 집계는 `created_at`만의 인덱스가 없어 추천 행 전체를 읽는다(추천이 수십만 건을 넘으면 검토). 코드 확인 API는 IP당 60초에 30회로 제한하며, 맞는 코드에는 초대한 회원의 닉네임을 보여 준다. 개인정보 수집·이용 안내 버전을 `2026-10-16`으로 올렸다(새 가입부터 기록, 기존 회원에게 다시 동의를 받는 흐름은 없음). 이전 웹은 추천 칸이 없고, 이전 api는 `referralCode`를 무시해 그대로 가입한다. 배포 순서는 마이그레이션 0022 → api(web 포함) → admin이다(game-worker 변경 없음, `docs/DEPLOYMENT.md`).
29. **리플레이·테이블 배치의 범위**: 리플레이는 좌석 판·카드·베팅·팟·보드의 실제 크기로 배치를 계산해 겹치지 않게 놓는다. 세로 휴대폰에서 가장 작은 좌석으로도 테이블과 조작이 한 화면에 들어가지 않으면, 테이블을 높이가 정해진 창 안에 통째로 그리고 그 창을 스크롤한다(42번 (2)). 창 밖의 좌석은 손가락으로 밀거나 그 좌석의 단계로 가야 보인다. 결과 단계의 정산은 조작 아래에 있고, 상태 칸의 '정산 보기'로 머리글과 하단 메뉴 사이까지 스크롤한다(42번 (3)). 가로 휴대폰(844×390)의 실시간 테이블은 아래쪽 버튼 묶음 옆을 비워 테이블 영역 높이가 214px에서 286px로 늘었지만, 겹치지 않는 배치에는 2인도 320px(9인 336–460px)이 필요해 가장 덜 겹치는 배치를 쓴다(배치 계산의 겹친 면적 2인 15,598 → 3,588px², 9인 31,987 → 5,684–16,849px². 높이를 정할 수 있는 리플레이는 해당 없음). 44번에서 짧은 화면의 조작을 오른쪽 열로 옮겨 844×390의 테이블 영역이 624×338이 되었고, 칩·BB 모두 2·6·9인의 계산상 겹침이 0이다. 테이블 아래쪽 버튼 묶음은 실제 높이를 재서 비우지만, 지나가는 알림과 초보 모드가 아닐 때의 안내는 넣지 않아 잠깐 테이블 위에 뜰 수 있고, 연습 시나리오는 첫 질문 패널이 나올 때 테이블이 한 번 작아진다. 배치 계산은 9인·좁은 화면에서 로컬 PC 기준 가장 느릴 때 약 100–117ms이고 영역 크기·인원·내 자리·금액 단위가 바뀔 때만 다시 하며, 휴대폰 실기기에서는 재지 않았다. 가로 휴대폰(844px)에서 앱 머리글 메뉴 글자가 줄바꿈되던 것은 전체 검증(P12)에서 고쳤다(38번). 실기기(iOS Safari·Android Chrome)와 실제 노치 안전 영역은 확인하지 않았다(에뮬레이션만, `docs/TEST_REPORT.md` 리플레이 가림).
30. **리플레이 타임라인의 범위**: 타임라인·슬라이더는 저장된 종료 핸드 기록에서 만든 단계 사이만 오가고, 단계 사이의 상태를 만들어 내지 않는다. 다른 사람의 패와 쇼다운 문장의 족보는 쇼다운 단계부터, 공개된 패만 보인다. 조작 영역이 단계 문장·구간 버튼·슬라이더·재생 줄로 커져 휴대폰 리플레이의 테이블이 작아졌다. 열자마자 단계 문장·테이블(또는 테이블 창)·조작 전체가 하단 메뉴 위에 들어오는 것은 iPhone 15(393×852)·Pixel 7(412×839)·360×800 Android의 2·6·9인, 태블릿(768×1024)·데스크톱(1440×900)의 2·6·9인이다(42번 (2), 재생 줄이 하단 메뉴보다 22px 위). iPhone SE(375×667)는 제목 아래 남는 높이로는 쓸 만한 창이 안 되어, 리플레이를 머리글 아래로 한 번(161px) 스크롤해야 전부 들어온다. 노트북(1280×720)은 좌석을 한 단계 작은 크기까지만 줄여 재생 줄이 화면 아래 38–106px에 있다. 가로 휴대폰(844×390)은 조작이 테이블 옆 열에 있어(구간 버튼과 재생 줄이 두 줄씩) 재생 줄을 보려면 스크롤하고, 상태 칸이 사이드 팟 줄과 '정산 보기' 자리를 늘 잡아 조작이 이전보다 16–32px 아래에 있다(42번 (3)). 단계 문장 칸은 단계마다 테이블이 움직이지 않도록 그 핸드에서 가장 긴 문장의 높이를 미리 잡되 3줄까지만 보이고, 넘치면 말줄임으로 끝난다(전체는 정산과 화면 읽기 프로그램에). 처음·끝·속도는 보조 메뉴로 옮기지 않았다(좁은 화면은 재생 버튼과 속도의 글자를 숨기고 한 줄에 둠). 768px 태블릿에서 앱 머리글의 메뉴 글자가 줄바꿈되고 '로그아웃'이 네 줄로 꺾여 64px 머리글 아래로 약 8px 나오던 것은 전체 검증(P12)에서 고쳤다(38번). 실기기에서는 확인하지 않았다(`docs/TEST_REPORT.md` 리플레이 타임라인).
31. **핸드 복기의 범위**: 팟 크기 필터는 핸드마다 블라인드를 저장하지 않아 그 테이블의 **지금** 빅 블라인드로 센다(화면에 안내). 블라인드를 바꾼 테이블의 지난 핸드는 다르게 걸릴 수 있다. 필터를 건 목록은 한 쪽을 채우려고 그 회원의 핸드를 많이 읽을 수 있어 필터 요청만 회원당 1분 60회로 막는다(필터 없는 목록은 그대로). 운영 통계의 "지금" 수치는 통계를 열 때마다 `hand_notes`를 한 번 모두 센다(노트가 수십만 행을 넘으면 집계 방식을 검토). 기간 수치는 다른 운영 통계처럼 어제까지이고, 날짜별 카운터라 회원별로 나누지 않는다. 팟 오즈는 내가 콜하거나 폴드한 순간의 팟과 콜 금액만 쓰며, 기록과 맞지 않거나 팟별 기록이 없는 이전 핸드에서는 보이지 않는다. 북마크·태그는 버전 없이 마지막 저장이 이기고, 화면은 그 응답만 따른다(다른 기기에서 바꾼 것은 다시 열 때 보임). `before`만 주는 이전 목록 요청은 같은 시각에 끝난 핸드를 건너뛸 수 있다(새 화면은 `beforeId`를 함께 보냄). 휴대폰은 에뮬레이션(Pixel 7)으로만 확인했다(`docs/TEST_REPORT.md` 핸드 복기).
32. **PWA 설치의 범위**: 오프라인 캐시가 없어 설치한 앱도 연결이 없으면 열리지 않는다(게임·인증·비공개 카드를 기기에 캐시하지 않으려는 결정, 안내에 표시). 45번의 푸시 서비스 워커도 페이지·API를 가로채거나 저장하지 않는다. 설치가 모든 기기에서 되는 것은 아니다: 카카오톡·인스타그램·네이버 등 앱 안 브라우저는 설치할 수 없어 Safari·Chrome으로 열라는 안내와 주소 복사만 있고, iOS·삼성 인터넷은 설치 API가 없어 글 안내뿐이며 메뉴 이름과 위치는 브라우저·OS 버전마다 다를 수 있다('웹 앱으로 열기'는 iOS 26 이상). 컴퓨터는 브라우저가 설치 창을 넘길 때만 로비에 안내가 보인다(설정에는 늘 있음). 기기 판단은 사용자 에이전트로 하므로 에이전트를 바꾸는 브라우저에서는 다른 탭이 먼저 열릴 수 있다(모든 탭을 고를 수 있음). '나중에'·'30일'과 설치됨 표시는 그 기기 브라우저의 `localStorage`에만 남아 기기·브라우저마다 따로이고, 사이트 데이터를 지우면 다시 보인다. 홈 화면에서 지운 것은 브라우저가 알려 주지 않으므로 다시 설치 창을 넘길 때까지 '설치됨'으로 남는다. 아이콘은 maskable 아이콘이 없어 Android가 흰 바탕 안에 줄여 보일 수 있다. Pixel 7 에뮬레이션의 로비에는 늘 안내 패널이 보여 모바일 E2E 화면이 그만큼 아래로 밀린다. 실기기에서 설치·홈 화면 실행을 확인하지 않았다(에뮬레이션만, `docs/TEST_REPORT.md` PWA 설치).
33. **계정 설정 동기화의 범위**: 동기화 전부터 쓰던 기기의 설정(`jc.prefs`)은 그 기기에서 처음 로그인한 계정 하나만 가져가고, 계정 설정이 한 번도 초기화되지 않았을 때(세대 0)만, 계정에 값이 없는 항목만 채운다. 한 기기를 여러 계정이 쓰면 두 번째 계정은 기본값에서 시작한다. 충돌은 설정·즐겨찾기 한 칸씩 '더 나중에 바꾼 쪽'으로 정하며, 바꾼 시각은 서버 시각에서 기기가 말한 '몇 초 전'(최대 30일)을 빼서 정하므로 오래 오프라인이던 기기의 변경은 그 사이 다른 기기에서 바꾼 값에 진다. 즐겨찾기는 50개까지(넘으면 가장 오래 전에 켠 것부터 빠짐), 끈 즐겨찾기 기록은 100개·30일까지만 남아 그보다 오래 오프라인이던 기기가 다시 켤 수 있다. 로그아웃하면 저장된 설정은 지우지만 저장하지 못한 변경은 그 계정 이름으로 이 기기에 남겨 다음 로그인 때 보낸다. 마지막 동기화 시각은 10분 단위다. 동기화 코드 묶음(chunk)을 불러오지 못하면 '저장하지 못함'이 보이고 다시 로드·로그인할 때까지 계정과 맞추지 않는다(이 기기에는 적용됨). 관리자 초기화 미리보기의 즐겨찾기 수는 켜진 것만 센다. (자동 머크는 2026-10-19부터 설정이 아니어서 룸에 보내지 않는다.) 웹 번들 한도까지 약 0.7 KB만 남아 다음 화면 기능은 지연 로드해야 한다.
34. **시간 은행의 범위**: 남은 시간은 테이블마다 따로다(룸의 Durable Object 상태, D1에 없음). 다른 테이블로 옮기면 그 테이블에서 처음 지급량을 받는다. 같은 테이블에서는 일어난 뒤 6시간·100명까지만 보관하므로 그보다 오래 떠났다 오면 다시 받는다. 보충은 그 회원이 받은 핸드 수로만 센다. 마이그레이션 0025가 정책을 **켜진 상태**(공식·회원 방, 30초·60초·10초·10핸드마다 5초)로 넣어 배포 직후 다음 핸드부터 적용된다. 이 값은 개발 기본값이며 운영 값은 정하지 않았다. 사용 단위·최대값은 정책 버전으로만 바꾸고, 진행 중인 핸드는 받은 규칙을 끝까지 쓴다. 점검 중 거절과 봇이 은행을 받지 않는 규칙은 자동 테스트가 없다(코드로 확인).
35. **토너먼트의 범위**: 6인 한 테이블 SNG만 있고 멀티 테이블·리바이·애드온·참가비·상금·봇 참가는 없다(요청 범위 밖). 기본 템플릿 값(1,500칩, 5분 레벨 13단계, 턴 20초)은 개발 기본값이며 운영 값은 정하지 않았다. 6명이 모두 앉아 끝까지 가는 대회는 자동 테스트가 없다: 통합 테스트는 2인(헤즈업)·3인 대회를 끝까지 진행하고 정원 3명에 6명이 동시에 등록하는 경우를 확인하며, 브라우저 E2E는 2인 대회를 일시정지·운영 중단까지 확인한다(순위·레벨 규칙은 룸 단위 테스트). 이전 game-worker와 새 api가 섞인 배포 중의 동작은 확인하지 않았으므로 game-worker가 먼저 나가기 전에는 대회를 열지 않는다. 운영 환경에서는 확인하지 않았다.
36. **관리자별 기능 권한의 범위**: 스위치끼리는 서버가 묶지 않는다. 회원 제재·연결 종료·칩 조정·재설정 링크·계정 설정은 회원 상세에서, 긴급 제어는 테이블 화면에서 쓰므로 `members`·`tables` 없이 켜면 API로는 되지만 콘솔에서 찾아 쓸 수 없다(편집기가 경고). 스위치 하나가 여러 라우트를 연다: 회원 조회는 메모, 핸드 기록은 종료 핸드 카드 열람, 운영 통계는 아카데미 통계, 긴급 제어는 종료·타이머 복구를 포함한다. 감사 로그(자기 기록)와 보안 화면은 끌 수 없다. 시스템 비밀은 콘솔 API가 없어 스위치도 없다. 요청마다 `admin_permissions`를 한 번 더 읽는다(최고관리자는 읽지 않음). 마이그레이션 0027이 그때의 일반 관리자에게 23개를 모두 켜 두므로 배포 직후 할 수 있는 일은 그대로이고, 마이그레이션과 api 배포 사이에 관리자가 된 계정은 모두 꺼진 채 시작한다. 배포 순서는 마이그레이션 0027 → api → admin이다(이전 api는 새 테이블을 쓰지 않는다. 이전 콘솔은 스위치를 몰라 메뉴를 모두 보여 주고, 새 콘솔도 이전 api가 `grants`를 주지 않으면 그렇게 한다. 어느 쪽이든 판정은 그때의 api가 한다). 운영 환경에서는 확인하지 않았다.
37. **소셜 운영·브랜드 상태의 범위**: 정책은 서비스 전체에 하나다. 회원 한 명이나 테이블 하나만 다르게 하는 기능은 없고, 바꿔도 회원에게 쪽지를 보내지 않는다(개인에게 영향을 주는 조치가 아님). 저장하면 연결이 있는 열린 테이블을 연결 많은 순으로 100개까지 바로 다시 읽게 한다(각각 실패하면 한 번 더). 그보다 많거나 답하지 않은 테이블은 다음 핸드 기록 때(같은 D1 batch), 연결이 없는 테이블은 다음에 열릴 때 읽는다. 응답의 `unreached`·`more`로 보인다. 표시 숨김은 회원 화면의 지금 값만 바꾼다. 저장된 역할, 관리자 콘솔, 차단 금지(`block_staff`)·신고 금지(`report_super_admin`) 판단은 실제 역할을 쓰므로, 숨겨도 운영진은 여전히 차단할 수 없다. api는 운영진이 들어 있는 응답마다 정책을 한 번 읽는다(요청 안에서는 한 번). 브랜드 상태는 이 배포가 내는 응답만 본다. 카카오·페이스북이 캐시한 미리보기와 실제 공유 화면은 운영에서 각 디버거로 확인해야 하고, 이번 작업에서는 운영 확인을 하지 않았다. 검사 기준은 브랜드 배너 하나(1200×630 PNG)에 맞춰져 있다. 마이그레이션 0028이 없으면 새 game-worker의 테이블이 열리지 않고 운영진이 들어 있는 api 응답이 실패하므로, 배포 순서는 0028 → game-worker → api → web·admin이다(`docs/DEPLOYMENT.md` 3절). 섞인 동안의 동작은 다음과 같다. 이전 웹은 반응이 꺼진 새 룸에서도 버튼을 보이고, 누르면 일반 오류가 난다. 새 웹은 이전 룸에서 기본 제한을 쓴다. 이전 룸·api는 정책을 몰라 모든 표시를 보인다. 이전 콘솔에는 두 화면이 없다. 운영 환경에서는 확인하지 않았다.
38. **전체 검증(P12)의 범위**: 모든 검증은 로컬 workerd·D1·Durable Objects와 이 PC의 Chrome 155에서 했다. 운영 D1·Cloudflare 엣지·실기기에서는 하지 않았다. 통합 테스트에는 로컬 개발 도구 쪽 일시 오류가 두 종류 있어 전체 실행 한 번에 0–2건이 실패할 수 있다. 첫째는 `wrangler d1 execute --local`이 받은 임의 포트가 fetch의 금지 포트에 걸려 `fetch failed`로 끝나는 경우다. 둘째는 wrangler dev의 ProxyWorker가 끊긴 POST를 다시 보내지 않아 500 `Network connection lost`가 나는 경우다. 두 오류 모두 단정문 전 준비 단계에서 났고, 실패한 파일을 다시 돌리면 통과했다. G014에서 둘째 오류를 더 조사했다. `tournaments.test.ts`의 같은 준비 단계에서 자주 났고(그 파일만 연결을 데우지 않고 돌린 일곱 번 중 다섯 번), 1초마다 요청을 보내 연결이 쉬지 않게 하면 네 번 모두 나지 않았다. 쉰 시간만 맞춘 재현은 되지 않아 원인은 확정하지 못했다(`docs/TEST_REPORT.md` 통합 실패 조사(G014)). 테스트 도우미는 고치지 않았다. 출력만으로는 쓰기가 D1에 닿았는지 알 수 없어, 쓰기를 다시 보내면 두 번 반영될 수 있기 때문이다. 검증 중 찾은 앱 머리글 문제(640–1023px에서 메뉴 글자 줄바꿈, 영어에서 설정·쪽지·로그아웃이 화면 밖)는 고쳤다. 이제 그 너비에서는 워드마크·언어 전환·로그아웃을 머리글에서 빼고(언어와 로그아웃은 설정 창에 있음), 넘치는 메뉴는 가로로 스크롤한다. 640px에서 영어는 여섯 메뉴 중 넷, 한국어는 다섯만 보인다. 머리글은 데스크톱 Chrome 창 너비로만 쟀고, 태블릿 실기기·Safari·확대 배율은 확인하지 않았다. 휴대폰 화면은 Pixel 7 에뮬레이션만 확인했다(`docs/TEST_REPORT.md` 전체 검증(P12)).
39. **Codex 브랜치 리뷰(G014) 뒤 바꾼 것과 범위**: 브랜치 전체를 Codex(`task --effort high`)로 검토해 받은 지적 5건을 모두 고쳤다(마이그레이션 없음). (1) 자동 머크의 내부 보내기에 계정 설정 버전 `rev`를 실어, 빠르게 두 번 저장했을 때 늦게 도착한 예전 값이 좌석 값을 되돌리지 않는다. 플레이어의 `muck` 명령은 `rev`를 바꾸지 않으므로, 테이블에서 바꾼 뒤 더 새 계정 값이 오면 계정 값을 쓴다. (2) 추천 기록의 상태(대기·미지급 이유·검토)를 행을 넣는 한 문장에서 정해, 동시에 들어온 같은 메일함·같은 네트워크 가입도 한 번만 대기가 된다. (3) 테이블 설정 수정은 읽은 행이 그대로일 때만 쓰고, 끼어든 변경이 있으면 다시 읽어 보낸 열만 얹는다(최대 3번, 그래도 바뀌면 409 `table_conflict`). 콘솔은 보던 `updatedAt`을 보내 오래된 화면의 저장을 409로 막고 다시 불러온다. 이전 콘솔은 병합만 받는다. (4) 무료 칩 보충을 청구할 때 두 테이블 이상에 앉은 회원이 지급될 조건이면 모든 테이블에 한 번 더 묻고, 두 번 모두 같은 세션·스택·마지막 정산 핸드일 때만 지급한다(아니면 `busy` 보류, 다시 누르면 다시 확인). 상태 조회와 한 테이블 회원은 전처럼 한 번만 묻는다. 지급 조건일 때만 룸 호출이 테이블 수만큼 늘어난다. (5) 대회 시작 batch가 참가자 자격(활성·봇 아님·인증·다른 대회 자리 없음)을 다시 조건으로 걸어, 자격 확인과 batch 사이에 정지된 회원이 `playing`으로 시작하지 않는다(다시 읽어 `dropped`). 시작이 커밋된 뒤의 정지는 기존 정지 경로를 따른다. (2)·(5)는 단위 테스트로 수정 전 코드에서 실패하고 수정 뒤 통과하는 것을 확인했다. (2)는 테스트를 먼저 쓰고 고치기 전에 실패를 확인했고, (5)는 수정 전 파일을 새 임시 사본으로 만들어 같은 테스트를 돌린 뒤 사본을 지웠다. (1)·(4)의 단위 테스트는 이번에 새로 나눈 함수를 시험하므로 수정 전 코드에 그대로 돌릴 수 없었다. (3)은 작업 파일을 수정 전 내용으로 덮어쓰는 단계가 자동 모드에서 거절되어 돌려 보지 못했다. 이 세 건은 수정 뒤 통과와 코드 검토로만 확인했다. (3)의 콘솔 화면은 두 관리자의 E2E로 확인했다. 배포 순서는 game-worker → api → admin이고 섞인 동안의 동작은 `docs/DEPLOYMENT.md` 3절에 있다. 운영 환경에서는 확인하지 않았다.
40. **종합 완성도 고도화(feat/polish, 2026-10-18)의 범위**: 새 기능, 서버·엔진·스키마·API 변경, 마이그레이션은 없다. (1) 칩·팟: 수정 전에는 스트리트마다 모든 좌석에서 25짜리 고정 칩이 팟으로 날았고, 지급은 승자마다 총액 칩을 네 번 날렸다. 이제 `apps/web/src/game/staging.ts`가 받은 cue로 베팅 → 팟 → 보드 → 쇼다운 → 지급(사이드팟 먼저, 스플릿은 한 명씩, 승자마다 한 번, 같은 좌석의 지급은 합침) 계획을 3.3초 안에서 세운다. 끝값이 서버 상태와 다르면 계획을 버리고 서버 상태를 바로 보인다. 연출은 보이는 시점만 늦추고 액션 바·합법 액션·타이머는 늦추지 않는다. 같은 버전의 상태는 cue를 다시 붙이지 않고, 연출 중 새 상태가 오면 따라잡고, 숨긴 탭에서는 멈춘다. (2) 카드: 상대 카드의 부채꼴과 승리 카드의 들림이 애니메이션 뒤 사라지던 것을 고쳤다. 쇼다운 패·승자·베스트 파이브는 연출 순서에 맞춰 보인다(가리기만 한다). (3) 액션: 처리 중 표시, 보내지 못한 누름 경고, 스택에서 나갈 금액, 미리 선택 취소 이유. (4) 사운드: 같은 소리 겹침과 동시 6개 제한(꽉 차면 새 배경 소리는 내지 않고, 중요한 소리는 가장 먼저 끝날 배경 소리를 멈추고 들어감), 숨긴 탭·멈춘 오디오의 소리는 버림, iOS 잠금 해제 보강, 승리 소리 볼륨. (5) 연결: 로비 필터를 주소에 두어 테이블에서 돌아와도 그대로, 핸드 목록 ↔ 핸드의 필터·개수·스크롤 유지, 핸드 ↔ 레슨·연습, 앉은 채 여는 핸드 기록·아카데미·지갑 링크는 새 탭. (6) 불러오기 실패에 다시 시도(쪽지, 게시판, 글, 친구, 대화, 핸드, 마이페이지, 관리자 감사 로그·회원 목록). 차단 목록 실패가 빈 목록으로 읽히지 않는다. 한계: 실기기에서는 확인하지 않았다(Chrome 모바일 에뮬레이션). 9인·가로 휴대폰 실시간 테이블 E2E는 없다(42번에서 더함). 작은 휴대폰의 리플레이 스크롤(29·30번)은 그대로다. 콜되지 않아 돌려받는 칩도 지급 칩으로 날아간다(42번에서 고침). 처음 만든 연출·사운드 테스트는 새 파일이라 수정 전 실패를 돌려 보지 못했다. (9) Codex 리뷰(읽기 전용, 코드만 읽음)의 지적 2건과 확인 중 찾은 1건을 고쳤다. 높음: 리플레이가 돌려받은 베팅을 화면에서 계산해 서버가 준 팟을 고쳐 썼다. 이제 서버(`replaySettlement`)가 핸드 통계의 `pot_won`으로 반환액을 정해 `returned`로 보내고, 엔진이 반환 팟을 따로 만들지 않은 핸드는 그 사람이 받은 마지막 팟에서 떼어 반환 팟으로 나눠 보낸다. 통계가 아직 없거나 기록과 맞지 않으면 저장 팟 그대로, `returned: null`이다. 팟·사람별 합계는 기록과 같고, 기록·원장·엔진은 바꾸지 않았다. 계산 테스트는 웹 단위에서 API 단위(새 8건)로 옮겼고, 실제 엔진 핸드로 통합 테스트 1건을 더했다. 중간: 관리자 이동 링크의 패널이 고정된 결과 밑에 가려졌다. 이제 고정된 결과의 높이(`--pin-h`)만큼 더 내려 세운다(되돌리면 E2E 실패). 직접 찾은 것: 이동한 패널이 위 패널들이 늦게 불러와지며 화면 밖으로 밀렸다(요청을 1.5초 늦추면 매번 재현). 이제 이동 뒤 페이지 크기가 바뀔 때마다 그 패널을 같은 자리에 맞추고, 운영자가 스크롤·탭·키를 쓰거나 8초가 지나면 멈춘다. 남은 한계: 통계가 채워지기 전 잠깐은 저장 팟 그대로 보이고, 8초보다 늦게 오는 패널은 다시 밀 수 있으며, 실기기에서는 확인하지 않았다(`docs/TEST_REPORT.md` 후속 개선 'Codex 리뷰와 반영').

59. **회원가입 WebView 호환·봇 계정별 난이도/스타일(feat/signup-webview-bot-profiles, 2026-10-26)**: Instagram·KakaoTalk 인앱 브라우저에서 값이 다 맞는데도 가입 버튼이 켜지지 않던 문제를 고치고, 봇의 난이도와 스타일을 나눠 관리자가 봇 계정마다 정하게 했다. 마이그레이션 `0034_bot_profiles`를 더한다(`docs/TEST_REPORT.md` '회원가입 WebView 호환·봇 계정별 난이도/스타일').
    - 가입 원인: 입력칸이 React 제어 입력칸이라 `input` 이벤트로만 상태가 바뀌었다. WebView의 자동 완성·비밀번호 관리자·날짜 선택기처럼 `input` 없이 값을 바꾸면 상태가 빈 채 남고, 다음 렌더가 DOM 값까지 지워 버튼이 꺼진 채였다(Chromium·WebKit에 인앱 User-Agent를 준 에뮬레이션에서 재현).
    - 가입 수정: 칸을 제어하지 않고 `useFieldSync`가 여러 이벤트·돌아오기·0.7초 확인으로 DOM 값을 읽는다. 버튼 조건은 `signupValidation` 하나이고, 꺼져 있으면 첫 이유를 버튼 위 고정 높이 줄에 보인다. 닉네임의 늦은 답·실패를 따로 다루고 서버의 '사용 가능'만 통과시킨다. 가입 옵션을 못 읽으면 '다시 시도'다(인증을 끄지 않음). 인증 토큰은 그 이메일에 묶이고, 탭의 `sessionStorage` 초안으로 새로고침·앱 전환을 견딘다(비밀번호·동의는 두지 않음). 날짜 입력을 지원하지 않는 브라우저만 텍스트 칸으로 바꾼다. 인앱 안내(기본 브라우저로 열기·주소 복사)는 강제하지 않고, User-Agent로 가입 로직을 나누지 않는다. 서버 검증·이메일 인증·레이트 리밋은 그대로다.
    - 봇: 난이도(정확도)와 스타일(경향)을 따로 정하고 봇 계정 값 > 테이블 값 > 시스템 기본(보통, 예전 해시 규칙 `auto`) 순으로 각각 상속한다. 관리자 → 봇 → '봇 계정'에서 계정마다 정하며(미리보기, 사유, 비밀번호 재확인, 동시 수정 409, 감사 `bots.profile`), 테이블 설정에 봇 스타일 칸(자동 혼합 + 다섯 스타일)을 더했다. 룸은 앉을 때와 딜할 때(5분마다, 2초까지만 기다림)만 읽고 액션마다 D1을 읽지 않는다. 다음 핸드부터 적용되고, 읽기에 실패하면 이전 값으로 딜한다.
    - 밸런싱: 전문가가 지나치게 강한지 시뮬레이션(약 202만 핸드)으로 쟀다. 고치기 전 어려움보다의 우위(+12.4 BB/100)는 콜이 많은 상대에게 몰려 있었고 주된 원인은 얇은 밸류·오버벳이었다. 오버벳을 25%에서 12%로 줄여 +7.4가 됐다(무작위 실수는 더하지 않음, 헤즈업에서는 구별 안 됨). 쉬움의 블러프·밸류를 올리고 스타일 계수를 넓혀, 스타일 검사 11개가 네 난이도 모두에서 통과한다(`docs/BOT_AI.md` 11절).
    - 테스트: 단위 엔진 102·웹 599·API 173·game-worker 65, 통합 전체 51개 파일 416건, 로컬 E2E 42건(가입·인증·봇·관리자·테이블·칩·토너먼트·리플레이)이 통과했다. 인앱 User-Agent를 준 Chromium·WebKit 네 환경의 재현 스크립트가 최종 빌드에서 13가지 입력 방식 모두 버튼이 켜졌다. 빌드·로컬 마이그레이션과 번들 가드(첫 화면 643KB/650KB, main보다 +13KB)가 통과했다.
    - Codex 리뷰: 1차 리뷰는 판단 시간 백분위의 넘침 칸 표기(P2)를 짚어 고쳤다. 적대적 리뷰의 [high] 'D1 읽기가 룸 큐를 시간 제한 없이 막음'은 2초 상한으로 반영했고, [medium] '프로필 쓰기와 감사 기록이 한 트랜잭션이 아님'은 기존 관리자 변경 모두의 패턴이라 반영하지 않았다. 수정 뒤 2차 리뷰는 지적 없음.
    - 한계: 실제 Instagram·KakaoTalk 앱과 실기기에서는 확인하지 않았다(Chrome·WebKit 에뮬레이션만). 보통과 어려움은 BB/100으로 구별되지 않는다. 시뮬레이션 상대는 정해진 규칙의 봇이라 사람이 느끼는 세기는 재지 않았다. 프로필 저장과 감사 기록은 다른 관리자 변경처럼 따로 쓰인다(둘을 한 트랜잭션으로 묶지 않음). 첫 화면 번들이 한도에 7KB 남았다.
