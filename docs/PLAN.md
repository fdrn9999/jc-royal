## 1. 프로젝트 정의

- **JC ROYAL(제이씨 로얄)**: 현금 가치가 없는 무료 가상 칩으로 즐기는 프리미엄 웹 소셜 카지노. 오락 및 개발 포트폴리오 목적.
- **게임 7종**: 텍사스 홀덤 포커룸(대표), 블랙잭, 바카라, 룰렛, 카지노 홀덤, 쓰리카드 포커, 슬롯머신.
- **품질 축**: UI · UX · SOUND.
- **하지 않는 것**: 실제 현금 입출금, 환전, 암호화폐, 현금성 경품, 칩의 외부 거래·사용자 간 양도, 관리자의 결과 조작, 잔액·연패에 따른 확률 변경.

### 로고

`assets/branding/logo.png`(금색 스페이드 + 왕관 + JC 모노그램, 1254×1254 PNG)를 원본으로 사용한다.

- favicon, 앱 아이콘(PWA 192/512, apple-touch), 로딩 로고는 이 PNG에서 리사이즈해 생성한다.
- 원본이 래스터 이미지라 요구사항의 "SVG 로고"는 자동으로 얻을 수 없다. 16~32px 파비콘에서는 세부 묘사가 뭉개지므로, **단순화한 단색 SVG 마크(스페이드 실루엣 + JC)** 를 PHASE 1에서 별도로 제작한다. 풀 컬러 로고는 PNG/WebP를 유지한다.

**게임 관련 설계 원칙**

- **공통 게임 셸**: `packages/ui`의 `GameShell`과 공통 베팅 상태 훅으로 구현하고 각 게임은 테이블 영역과 엔진 어댑터만 제공한다. 포커룸은 실시간 구조가 달라 상단 바·사운드·기록 패널만 공유한다.
- **스테이크 등급**: 등급은 베팅 한도만 다르고 규칙·확률·지급표는 동일하다. 한도는 서버에서 검증한다.
- **빠른 진행·오토 스핀**: 자동 진행은 횟수 상한과 손실 한도 설정이 필수이며, 책임 이용 제한(플레이 시간·휴식)에 걸리면 즉시 멈춘다. 잔액 부족·보너스 진입·탭 비활성 시에도 멈춘다. 터보는 연출 시간만 줄이고 서버 처리는 동일하다.
- **올인 승률 표시**: 모든 홀카드가 공개된 뒤에만 계산·표시한다(공개 정보만 사용).
- **래빗 헌팅·Run It Twice**: 남은 보드는 핸드 시작 시 커밋한 덱 순서 그대로 사용한다(Provably Fair 검증 대상에 포함). 래빗 헌팅은 핸드 종료 후에만 공개하고 머크된 홀카드는 공개하지 않는다. Run It Twice는 올인 당사자 전원이 동의할 때만 적용하고 팟을 절반씩 정산하며, 홀수 칩 규칙을 `GAME_RULES.md`에 명시한다.
- **사이드 벳**: 종류마다 공개된 표준 지급표 하나를 선정해 지급표와 이론 RTP를 `GAME_RULES.md`에 기록하고, `game_rule_versions`로 on/off 한다. 사이드 벳은 본 베팅보다 하우스 엣지가 높다는 점을 지급표 패널에 표시한다.
- **블랙잭 전략 힌트**: 적용 중인 규칙(덱 수, S17, DAS 등)에 맞는 기본 전략표를 사용한다. 본인 카드와 딜러 업카드만 사용하며 기본값은 꺼짐이다. 실시간 조언 도구 금지 원칙은 사람끼리 겨루는 포커룸에만 해당한다.
- **룰렛 통계·바카라 로드맵**: 과거 결과 표시일 뿐이며 각 회차는 독립이라는 안내를 화면에 함께 둔다.
- **스퀴즈·연출 일반**: 결과는 서버에서 확정된 뒤 연출만 수행한다. 연출 도중 연결이 끊겨도 정산은 이미 완료되어 있다.
- **원근 뷰**: DOM + CSS 3D transform으로 구현한다(결정 3.1 유지). 베팅 영역의 터치 타깃 크기가 기준 미만이 되는 화면에서는 평면 뷰로 전환한다.
- **픽 보너스**: 진입 시 서버가 시드로 상자별 보상 배치를 확정하고(해시 커밋), 사용자의 선택이 실제로 결과를 결정한다. 선택과 무관하게 금액이 미리 정해진 "보여주기식 선택"으로 만들지 않는다. RTP는 균등 선택 기대값으로 계산한다.
- **Royal Spade 슬롯**: 릴 스트립·지급표·보너스 규칙을 설정 파일로 정의하고, 전수 계산(가능한 범위)과 대규모 시뮬레이션으로 RTP를 검증해 지급표 화면에 공개한다.

### 추가 기능의 설계 원칙

- **게스트**: 싱글 플레이 게임만 가능. 포커룸·채팅·리더보드·친구는 정식 계정 전용. 게스트 생성은 Turnstile과 Rate Limit으로 보호하고, 미전환 게스트는 스케줄 작업으로 정리한다. **게스트 칩은 연습용이며 정식 계정으로 전환할 때 넘어가지 않는다**(전환 시 일반 가입 보너스만 지급). 게스트를 대량으로 만들어 잘 풀린 계정만 전환하는 것을 막기 위함이다.
- **칩 덤핑·담합 방지**: 사용자 간 양도 기능이 없어도 포커에서 일부러 져 주면 사실상 양도가 된다. 포커룸 입장은 이메일 인증을 마친 계정만 가능하고, 신규 계정에는 일정 기간 바이인 상한을 둔다. 반복되는 같은 상대, 비정상적인 폴드·올인 패턴, 같은 네트워크의 계정 묶음을 탐지해 보안 이벤트로 남기고 제재 흐름으로 넘긴다. 탐지 규칙은 PHASE 3b에서 봇·테이블 확장과 함께 넣는다.
- **보너스·리필·미션 보상**: 모두 지갑 원장(`wallet_transactions`)의 한 종류로 기록한다. 별도 경로로 잔액을 바꾸지 않는다.
- **봇**: 포커 테이블 Durable Object 안에서 동작한다. 봇 함수에는 사람 클라이언트가 받는 것과 같은 **공개 정보 객체(`PublicInformationSet`)만** 넘기고, 덱·상대 홀카드를 담은 테이블 상태는 타입 수준에서 접근할 수 없게 한다. "공개 정보가 같으면 상대 홀카드를 바꿔도 봇의 행동이 같다"를 테스트로 강제하고, 봇 정책 버전과 선택한 행동을 핸드 기록에 남긴다. 봇의 칩은 원장의 `BOT_TREASURY` 지갑에서 나오고(§4.4) 리더보드에는 집계하지 않는다.
- **채팅**: 길이 제한, Rate Limit, 금칙어 필터, 사용자 차단, 신고 → 관리자(ADMIN) 처리. 메시지는 React 텍스트 노드로만 렌더링한다(HTML 삽입 금지).
- **리더보드**: 순위 기준은 "보유 칩"이 아니라 기간 내 순획득·플레이 실적으로 하여 리필 반복으로 순위를 올릴 수 없게 한다. 랭킹 보상은 거래할 수 없는 외형 보상으로 한정하고, 담합 탐지에 걸린 계정은 집계에서 제외한다.
- **책임 이용**: 자기 제한은 서버에서 강제한다. 제한 완화는 대기 시간을 둔다.
- **포커 편의 기능**: 프리액션은 클라이언트에 예약만 해 두고, 실제 액션은 자기 턴이 왔을 때 일반 액션과 같은 경로로 서버 검증을 거친다(앞선 레이즈로 조건이 바뀌면 예약 취소). 족보 표시는 본인 카드와 공개된 커뮤니티 카드만으로 계산한다. 승률·상대 범위 같은 실시간 조언 도구는 제공하지 않는다. 타임뱅크는 서버 DO가 관리한다.
- **접근성·모션**: 색만으로 정보를 전달하지 않는다(무늬·문자 병기). `prefers-reduced-motion`과 계정의 "애니메이션 강도" 설정 중 더 약한 쪽을 적용하며, 연출을 줄여도 게임 진행 정보는 빠지지 않게 한다.
- **승리 연출**: 강도는 베팅 대비 배당 배수로 서버가 등급을 정해 내려보낸다. 결과 수치는 연출 시작 시점에 이미 확정·표시 가능해야 하고, 탭/클릭으로 건너뛸 수 있다. 과도한 네온·점멸은 쓰지 않는다. 손실을 승리처럼 연출하지 않는다(순손실 라운드에 승리 효과 금지).
- **앰비언트 사운드**: BGM은 사용자 첫 입력 이후에만 시작하고, 탭이 백그라운드로 가면 멈춘다. 음악 레이어 전환은 서버가 보낸 게임 상태 이벤트에만 반응한다.
- **해금형 커스터마이징**: 순수 외형이며 게임 결과·확률에 영향을 주지 않는다. 구매·거래·양도 불가.
- **관리자 모니터링은 관측 전용**: RTP·실시간 모니터는 결과에 개입하는 수단을 제공하지 않는다. 라이브 뷰에는 미공개 카드·시드가 포함되지 않는다. 테이블 강제 종료는 진행 중 핸드의 베팅을 환불하고 스택을 지갑으로 반환한다.
- **경제 설정**: 변경은 다음 지급 시점부터 적용되고 이미 지급된 내역에 소급하지 않는다. 게임 확률·지급표는 여기서 바꿀 수 없다(규칙은 `game_rule_versions`로만 공개 관리).
- **점검 모드**: 새 라운드 시작만 차단하고 진행 중인 라운드·핸드는 끝까지 처리한 뒤 정산한다.
- **제재**: 모든 제재는 사유·기간·처리자를 기록하고 대상 사용자에게 사유를 안내한다. 정지 시 해당 사용자의 세션을 즉시 무효화한다.
- **감사 로그 해시 체인**: 각 행에 순번 `seq`(UNIQUE), `prev_hash`, `hash = SHA-256(prev_hash ‖ 정규화한 행 내용)`을 저장한다.
  - 관리자 변경 작업과 그 감사 행은 **같은 D1 배치**로 쓴다(작업만 성공하고 기록이 빠지는 일을 막음).
  - 두 요청이 같은 `prev_hash`를 읽고 동시에 쓰면 `seq` UNIQUE 충돌로 한쪽이 실패하고 재시도한다. 체인이 갈라지지 않는다.
  - D1 관리자 권한으로 체인 전체를 다시 쓰는 것까지는 막지 못한다. 체인 헤드 해시를 주기적으로 R2에 **시각별 새 객체**로 추가하고 버킷 잠금으로 덮어쓰기·삭제를 막아 사후 탐지 범위를 넓힌다. 같은 Cloudflare 계정 안이라는 한계는 남으므로 `SECURITY.md`에 명시한다.
  - **DB가 둘이라 체인도 둘이다.** 관리자 계정·초대·키·복구·관리자 세션 변경은 관리자 DB 안의 별도 감사 체인(`admin_audit_logs`)에 같은 배치로 쓴다. 서비스 데이터 변경은 공용 DB의 `audit_logs`에 같은 배치로 쓴다. 두 DB에 걸친 작업을 하나의 배치로 묶을 수는 없으므로, 관리자 DB 체인의 항목은 보류함(outbox)을 거쳐 공용 체인에도 사본을 남긴다(지연 복제). 감사 화면은 두 체인을 시간순으로 합쳐 보여 준다.
  - 공용 `audit_logs`의 행위자는 다른 DB에 있는 관리자 계정이라 FK를 걸 수 없다. 대신 그 시점의 관리자 ID·아이디·역할을 행에 복사해 저장한다.
- **요청·승인**: 민감 작업은 ADMIN이 요청하고 SUPER_ADMIN이 보안 키 재인증으로 승인한다. 요청자가 자기 요청을 승인할 수 없다(§6 차등 권한표).
- **내보내기**: 내보내기 실행 자체를 감사 로그에 기록하고, 비밀번호 해시·세션 토큰·시드 등 비밀 값은 대상에서 제외한다.

**로비 설계 원칙**

- **실시간 정보의 출처**: 포커 인원·테이블 수는 `LobbyDO`가 집계한다. 로비는 WebSocket을 열지 않고 짧은 주기로 조회하며 응답을 짧게 캐시한다(로비에 머무는 사용자마다 연결을 유지하는 비용을 피함). 바카라·룰렛 타일의 기록은 공용 테이블이 없으므로 **본인의 최근 결과**이고, 과거 결과가 다음 결과를 알려 주지 않는다는 안내 원칙을 그대로 따른다.
  - 테이블 DO는 주기적으로 상태를 보고하고(heartbeat), `LobbyDO`는 일정 시간 보고가 없는 테이블을 목록에서 뺀다. 죽은 테이블의 인원이 현황에 남지 않게 하기 위함이다.
  - 로비가 보여 주는 빈자리는 **표시용**이다. 실제 착석은 테이블 DO가 그 순간의 좌석 상태로 다시 확정한다.
  - 개별 DO에는 처리량 한계가 있으므로, 규모가 커지면 `LobbyDO`를 블라인드 단계별로 나눈다(초기에는 하나로 시작).
- **이어하기**: 진행 중 라운드는 `GameSessionDO`, 착석 중 테이블은 `poker_escrows`의 활성 상태에서 읽는다. 로비에 들어올 때마다 서버에서 확인하므로 다른 기기에서 시작한 게임도 보인다.
- **바로 입장**: 테이블 선택은 서버가 한다. 빈자리가 있는 테이블 중 인원이 많은 곳을 우선하고, 차단한 상대가 있는 테이블은 피한다. 사용자가 상대를 고를 수 없으므로 칩 덤핑 목적의 동석을 어렵게 하는 효과도 있다. PHASE 3a에서는 맞는 테이블이 없으면 빈 테이블을 열고 대기하며, 봇이 들어온 뒤(3b)에는 봇으로 채운다.
- **한 번에 한 테이블**: 사용자별 활성 포커 좌석은 하나만 허용한다. D1의 `poker_seat_leases`(사용자 ID UNIQUE)를 에스크로 예약과 같은 배치로 잡고, 이석이 끝나 에스크로가 `CLOSED`가 될 때 푼다. 테이블 DO끼리는 서로의 좌석을 알 수 없으므로 이 제약은 D1에서 건다.
- **테이블 미리보기·관전**: 공개 정보만 보여 준다. 홀카드는 미리보기와 관전 어디에도 나오지 않는다.
- **초대 링크·코드**: 추측할 수 없는 무작위 토큰을 쓰고, 짧은 코드는 입력 시도 횟수를 제한한다. 방장이 만료 시각을 정하고 언제든 회수할 수 있다. 링크로 들어와도 로그인·이메일 인증·바이인 조건은 그대로 적용된다.
- **비밀방과 칩 덤핑**: 비밀방은 상대를 직접 고를 수 있어 "바로 입장"의 무작위 배정 효과가 없다. 비밀방의 결과는 리더보드·미션·업적 집계에서 제외하고, 바이인 상한을 일반방보다 낮게 두며, 담합 탐지 규칙을 더 엄격하게 적용한다.
- **실시간 현황**: 실제 값만 표시하고 부풀리지 않는다. 봇은 접속자 수에 넣지 않는다.
- **큰 족보·빅윈 피드**: 실제로 일어난 일만 싣고 가짜 항목을 만들지 않는다. 봇의 결과는 싣지 않는다. 칩 금액 대신 족보 이름과 배당 배수를 보여 준다.
  - **로그인한 사용자에게만** 보여 주고 비로그인 랜딩에는 싣지 않는다.
  - 항목은 정산이 최종 완료(`SETTLED`)된 뒤에만 발행하며 라운드당 한 번만 발행된다. 환불된 라운드는 싣지 않는다.
  - 닉네임은 일부를 가리고, 가입 시 피드 노출 여부를 안내하며 설정에서 끌 수 있다. 피드 자체를 숨길 수도 있다. 항목은 짧은 기간만 보관하고 탈퇴·닉네임 변경 시 삭제한다.
  - 책임 이용 한도에 걸렸거나 휴식 기간인 사용자에게는 피드를 보여 주지 않는다.
- **보너스 위젯**: 수령은 서버가 시각과 자격을 확인하고 원장에 기록한다. 위젯의 남은 시간은 표시용이다.
- **점검**: 점검 중인 게임의 타일은 흐리게 하고 예상 종료 시각을 표시한다. 진행 중이던 라운드는 끝까지 처리되므로 이어하기 배너는 계속 동작한다.
- **비로그인 랜딩**: 첫 방문 시 19+ 확인을 먼저 거친다. 둘러보기는 자유롭고 플레이는 게스트 또는 로그인이 필요하다.
- **하단 탭 바**: 게임 화면에서는 숨기고 그 자리를 게임 액션 바가 쓴다. 알림 탭에는 읽지 않은 개수를 표시한다.

**마이페이지 설계 원칙**

- **아바타 업로드**: 이메일 인증 계정만 가능. 허용 형식(JPEG·PNG·WebP), 파일 크기, **최대 픽셀 수**를 디코딩 전에 검사하고(압축 폭탄 방지), 서버에서 고정 크기로 다시 인코딩하면서 EXIF 등 메타데이터를 제거한다. 원본은 저장하지 않는다. R2에는 매번 새 무작위 키로 저장해 교체·삭제 시 캐시된 예전 이미지가 남지 않게 한다. 신고가 들어오면 ADMIN이 기본 아바타로 되돌릴 수 있다. 게스트는 기본 아바타만 쓴다.
- **공개 프로필**: 기본 공개 항목은 닉네임·아바타·레벨·가입 연도뿐이다. 통계·배지·최근 게임은 본인이 켠 것만 보인다. 이메일, 지갑 내역, 로그인 정보는 어떤 설정으로도 공개되지 않는다. 차단한 상대에게는 카드가 보이지 않는다.
- **닉네임**: 유니코드 정규화(NFKC)와 대소문자 통일을 거친 값에 UNIQUE를 걸어 모양만 다른 중복을 막는다. `관리자`·`운영자`·`BOT`·`JC ROYAL` 등은 예약어로 막아 사칭을 줄인다. 변경 이력은 본인과 관리자만 볼 수 있다. 제재 중에는 변경할 수 없다. 다른 사람이 쓰던 닉네임은 일정 기간 재사용을 막는다.
- **지갑 내역**: 별도 집계 테이블이 아니라 원장(`wallet_transactions`)을 그대로 읽는다. 사용자가 보는 숫자와 원장이 어긋날 수 없게 하기 위함이다. 목록은 커서 기반으로 나눠 읽는다.
- **플레이 요약·출석 달력**: 손실을 있는 그대로 보여 주고 "만회" 같은 표현이나 손실 직후 플레이를 권하는 문구를 쓰지 않는다. 연속 출석이 끊겼다는 독촉 알림을 보내지 않는다. 연속 출석 보상 금액은 `economy_settings`에서 관리하고 원장에 기록한다.
- **보안 센터**: 로그인 이력에는 시각, 기기·브라우저, 대략적인 지역(국가·도시)만 보여 준다. IP 원문은 저장하지 않고 일부를 가린 값만 보관하며 90일 뒤 삭제한다. "새 기기"는 로그인 성공 시 브라우저에 심는 무작위 기기 식별 쿠키가 없는 경우로 정의한다(브라우저 지문 수집은 하지 않는다). 알림 메일에는 시각·대략적 지역과 해당 세션을 바로 끊는 링크를 넣는다.
- **이메일 변경**: 비밀번호 재확인 → 새 이메일 인증 → 변경. 기존 이메일로 알림과 7일간 유효한 되돌리기 링크를 보낸다.
  - 유예 기간 동안 이전 이메일은 **예약 상태**로 두어 다른 계정이 가져갈 수 없게 한다.
  - 진행 중인 변경은 계정당 하나만 허용한다. 유예 기간 중에는 이메일을 다시 바꿀 수 없다.
  - 되돌리기 토큰은 해시로 저장하고 한 번만 쓸 수 있으며 해당 변경 건에 묶인다.
  - 변경할 때와 되돌릴 때 모두 전체 세션과 비밀번호 재설정 토큰을 무효화한다. 되돌린 뒤에는 비밀번호를 새로 정해야 로그인할 수 있다.
- **알림함**: 제재 안내와 보안 알림은 수신 거부할 수 없다. 광고성 알림은 만들지 않는다.
- **설정 미리보기**: 실제 게임과 같은 카드·칩·테이블 컴포넌트를 써서 미리보기와 실제 화면이 달라지지 않게 한다.
- **게스트**: 마이페이지는 홈·기록·설정만 열고, 나머지 탭은 정식 계정 전환 안내를 보여 준다.

**사운드 설계 원칙**

- **소스**: 효과음은 CC0 실녹음 샘플을 골라 편집하고, 음성(포커 행동 음성·딜러 음성)은 AI 음성 합성으로 만든다.
  - AI 음성 도구는 **생성물의 상업적 이용, 편집, 웹 서비스를 통한 공개 전송을 허용하는 약관**인지 확인한 뒤 고른다. 파일을 저장소가 아니라 R2에 두더라도 사용자에게 내보내면 배포이므로, 약관이 허용하지 않는 음성은 어디에도 쓰지 않는다. 공개 저장소에 올릴지는 재배포 허용 여부로 따로 판단한다. 도구명·음성 이름·생성일·약관 링크를 `assets/sounds/LICENSES.md`에 기록한다.
  - 실존 인물의 목소리를 흉내 낸 음성은 쓰지 않는다. 언어당 딜러 음성은 하나로 통일한다.
  - BGM도 라이선스가 명확한 무료 음원만 쓰고 같은 파일에 출처를 기록한다.
- **믹서 구조**: `audio-engine`에 마스터 아래 5개 버스(효과음·음성·음악·주변음·UI)를 둔다. 요구사항 13.6의 전체/효과음/배경음악/음소거 설정은 이 구조의 상위 묶음으로 그대로 제공하고, 세부 믹서는 그 아래 펼쳐 보이게 한다. 설정은 계정(`user_settings`)에 저장한다.
- **프리셋**: 조용히(음성·음악·주변음 끔, 효과음 낮게) / 기본 / 몰입(주변음·스팅어 포함 전체).
- **공간감·야간 모드**는 Web Audio 노드(스테레오 패너, 저역 통과 필터, 마스터 컴프레서)로 구현한다. Howler의 Web Audio 컨텍스트에 연결하되, HTML5 오디오로 폴백된 환경에서는 공간감과 야간 모드를 끄고 기본 재생만 한다. 모노 출력·한쪽 이어폰 사용자를 위해 공간감은 끌 수 있고, 좌우 치우침은 정보가 한쪽에서만 들리지 않을 정도로 제한한다.
- **음성 우선순위**: 음성이 나올 때 음악·주변음을 살짝 낮춘다(더킹). 음성끼리 겹치면 대기열에 넣되 오래된 멘트는 버린다. 터보 모드에서는 음성을 생략한다.
- **정보는 소리로만 전달하지 않는다**: 음성·알림음이 알려 주는 내용은 항상 상태 배너·말풍선·타이머 링으로도 보인다. 음성 자막을 따로 두지 않는 대신 이 원칙으로 음소거 사용자를 보장한다.
- **내 차례 알림**: 백그라운드 탭에서는 브라우저가 재생을 제한할 수 있으므로 탭 제목 깜빡임을 항상 함께 쓴다. 브라우저 알림(Notification)은 사용자가 설정에서 켠 경우에만 요청한다.
- **스팅어**: 서버가 보낸 상태 이벤트에만 반응한다. 결과를 암시하지 않도록 승패가 정해지기 전 구간에만 쓰고, 결과에 따라 다른 스팅어를 미리 틀지 않는다. 야간 모드와 "조용히" 프리셋에서는 끈다.
- **자동재생**: 모든 소리는 사용자 첫 입력 이후에만 시작하고, 탭이 백그라운드로 가면 음악·주변음을 멈춘다(내 차례 알림은 예외).
- **용량**: 효과음은 오디오 스프라이트로 묶어 초기에 받고, BGM·음성 팩은 필요할 때 지연 로딩한다.

### UI/UX 레퍼런스

화면 구성과 조작 흐름은 아래 두 계열을 적극 참고한다. **이 절은 확인되지 않은 가설이다.** 일반적으로 알려진 특징을 정리한 것이며 실제 화면을 다시 확인하지 않았다. 구현 명세로 쓰지 않는다. PHASE 1에서 실제 화면을 캡처해 벤치마크 보드를 만들고(캡처 이미지는 저장소에 올리지 않는다), 화면별 정보 구조·키보드 이동 순서·모바일 분기점·터치 타깃 크기·오류 상태를 수치로 정한 화면 명세를 따로 작성한다. 그 명세가 이 절을 대체한다.

| **Evolution** (라이브 카지노·First Person 시리즈) | 블랙잭, 바카라, 룰렛, 카지노 홀덤, 쓰리카드 포커, 공통 게임 셸, 로비 | 테이블 게임 화면의 정보 배치와 베팅 흐름 |
| **한게임 포커 · 피망 포커** | 포커룸, 포커 로비, 한국어 사용자 경험 전반 | 한국 사용자에게 익숙한 방 목록·베팅 버튼·족보 안내·연출 |

**Evolution 계열에서 가져올 패턴 → 싱글 테이블 게임**

- **화면 구조**: 위쪽에 테이블(딜러 시점), 아래쪽에 베팅 영역과 칩 트레이. 하단 바에 잔액과 총 베팅액을 항상 고정 표시한다. → 공통 게임 셸의 기본 배치로 삼고, "원근 딜러 테이블 뷰"는 First Person 시리즈의 시점을 기준으로 잡는다.
- **라운드 상태 배너**: "베팅하세요 → 베팅 마감 → 결과"를 화면 중앙의 한 줄 배너와 원형 카운트다운으로 보여 준다. → 싱글 게임은 실제 제한 시간이 없으므로 카운트다운 없이 상태 배너만 쓴다. 현재 단계가 항상 한눈에 보여야 한다(요구사항 1.2-1).
- **칩 트레이와 보조 버튼**: 칩 선택 → 영역 탭으로 베팅, 실행취소·2배·재베팅을 칩 트레이 양옆에 배치한다. 선택 불가 영역은 흐리게, 한도 초과는 영역 위에 즉시 표시한다.
- **테이블 한도 표기**: 테이블 이름 옆에 최소–최대 베팅을 항상 표시한다. → 스테이크 등급 테이블에 적용.
- **바카라**: 로드맵(주로·대로·대안로·소로·갑충로)을 화면 하단에 상시 배치하고 Player/Banker/Tie 횟수 요약을 함께 둔다. 로비의 바카라 타일에도 축약 로드맵을 보여 준다.
- **룰렛**: 최근 결과 숫자 띠, 레이스트랙 전환 버튼, 통계 패널(핫/콜드), 당첨 숫자 확대 표시.
- **결과 연출**: 당첨 금액을 화면 중앙에 짧게 띄우고 이긴 베팅 영역만 강조한다. 과한 전체 화면 효과 대신 절제된 조명과 금색 포인트를 쓴다. → "단계별 승리 연출"의 일반 승리 등급 기준.
- **로비**: 카테고리 탭, 테이블 타일(썸네일·한도·즐겨찾기 별), 최근 플레이한 게임 줄.
- **보조 메뉴**: 기록·설정·도움말(규칙·지급표)·사운드를 화면 모서리의 일관된 위치에 둔다.

**한게임 포커 · 피망 포커에서 가져올 패턴 → 포커룸**

- **방 목록 중심 로비**: 블라인드 단계별 채널, 방 번호·방 제목·인원·블라인드·바이인이 한 줄에 보이는 목록, **바로 입장(빠른 시작)** 버튼, 방 만들기, 비밀방 자물쇠 표시.
- **한국식 베팅 버튼**: 베팅 프리셋을 **쿼터 · 하프 · 풀 · 올인**으로 표기하고 각 버튼에 실제 금액을 함께 보여 준다(영어 UI에서는 ¼ Pot · ½ Pot · Pot · All-in). 다이(폴드)·체크·콜 버튼은 크고 고정된 위치에 둔다.
- **족보 안내**: 내 현재 족보를 내 카드 옆에 한글로 상시 표시하고(예: "투 페어 — A, K"), 족보 순위표 패널에서 현재 족보를 강조한다. 쇼다운에서는 승리 족보에 쓰인 카드 5장만 들어 올려 강조한다.
- **금액 표기**: 한국어 UI에서는 큰 칩 수를 만·억 단위로 줄여 표기한다(예: 1억 2,500만). 내부 값은 정수 그대로이며 표기만 바꾼다. 정확한 값은 길게 누르거나 올리면 보인다.
- **좌석 정보**: 아바타, 닉네임, 보유 칩, 레벨 배지, 마지막 행동 말풍선(콜·하프·올인 등), 턴 타이머 링.
- **행동 음성 안내**: 콜·레이즈·올인·다이 같은 행동을 짧은 음성으로 알려 준다. → **신규 추가 기능**으로 채택한다. 한국어/영어 음성 팩, 사운드 설정에서 별도 볼륨·끄기, PHASE 3b.
- **말풍선 채팅·이모티콘**: 채팅을 좌석 위 말풍선으로도 띄우고 정형 이모티콘을 빠르게 보낼 수 있게 한다.
- **큰 족보 연출**: 풀하우스 이상에서 족보 이름을 화면 중앙에 크게 띄운다. → "단계별 승리 연출"의 포커 등급 기준.
- **무료 충전 안내**: 칩이 부족할 때 리필 가능 시각과 남은 횟수를 입장 차단 화면에서 바로 안내한다.

**참고의 한계**

- 구조·흐름·정보 배치를 참고하는 것이며 로고, 캐릭터, 일러스트, 사운드, 고유 명칭, 화면을 그대로 본뜬 디자인은 가져오지 않는다. 색·서체·카드·칩·테이블은 JC ROYAL 디자인 시스템(금색·블랙·펠트 그린)으로 새로 만든다. 제휴나 관련이 있는 것처럼 보이는 표현을 쓰지 않는다.
- 두 계열의 분위기가 다르다. Evolution은 절제된 방송 화면, 국내 포커는 정보량이 많고 연출이 강하다. 충돌할 때는 요구사항 2.3의 방향(고급 호텔 카지노, 과한 네온·점멸 배제)을 우선하고, 국내 포커에서는 **조작 편의와 한국어 표현**을 가져온다.
- 국내 포커 게임의 유료 요소(아이템·유료 충전·등급 상품)는 가져오지 않는다.

### 결정 3.1 — 카드 테이블은 DOM, 릴·휠만 PixiJS

요구사항은 PixiJS를 우선 검토 대상으로 두었지만, 카드·칩·테이블은 DOM + CSS transform + GSAP로 구현한다.

- 카드 게임은 동시에 움직이는 요소가 수십 개 수준이라 GPU 가속 transform으로 충분하다.
- 텍스트 선명도, 반응형 레이아웃, 키보드 조작·스크린리더 접근성을 DOM에서 그대로 얻는다(요구사항 1.2-8).
- 카드·칩을 SVG로 두면 해상도와 무관하게 선명하고 테마(카드 디자인·테이블 테마) 교체가 쉽다.
- 슬롯 릴(고속 스크롤·블러·파티클)과 룰렛 휠(회전·공 궤적)은 캔버스가 유리하므로 PixiJS를 지연 로딩한다. 초기 번들에 포함하지 않는다.

### 결정 3.2 — Tone.js는 도입하지 않는다

합성 사운드가 필요한 구체적 사례가 생기기 전까지 보류한다.

### 사운드 에셋

효과음은 CC0 또는 상업적 이용 가능한 라이선스의 샘플만, 음성은 AI 음성 합성으로 만들며(§2 사운드 설계 원칙) 출처와 라이선스를 `assets/sounds/LICENSES.md`에 기록한다. 동작당 3~5개 변형 샘플을 등록해 무작위 선택 + 미세한 피치·볼륨 변형을 적용한다(연출용 무작위는 `Math.random()` 사용 가능 — 게임 결과와 무관).

## 4. 아키텍처

### 4.1 배포 단위

```text
[브라우저]
   │  HTTPS / WSS (동일 출처)
   ▼
┌─────────────────────────────── Worker: jc-royal-web ───────────────────────────────┐
│  정적 자산(React SPA)   +   Hono API (/api/*)   +   WebSocket 업그레이드 (/ws/*)     │
└───────┬──────────────────────┬───────────────────────────┬──────────────────────────┘
        │                      │                           │
        ▼                      ▼                           ▼
   D1 (원장·계정·기록)   PokerTableDO (테이블당 1개)   GameSessionDO (사용자당 1개)
        ▲                      LobbyDO (룸 목록·접속 수)
        │
┌───────┴──────────── Worker: jc-royal-admin ────────────┐      Worker: jc-royal-jobs
│  관리자 SPA + 관리자 API (별도 호스트, 별도 세션 쿠키)   │      (Cron: 정리·집계·시즌)
└────────────────────────────────────────────────────────┘
```

- **web과 API를 한 Worker·한 출처로 묶는다.** 쿠키가 SameSite=Strict로 동작하고 CORS가 필요 없어 CSRF 방어가 단순해진다. 정적 자산 설정에서 `/api/*`, `/ws/*`는 Worker가 먼저 처리하도록 명시한다.
- **admin은 별도 Worker·별도 호스트.** 쿠키 범위, WebAuthn RP ID, API 라우트가 일반 서비스와 분리된다. 일반 Worker에는 관리자 라우트 자체가 존재하지 않는다.
- **관리자 인증 데이터는 별도 D1(`jc-royal-admin-auth`)에 둔다.** D1 바인딩은 데이터베이스 전체에 대한 접근을 주므로(테이블 단위로 제한하는 방법은 공식 문서에서 찾지 못함 — 미확인), 같은 DB를 쓰면 사용자 Worker 코드도 관리자 자격 증명을 읽을 수 있다. 관리자 계정·역할·WebAuthn 자격 증명·관리자 세션·복구 요청·챌린지는 admin Worker에만 바인딩한 DB에 두고, 서비스 데이터(회원·원장·기록·감사 로그)는 공용 D1을 admin Worker도 바인딩해 사용한다.
- 남는 한계: admin Worker는 서비스 D1 전체를 읽고 쓸 수 있다. 관리자 API 코드의 권한 검증이 유일한 경계이므로, admin Worker의 서비스 DB 접근은 권한 문자열을 확인하는 데이터 접근 계층 하나로만 지나가게 한다.
- Durable Object 클래스는 `workers/`에 두고 web Worker가 바인딩한다.

### 4.2 모노레포 구조

요구사항의 구조를 따르되 Worker 배포 단위에 맞춘다.

```text
jc-royal/
├── apps/
│   ├── web/                 # 사용자 SPA + Hono API Worker
│   └── admin/               # 관리자 SPA + 관리자 API Worker
├── workers/
│   ├── poker-room/          # PokerTableDO, LobbyDO
│   ├── game-session/        # GameSessionDO (싱글 플레이 게임 진행 상태)
│   └── scheduled-jobs/      # Cron Worker
├── packages/
│   ├── shared/              # 타입, Zod 스키마, 상수, 오류 코드
│   ├── database/            # Drizzle 스키마, 마이그레이션, 지갑 원장 함수
│   ├── auth/                # 세션, 비밀번호, WebAuthn, RBAC
│   ├── game-core/           # 카드·덱·RNG·Provably Fair·칩 연산
│   ├── poker-engine/        # NLHE 상태 머신, 핸드 평가, 팟 계산, 봇
│   ├── blackjack-engine/
│   ├── baccarat-engine/
│   ├── roulette-engine/
│   ├── casino-holdem-engine/
│   ├── three-card-poker-engine/
│   ├── slot-engine/
│   ├── audio-engine/        # Howler 래퍼, 사운드 큐, 설정
│   └── ui/                  # 디자인 시스템, 카드·칩·테이블 컴포넌트
├── assets/                  # branding, cards, chips, tables, sounds
├── tests/                   # Playwright E2E
├── docs/
└── .github/workflows/
```

엔진 패키지는 **순수 TypeScript**(DOM·Workers API 비의존)로 작성한다. 난수원은 인자로 주입받아 테스트에서 결정적으로 재현한다.

### 4.3 게임 서버

**싱글 플레이 게임(블랙잭·바카라·룰렛·카지노 홀덤·쓰리카드·슬롯)**

- 요청 흐름: `POST /api/games/:game/...` → 세션·입력 검증 → 사용자별 `GameSessionDO` → 엔진 실행 → D1 정산.
- 사용자당 DO 하나가 요청을 받는다. 다만 DO는 D1 호출처럼 외부 I/O를 기다리는 동안 다른 요청이 끼어들 수 있으므로 "DO라서 자동으로 직렬화된다"고 가정하지 않는다. 라운드마다 `busy` 표시를 DO 저장소에 두고, 처리 중인 라운드에 들어온 두 번째 요청(더블 클릭, 다중 탭)은 기다리게 하거나 거부한다.
- 블랙잭처럼 여러 단계로 진행되는 라운드의 상태(덱, 딜러 히든 카드)는 DO 저장소에만 두고, 클라이언트에는 공개 가능한 정보만 보낸다.
- 라운드 시작 시 적용 중인 `game_rule_versions.id`를 고정한다. 관리자가 규칙을 바꿔도 진행 중인 라운드는 영향받지 않는다.

**DO ↔ D1 정산 프로토콜**

D1 `batch()`는 D1 안에서만, DO 저장소는 그 객체 안에서만 원자적이다. 둘을 묶는 트랜잭션은 없으므로 다음 규칙으로 일관성을 만든다.

- **원본 구분**: 자금의 원본은 D1, 라운드 진행 상태의 원본은 DO.
- **라운드당 금전 상태 행 하나**: D1 `settlement_intents`에 `round_id`(UNIQUE)당 한 행을 두고, 상태 전이는 `UPDATE ... WHERE round_id = ? AND state = ?`(조건부 갱신)로만 한다. 갱신된 행이 0이면 그 전이는 이미 다른 경로가 가져간 것이므로 원장을 쓰지 않는다. 원장 기록과 상태 갱신은 같은 배치다.

  | 현재 상태 | 허용 전이 | 조건 |
  | --- | --- | --- |
  | (없음) | `RESERVED` | 베팅액 차감 성공 |
  | `RESERVED` | `OUTCOME_COMMITTED` | 엔진이 결과를 확정하고 결과 해시를 기록 |
  | `RESERVED` | `REFUNDED` | 결과 확정 전 취소·만료 |
  | `OUTCOME_COMMITTED` | `SETTLED` | 확정된 결과대로 지급 |

  - **결과가 확정된 뒤에는 환불할 수 없다.** `OUTCOME_COMMITTED`에서는 같은 결과로 정산하는 길만 있다. 정산과 환불이 둘 다 성공하는 경로가 없다.
  - `SETTLED`와 `REFUNDED`는 종료 상태다.
  - 조건부 갱신이 0행일 때 같은 배치의 원장 기록까지 막는 구체적인 SQL 형태(예: 원장 INSERT를 상태 조건이 붙은 `INSERT ... SELECT`로 작성)는 PHASE 0에서 실증해 확정한다.
- **멱등 키와 내용 검증**: 원장 행의 키는 `round_id:reserve` / `round_id:settle` / `round_id:refund`. 각 행에 사용자·금액·규칙 버전·결과 해시를 묶은 `payload_hash`를 저장하고, 같은 키로 다른 내용이 들어오면 오류로 처리하고 보안 이벤트를 남긴다.
- **DO 쪽 라운드 상태**: `INIT → RESERVE_PENDING → ACTIVE → SETTLEMENT_PENDING → SETTLED | REFUNDED`. DO는 "다음에 할 D1 작업"을 먼저 저장한 뒤 D1을 호출하고, 끝나면 완료를 표시한다.
  - 차감 실패(잔액 부족) → `INIT`에서 폐기. 카드를 배분하지 않는다.
  - 차감 응답 유실 → `RESERVE_PENDING`에서 재시도. 중복 키로 기존 거래를 확인하고 `ACTIVE`로 진행.
  - `ACTIVE`에서 사용자가 돌아오지 않음 → 게임별 만료 시간 뒤 **정해진 기본 행동**으로 라운드를 끝낸다(예: 블랙잭은 스탠드, 카지노 홀덤·쓰리카드는 폴드, 픽 보너스는 정해진 순서의 첫 상자). 환불이 아니라 규칙상의 기본 행동이며 `GAME_RULES.md`에 명시한다.
  - 지급 응답 유실 → `SETTLEMENT_PENDING`에서 같은 결과로 재시도.
- **Reconciler**(스케줄 Worker): D1에서 오래 머문 `RESERVED`·`OUTCOME_COMMITTED` 행을 찾아 해당 사용자의 `GameSessionDO`를 호출해 이어서 처리하게 한다. Reconciler가 직접 환불하지 않는다 — 환불 여부는 라운드 상태를 아는 DO만 판단한다.
- D1 한도 초과·장애 시 새 라운드 시작을 차단하고 진행 중 라운드는 그 상태로 유지한다.

**포커룸**

- 테이블당 `PokerTableDO` 1개. WebSocket Hibernation으로 유휴 비용을 줄이고, 턴 타이머는 DO Alarm으로 처리한다.
- 테이블 상태는 DO의 SQLite 저장소에 액션마다 기록 → DO가 재시작돼도 복원된다.
- 메시지는 플레이어별로 개별 생성한다. 상대의 홀카드는 쇼다운 공개 조건이 성립한 뒤에만 전송하고, 관전자에게는 홀카드를 보내지 않는다.
- 클라이언트 액션에는 `handId`와 순번(`seq`)을 포함시켜 중복·지연 요청을 거부한다.
- **턴 타이머**: 턴마다 `hand_id`, `turn_seq`, `turn_token`, `deadline`을 DO SQLite에 저장한다. 사용자 액션과 Alarm 모두 "해당 `turn_token`이 아직 대기 중"일 때만 한 번 전이시키므로, 동시에 도착해도 하나만 반영된다. Alarm은 최소 1회 실행(실패 시 재시도)되므로 이미 처리된 토큰이면 아무 것도 하지 않고, 마감 전에 깨어나면 재예약한다. 클라이언트 타이머는 표시용이다. 사용자 액션은 서버가 받은 시각이 `deadline` 이내일 때만 유효하다. Alarm의 자동 재시도는 횟수 제한(외부 검토에서 최대 6회로 확인)이 있으므로, 핸들러는 실패를 잡아 새 Alarm을 직접 다시 예약하고, 스케줄 Worker가 마감이 한참 지난 활성 테이블을 깨우는 감시 작업을 둔다.
- **Hibernation 복원**: 인메모리 상태는 사라지므로 연결별 메타데이터(사용자·좌석·관전 여부)는 WebSocket attachment에, 게임 상태는 SQLite에 둔다.
- 재접속 시 전체 스냅샷을 다시 보낸다. 연결이 끊긴 플레이어는 타임아웃 시 체크 가능하면 체크, 아니면 폴드 처리한다.
- `LobbyDO`가 테이블 목록·빈자리·접속 수를 집계해 로비에 제공한다. 룸 메타데이터의 원본은 D1이다.
- 핸드 종료 시 `poker_hands`·`poker_actions`를 D1에 저장한다(리플레이어의 데이터 소스).

### 4.4 가상 칩 지갑

- 잔액은 **정수**(칩 단위). 부동소수점 연산 금지. 비율 배당은 정수 연산으로 계산하고 규칙을 `GAME_RULES.md`에 명시한다.
  - 바카라 뱅커(0.95:1)는 소액에서 내림으로 이익이 0이 되지 않도록 **뱅커 베팅을 20칩 단위로 제한**한다. 블랙잭 3:2도 같은 이유로 베팅을 2칩 단위로 제한한다. 허용 단위는 UI와 지급표에 표시한다.
- `wallet_transactions`는 추가 전용(append-only) 원장이다. `virtual_wallets.balance`는 원장의 합과 항상 일치해야 한다.
  - 검증은 **증분 방식**: 지갑별 마지막 검증 거래 ID와 누계를 저장해 새 거래만 합산한다. 전체 재합산은 저빈도 분할 작업으로 돌리며, 시작 시점의 마지막 거래 ID를 기준선으로 잡아 그 뒤에 들어온 거래는 다음 회차로 넘긴다(D1 행 읽기 한도 보호). 결과는 관리자 "잔액 검증" 화면의 데이터 소스다.
- **원자성**: 잔액 갱신과 원장 기록을 D1 `batch()` 하나로 실행한다. `virtual_wallets.balance`에 `CHECK (balance BETWEEN 0 AND 9007199254740991)`을 걸어 잔액 부족·JS 안전 정수 초과 시 배치 전체가 실패하게 한다. 테이블은 STRICT로 만든다.
- **멱등성**: 모든 원장 행은 `idempotency_key`(UNIQUE)를 가진다.
  - 배치의 **첫 문장을 원장 INSERT**로 두고 중복을 무시하지 않는다(`INSERT OR IGNORE` 금지). 중복 키 오류가 나면 배치 전체가 롤백되고, 호출자는 기존 거래를 조회해 그 결과를 돌려준다. 이렇게 해야 재시도에서 잔액 UPDATE만 다시 실행되는 일이 없다.
  - 원장 행은 `virtual_wallets.id`를 FK로 참조한다. 잔액 UPDATE가 0행을 바꾸면(없는 지갑) 오류로 처리한다.
- **읽기 일관성**: 정산 직후 잔액 조회는 방금 쓴 값을 읽어야 한다. D1 읽기 복제는 쓰지 않으며, 켜게 되면 Sessions API(bookmark)로 read-your-writes를 보장한다.
- **포커 에스크로**: 착석 시 지갑 → 테이블 에스크로로 이동하고, 테이블 안에서는 DO가 스택을 관리하며, 이석 시 남은 스택을 지갑으로 반환한다. 핸드마다 D1을 쓰지 않는다.
  - D1 `poker_escrows`에 `escrow_id`, `table_id`, 상태 `RESERVED → CLAIMED_BY_TABLE → CASHOUT_PENDING → CLOSED`(또는 `RESERVED → REFUNDED`)를 기록한다. 전이는 조건부 갱신으로만 한다.
  - **착석**: D1에서 차감·`RESERVED` 기록·좌석 lease를 한 배치로 → DO가 `escrow_id`를 **한 번만** 스택으로 수용하고 그 사실을 저장 → D1을 `CLAIMED_BY_TABLE`로.
  - **`RESERVED`에 머문 에스크로를 시간만 보고 환불하지 않는다.** Reconciler는 해당 `table_id`의 DO에 "이 `escrow_id`를 수용했는가"를 물어서, 수용했으면 D1을 `CLAIMED_BY_TABLE`로 맞추고, 수용하지 않았다는 답을 받았을 때만 환불한다. DO는 "수용하지 않음"이라고 답할 때 그 `escrow_id`를 **거부 목록에 저장**해 이후에 늦게 도착한 착석 요청도 받지 않는다. DO에 연락이 닿지 않으면 아무 것도 하지 않고 다음 주기에 다시 묻는다.
  - **이석**: DO가 반환 금액과 멱등 키를 먼저 저장(`CASHOUT_PENDING`)하고 좌석을 잠근 뒤 → D1 반환 → `CLOSED`. 실패하면 같은 키·같은 금액으로 재시도한다.
  - **강제 종료**: 테이블을 먼저 동결(새 액션 거부)하고, 좌석별 `스택 + 진행 중 핸드에 낸 금액`을 합친 **반환 명세를 DO에 한 번에 저장**한 뒤, 명세의 각 줄을 에스크로별 멱등 작업으로 D1에 반영한다. 재시작되면 저장된 명세에서 아직 반영되지 않은 줄만 이어서 처리한다.
- **봇 자금**: 봇도 원장 안에서 움직인다. 시스템 계정 `BOT_TREASURY`에서 사람과 같은 에스크로 절차로 바이인하고 이석 시 반환한다. 봇의 손익은 이 계정에 그대로 남는다.
- **계정 종류와 칩 총량 불변식**
  - 계정 종류: `PLAYER`(사용자 지갑), `HOUSE`(싱글 게임의 상대), `BOT_TREASURY`(봇 자금). `balance >= 0` 제약은 `PLAYER`에만 건다. `HOUSE`와 `BOT_TREASURY`는 음수가 될 수 있다(하우스가 "파산"해 당첨금을 못 주는 상황을 만들지 않기 위함).
  - **발행은 지갑이 아니라 카운터다.** `issued_supply`는 지금까지 만들어진 칩의 총량이고, 보너스·리필·가입 보상·관리자 조정(증액)만 이 값을 늘리며 관리자 조정(감액)·탈퇴 계정 소각만 줄인다. 발행·소각은 대상 계정 잔액과 `issued_supply`를 같은 배치에서 함께 바꾼다.
  - 그 밖의 모든 거래(베팅, 지급, 바이인, 반환)는 **복식 기록**이다. 하나의 `transaction_id` 아래 여러 줄이 있고 줄의 합은 0이다.
  - 불변식: `PLAYER 합 + HOUSE + BOT_TREASURY + 닫히지 않은 에스크로 합 = issued_supply`. 스케줄 작업이 검증하고 어긋나면 보안 이벤트를 남긴다.
  - 검증 기준 시점: 테이블 안에서 스택이 오가도 그 테이블의 에스크로 합은 변하지 않는다(테이블 안의 이동은 에스크로끼리의 이동). 따라서 D1에 기록된 에스크로 금액만으로 검증할 수 있다. 이석 시 반환 금액과 원래 에스크로 금액의 차이는 같은 테이블의 다른 좌석과 합쳐 0이어야 하며, 테이블이 닫힐 때 테이블 단위로 이를 검증한다.
- 관리자 수동 조정은 사유 필수, 권한 검증, 감사 로그, 멱등 키를 요구한다.

### 4.5 공정성·난수

- 게임 결과용 난수는 `crypto.getRandomValues()`만 사용한다. `Math.random()`은 엔진 패키지에서 lint 규칙으로 금지한다.
- 범위 난수는 거절 샘플링으로 모듈로 편향을 제거하고, 셔플은 Fisher–Yates를 쓴다.
- **Provably Fair**: 라운드 시작 전에 CSPRNG로 서버 시드를 만들고 SHA-256 해시를 먼저 공개한다. 결과는 `HMAC-SHA256(서버 시드, 클라이언트 시드 : nonce)` 스트림에서 결정적으로 유도한다. 라운드 종료 후 서버 시드를 공개하면 사용자가 검증 페이지(또는 공개된 알고리즘)로 결과를 재계산할 수 있다.
  - **커밋 순서**: 서버 시드 해시 공개가 항상 사용자 기여값보다 먼저다. 서버가 사용자 시드를 본 뒤 유리한 서버 시드를 고르는 것(그라인딩)을 막기 위함이다. 싱글 게임은 다음 라운드용 해시를 미리 공개하고, 클라이언트 시드는 그 뒤에 사용자가 바꿀 수 있다.
  - **커밋 대상은 시드만이 아니다.** 서버가 나중에 고를 수 있는 값이 하나라도 남으면 그 값을 바꿔 가며 유리한 결과를 찾을 수 있다. 그래서 커밋은 `서버 시드 + round_id(또는 table_id·hand_id) + 순번(nonce) + 게임·규칙 버전 + 알고리즘 버전`을 정해진 형식으로 이어 붙인 값의 해시로 하고, 베팅과 클라이언트 시드를 받기 **전에** 사용자에게 내려보낸다. nonce는 사용자(포커는 테이블)별로 1씩 증가하는 값이며 건너뛸 수 없다.
  - **커밋 로그**: 모든 커밋은 D1의 추가 전용 `fairness_commits`에 사용자(테이블)별 연속 순번과 함께 기록된다. 순번에 빈 곳이 있으면 누락된 커밋이 있다는 뜻이므로 사용자가 검증 페이지에서 자기 순번이 이어지는지 확인할 수 있다. 클라이언트는 받은 커밋을 로컬에도 보관해 서버 기록과 대조할 수 있다.
  - **포커**: 핸드 N이 끝나기 전에 핸드 N+1의 서버 시드 해시를 공개한다. 핸드 N+1 시작 시 착석한 사람 플레이어의 클라이언트 시드를 좌석 번호순으로 결합하고 `table_id`, `hand_id`, 규칙 버전, 알고리즘 버전을 함께 넣어 덱을 유도한다. 시드를 내지 않은 플레이어는 정해진 기본값을 쓴다. 봇은 시드에 기여하지 않는다.
  - **취소된 커밋도 공개**: 커밋 후 시작하지 못했거나 중단된 라운드·핸드는 정해진 사유 코드와 함께 즉시 시드를 공개하고, 순번을 그대로 소비한다(같은 순번으로 다시 커밋할 수 없다). 불리한 덱만 골라 버리는 것을 순번의 연속성으로 드러나게 하기 위함이다.
  - **포커 핸드 기록 실패**: 핸드 종료 후 시드 공개와 핸드 기록을 D1에 쓰지 못하면, 테이블 DO는 그 기록을 보류함(outbox)에 두고 다시 시도하며, 쓰기가 끝날 때까지 다음 핸드를 시작하지 않는다.
  - **검증 데이터**: 알고리즘 버전, 전체 시드, 전체 액션, Run It Twice 합의 여부와 보드 소비 순서를 포함한다.
  - **시드 보관**: 공개 전 서버 시드는 해당 DO 저장소에만 둔다. D1 `fairness_seeds`에는 처음에 커밋 해시와 알고리즘 버전만 쓰고, 종료 후 공개 시드를 채운다. 로그·CSV·오류 추적에 시드를 남기지 않는다.
  - 시드가 공개되기 전에는 관리자 화면을 포함한 어떤 애플리케이션 경로로도 시드·미공개 카드를 조회할 수 없게 한다.
  - **한계**: 이 방식은 "커밋한 덱대로 진행했다"는 것을 증명한다. Cloudflare 계정으로 런타임 코드를 바꿀 수 있는 인프라 운영자까지 암호학적으로 배제하지는 못하며, "관리자에게 비노출"은 애플리케이션 관리자 기준이다. 이 범위를 검증 페이지에 명시한다.

## 6. 인증·보안

### 일반 사용자

- 이메일 + 비밀번호, 선택적 패스키(WebAuthn). 이메일 인증, 비밀번호 재설정, 탈퇴, 세션 목록·개별 종료.
- 세션: 무작위 불투명 토큰을 `__Host-` 접두사의 `Secure; HttpOnly; SameSite=Lax; Path=/` 쿠키로 전달하고 DB에는 해시만 저장한다. 절대 만료 + 비활성 만료.
- 비밀번호 해시 알고리즘은 **PHASE 0에서 실측해 확정**한다. 후보는 `node:crypto` scrypt, Argon2id WASM, WebCrypto PBKDF2. 실제 배포된 Worker에서 가입·로그인·동시 로그인을 측정하고, 안전한 파라미터가 무료 플랜의 요청당 CPU 한도를 넘으면 유료 플랜을 전제로 확정한다. **CPU 한도에 맞춰 해시 강도를 낮추지 않는다.**
- CSRF: 동일 출처 + SameSite 쿠키 + 상태 변경 요청의 Origin 검사. XSS: React 기본 이스케이프 + CSP. SQL Injection: Drizzle 파라미터 바인딩만 사용.
- Rate Limiting: 로그인·가입·게스트 생성·채팅·베팅 엔드포인트.
- WebSocket: 업그레이드 요청에서 세션 쿠키와 Origin을 검증한 뒤 DO로 전달한다.

### 역할과 관리자 계정

역할은 세 가지다: 게임 서비스의 `USER`, 관리자 사이트의 `ADMIN`과 `SUPER_ADMIN`. 원 요구사항의 `MODERATOR`는 두지 않고 그 업무(신고 처리·제재)는 `ADMIN`이 맡는다(원문과 다른 점).

**관리자 계정은 게임 계정과 별개다.** 회원에게 관리자 권한을 부여하는 기능은 없다. 관리자는 관리자 사이트 전용 계정이며 별도 D1(`jc-royal-admin-auth`)에만 존재한다.

- 이유: 게임 계정의 비밀번호·세션이 탈취돼도 관리자 권한과 무관해지고, 운영 화면을 보는 사람이 같은 계정으로 게임에 참여하는 이해충돌을 구조적으로 막는다.
- 역할은 관리자 계정의 컬럼 하나로 두고 `roles`·`permissions` 테이블은 만들지 않는다(§5).
- 관리자가 게임을 하려면 일반 회원 계정을 따로 쓴다. 관리자 계정에 본인의 게임 계정을 등록하게 하고, 등록된 계정은 리더보드 집계에서 제외한다.

| | `SUPER_ADMIN` | `ADMIN` |
| --- | --- | --- |
| 인원 | **1명(소유자)으로 고정** | 여러 명 |
| 생성 | 배포 후 일회성 부트스트랩으로 한 번 | `SUPER_ADMIN`이 초대 |
| 로그인 | 비밀번호 + FIDO2 보안 키(필수, 허용 목록에 있는 USB 키 모델만) | 비밀번호 |
| 접속 환경 | 어디서나, 단 보안 키가 있어야 함 | 어디서나, 별도 장치 없이 |
| 권한 | 전체 | 일상 운영 한정(아래 표) |

- **보안 키는 `SUPER_ADMIN`만 가진다.** `SUPER_ADMIN`을 추가로 만드는 기능은 없고, 이 계정은 삭제하거나 `ADMIN`으로 내릴 수 없다. MAIN·BACKUP 키는 모두 소유자의 것이다.
- **`ADMIN`의 2단계 인증(인증 앱 OTP)은 보류한다**(2026-10-13 결정). 당장은 비밀번호만으로 로그인한다. 비밀번호 하나가 유출되면 `ADMIN` 권한 전체가 넘어가므로, `ADMIN`이 단독으로 할 수 있는 일을 되돌릴 수 있는 범위로 묶고(아래 권한표) 다음 보완책을 둔다. OTP는 계정 구조를 바꾸지 않고 나중에 추가할 수 있다.
- 보완책: 제재·세션 종료·공지 변경에 시간당 횟수 상한(초과 시 계정 잠금과 SUPER_ADMIN 알림), 시스템 로그·오류 로그에서 비밀값과 개인정보 필터링, 긴 비밀번호 강제와 유출 비밀번호 목록 대조, Turnstile, 로그인 실패 횟수 제한과 잠금, 짧은 세션 만료, 새 기기 로그인 시 `SUPER_ADMIN`에게 알림 메일, `SUPER_ADMIN`이 `ADMIN`별 로그인 이력을 조회하고 세션을 강제 종료할 수 있음.

**`ADMIN` 추가 절차**

1. `SUPER_ADMIN`이 보안 키 재인증 후 초대를 발급한다(일회용, 짧은 만료).
2. 초대받은 사람이 링크에서 관리자 아이디·비밀번호를 정하면 계정이 활성화된다.
3. 초대 발급·수락·만료는 모두 감사 로그에 남고 `SUPER_ADMIN`에게 알림 메일이 간다.

`ADMIN`을 비활성화하거나 삭제하면 그 세션을 즉시 무효화한다. `ADMIN`은 다른 관리자 계정을 만들거나 바꿀 수 없다.

- **요청 → 승인 → 실행**: "요청" 항목은 `ADMIN`이 사유와 함께 `approval_requests`에 올리고, `SUPER_ADMIN`이 보안 키 재인증으로 승인해야 실행된다.
  - 상태: `PENDING → APPROVED → EXECUTING → EXECUTED | FAILED`, 그리고 `PENDING → REJECTED | EXPIRED | CANCELLED`. 전이는 조건부 갱신으로만 한다.
  - 요청 내용(대상·금액·사유)의 해시를 저장하고, 승인은 그 해시에 대해 이루어진다. 승인 뒤에는 내용을 바꿀 수 없다.
  - **승인과 실행은 별개다.** 칩 조정처럼 공용 D1 안에서 끝나는 작업은 승인과 실행을 한 배치로 처리한다. 테이블 강제 종료처럼 DO를 호출해야 하는 작업은 `EXECUTING`으로 바꾼 뒤 요청 ID를 멱등 키로 DO를 호출하고, 결과에 따라 `EXECUTED`나 `FAILED`로 닫는다. 응답이 유실되면 같은 키로 다시 호출한다.
  - 대기 중 요청은 정해진 시간이 지나면 `EXPIRED`가 된다.
- `SUPER_ADMIN`이 직접 하는 민감 작업(칩 조정, 규칙·경제 설정, 관리자 관리, 키 관리)은 매번 보안 키 재인증을 요구한다. `SUPER_ADMIN`이 1명이므로 `SUPER_ADMIN`끼리의 상호 승인은 두지 않는다.
- 어떤 역할도 진행 중인 게임의 비공개 카드·미공개 시드를 볼 수 없고, 특정 플레이어의 결과를 바꾸는 기능은 없다.

### 최고관리자 — FIDO2 보안 키

- 로그인: 비밀번호 검증 → WebAuthn 챌린지 → 보안 키 서명 검증 → 역할 확인 → 관리자 세션 발급. **비밀번호만으로 통과하는 경로는 없다.**
- 등록 옵션: `authenticatorAttachment: "cross-platform"`, `userVerification: "required"`. 서버에는 공개키·Credential ID·서명 카운터·관리용 이름·등록일·마지막 사용일·활성 여부만 저장한다.
- **USB 키만 받도록 강제**: `cross-platform` 옵션만으로는 휴대폰을 이용한 하이브리드 인증도 통과할 수 있다. 등록 때 attestation을 받아 **AAGUID(키 모델 식별자) 허용 목록**에 있는 모델만 받는다. 허용 목록에는 소유자가 실제로 쓰는 키 모델만 넣는다. 보유한 키가 attestation을 제공하는지는 PHASE 0에서 확인하고, 제공하지 않는 모델이면 이 강제를 적용할 수 없으므로 그때 다시 정한다.
- 키 여러 개 등록(MAIN / BACKUP), 분실 키 비활성화 → 기존 세션 전부 무효화 → 인증 이력 확인 → 새 키 등록. MAIN과 BACKUP은 서로 다른 장소에 보관한다.
- 모든 키 분실 시: 웹 UI가 아닌 **Wrangler CLI 기반 오프라인 복구 절차**(Cloudflare 계정 권한 필요)로 일회용 등록 토큰을 발급하고, `recovery_requests`와 감사 로그에 기록한다. 절차는 `docs/SECURITY.md`에 문서화한다.
  - 복구 토큰은 **세션을 발급하지 않는다.** 짧은 만료의 단일 요청으로 "기존 비밀번호 검증 + 새 보안 키 등록"만 허용하고, 로그인은 그 뒤 정상 절차(비밀번호 + 새 키)로 한다.
  - 복구가 실행되면 기존 키 전부 폐기, 기존 세션 전부 무효화, 알림 메일 발송.
  - 남는 위험: Cloudflare 계정 자체가 탈취되면 이 절차로 새 키를 등록할 수 있다. Cloudflare 계정에도 하드웨어 키 2단계 인증을 걸고 CI 토큰 권한을 배포용으로 최소화한다.
- **복구 경우의 수**

  | 상황 | 복구 방법 |
  | --- | --- |
  | 키 하나 분실 | 남은 키로 로그인 → 분실 키 폐기 → 새 키 등록 |
  | 비밀번호만 분실 | CLI 복구 절차로 비밀번호 재설정 토큰 발급 → 보안 키 인증과 함께 새 비밀번호 설정 |
  | 키 전부 분실 | CLI 복구 절차(위) |
  | 비밀번호와 키 전부 분실 | CLI 복구 절차로 계정 인증 수단 전체 재설정. Cloudflare 계정 접근이 유일한 근거가 된다 |
  | Cloudflare 계정 접근 불가 | 이 서비스 안에서는 복구할 수 없다. Cloudflare 계정 복구 절차에 의존한다 |

  SUPER_ADMIN이 1명이므로 소유자가 자리를 비우면 승인 대기 요청은 처리되지 않는다. 승인 요청에는 만료 시간을 두고, 급한 대응(회원 세션 종료, 30일 이하 정지)은 ADMIN이 단독으로 할 수 있게 해 둔 범위로 버틴다.
- **세션 쿠키**: `__Host-` 접두사, `Secure; HttpOnly; SameSite=Strict; Path=/`, Domain 속성 없음. RP ID는 관리자 호스트(예: `admin.example.com`)로 고정하고 origin은 정확히 일치하는지 검증한다.
- **챌린지**: CSPRNG로 생성하고 계정·용도(로그인/등록/재인증)에 묶어 저장하며, 짧은 만료 후 한 번 쓰면 삭제한다.
- 중요 작업(관리자 계정 관리, 잔액 조정, 요청 승인, 키 관리)은 보안 키 재인증을 요구한다. 인증 실패 횟수 제한, 키 등록·삭제 알림 메일.
- **RP ID 주의**: WebAuthn 자격 증명은 도메인에 묶인다. `*.workers.dev`에서 등록한 키는 커스텀 도메인으로 옮기면 쓸 수 없으므로, 관리자 도메인을 정한 뒤 운영용 키를 등록한다.
- 최초 SUPER_ADMIN 계정(관리자 전용 계정) 생성은 배포 후 일회성 부트스트랩 토큰(Cloudflare Secret)으로만 가능하다. "관리자 자격 증명이 0개"라는 조건 검사와 토큰 소비를 한 배치로 처리하고, 한 번 성공하면 이 경로는 영구히 닫힌다.

### 비밀 관리

세션 서명키, Turnstile·Resend 키, 부트스트랩 토큰은 Cloudflare Secrets, CI 자격 증명은 GitHub Secrets. 로컬은 `.dev.vars`(gitignore). 저장소에는 `.dev.vars.example`만 둔다.

### 직전 실행 단계 (마스터 프롬프트 §28)

0. **STEP 0 — 배포 준비**: `wrangler login`, Cloudflare 요금제 확인, 검증용 Worker·D1 생성, CI용 API 토큰 발급, 관리자 도메인(또는 임시 도메인) 결정. PHASE 0은 실제 Worker가 있어야 하므로 이 단계가 먼저다.
1. **STEP 1 — 아키텍처 확정**: `검증 필요`·`미확인` 항목을 공식 문서로 확인하고 PHASE 0 플랫폼 검증을 실제 Worker에서 실행한 뒤, 그 결과로 `ARCHITECTURE.md`, `DATABASE.md`, `SECURITY.md` 초안 작성.
2. **STEP 2 — 실행 가능한 프로젝트**: 모노레포 초기화, 공통 설정, 개발 서버, 기본 테스트, Wrangler 설정, CI.
3. **STEP 3 — 디자인 시스템·로비**: 브랜드 적용, 레이아웃, 네비게이션, 게임 카드, 반응형.

## 8. 테스트·CI/CD

- **엔진 단위 테스트(Vitest)**: 핸드 랭킹·키커·동점, 사이드 팟·스플릿 팟(홀수 칩 분배 포함), 최소 레이즈·불완전 올인 레이즈, 블라인드·헤즈업 버튼 규칙, 블랙잭 에이스·스플릿, 바카라 서드 카드 전 경우, 룰렛 전 베팅 지급률, 쓰리카드 랭킹(스트레이트 > 플러시)·딜러 자격, 슬롯 페이라인·RTP, 중복 정산 방지.
- **통합 테스트(`vitest-pool-workers`)**: DO 동시 접속, 중복 액션, 재접속, 타임아웃, 상태 복구, 지갑 원자성·멱등성.
  - 지갑: 배치 실패, 응답 유실 후 재시도, 동시 차감, 없는 지갑, 정수 상한 근처.
  - 정산: 라운드 상태 머신의 각 단계 사이에서 중단시킨 뒤 Reconciler가 정산 또는 환불로 수렴하는지.
  - 포커: 에스크로 각 전이 사이 중단, 마감 시각에 액션과 Alarm 동시 도착, Alarm 재실행, 강제 종료 중 부분 실패, 칩 총량 불변식.
  - 봇: 상대 홀카드를 바꿔도 공개 정보가 같으면 행동이 같은지.
- **인증 테스트**: 세션 만료, 역할 검증, 권한 상승 시도, WebAuthn 등록·인증·폐기·복구, 역할별 권한표 전 항목(허용·거부), 초대 만료·재사용, ADMIN 로그인 실패 잠금, SUPER_ADMIN 추가 생성·삭제·강등 불가, ADMIN의 승인 없는 요청 항목 실행 거부, 게임 계정 세션으로 관리자 API 접근 거부.
- **E2E(Playwright)**: 사용자 시나리오 8단계, 관리자 시나리오 6단계. WebAuthn은 Chromium CDP 가상 인증 장치를 사용한다.
- **브랜치**: `main`(운영) / `develop`(통합) / `feature/*`.
- **GitHub Actions**: PR → install · lint · typecheck · unit test · build. `develop` → Preview 배포. `main` → D1 마이그레이션 후 Production 배포.
- **환경**: Local(Miniflare) / Preview / Production. D1 데이터베이스와 Secrets를 환경별로 분리한다.

## 10. 검토 이력

### 2026-10-13 — Codex 외부 검토 (v0.2 대상)

치명 6건, 중요 10건, 경미 3건의 지적을 받아 v0.3에 반영했다. Cloudflare 한도·동작에 관한 근거 일부는 검토 측이 공식 문서로 확인했고, 보안·공정성 지적은 대부분 추론이다. 이 저장소에서 직접 실측한 것은 아직 없다(PHASE 0 대상).

**픽 보너스를 유지하는 이유**: "결과는 서버 결정" 원칙은 클라이언트가 결과를 계산하거나 조작할 수 없어야 한다는 뜻이다. 픽 보너스에서 사용자의 선택은 블랙잭의 힛/스탠드와 같은 게임 입력이고, 서버가 미리 커밋한 배치에 그 입력을 적용해 지급액을 정하는 것은 서버다. 선택과 무관하게 금액이 정해진 연출용 선택은 사용자를 속이는 구조라 채택하지 않는다.
