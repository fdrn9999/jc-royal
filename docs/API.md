# REST API 명세

공통 사항:

- **경로와 형식**: 모든 경로는 `/api` 아래에 있고, 요청·응답은 JSON입니다.
- **오류 응답**: `{ "error": { "code", "message", "details?" } }` 형식입니다.
- **인증**: 사용자 사이트는 `jc_sid` 쿠키, 관리자 콘솔은 `jc_asid` 쿠키를 씁니다. 둘 다 HttpOnly입니다.
- **CSRF 방어**: 상태를 바꾸는 요청은 허용된 `Origin`과 `Content-Type: application/json`이 있어야 합니다.
- **입력 검증**: zod 스키마는 `packages/types/src/api.ts`와 `community.ts`에 있습니다.
- **운영진 표시 `role`**: 다른 회원에게 보이는 회원 정보(친구·친구 요청·차단 목록, 1:1 대화 상대, 게시판 글·댓글 작성자, 로비의 방장 `host`, 핸드 기록·리뷰의 `players[]`)에는 서버가 `users.role`에서 읽은 `role`이 관리자에게만 붙습니다: `'super_admin'` 또는 `'admin'`. 일반 회원은 필드 자체가 없습니다. 요청 본문의 `role`은 어디서도 읽지 않습니다. 역할이 바뀌면 다음 응답부터 바뀐 값이 나가고, 핸드 기록도 기록 당시가 아니라 지금 역할을 보여 줍니다.
- **VIP 표시 `vip`**: 같은 회원 정보(친구·친구 요청·차단 목록, 1:1 대화 상대, 게시판 글·댓글·답글 작성자, 로비의 방장 `host`, 토너먼트 참가자 `entries[]`와 우승자 `winnerVip`, 테이블 좌석과 채팅 줄, 내 정보 `/api/auth/me`)에는 VIP 회원에게만 이름 색 `vip`(`'gold'`·`'rose'`·`'sapphire'`·`'amethyst'`·`'emerald'`·`'cyan'`)이 붙습니다. 관리자·최고관리자·테이블 봇에는 붙지 않고, 정지된 회원은 정지가 풀릴 때까지 빠집니다(`packages/types/src/vip.ts` `shownVip`). 이름과 같은 쿼리(JOIN)에서 읽으므로 목록 길이만큼 쿼리가 늘지 않습니다. 요청 본문·좌석·채팅의 `vip`는 어디서도 읽지 않습니다. VIP는 표시일 뿐 권한·칩·게임 규칙·좌석·토너먼트 어디에도 쓰이지 않습니다. 바뀌면 다음 응답부터 바뀐 값이 나가고(로그인한 모든 기기가 다음 요청에서 받음), 앉아 있는 테이블은 바로 다시 그립니다(관리자 `PATCH /users/:id/vip`). 핸드 기록·리플레이는 바꾸지 않습니다.

## 인증 `/api/auth`

| 메서드 | 경로 | 설명 |
|---|---|---|
| GET | `/signup-options` | `{emailVerification, privacyNoticeVersion}` — 가입 화면이 이메일 인증 단계를 보일지 결정 |
| POST | `/email-verification/request` | `{email,locale?}` → `{ok, expiresInMinutes:10, resendAfterSeconds:60}`. 6자리 인증번호 메일(요청 `locale`, 기본 ko). 409 `email_taken`, 429 `resend_too_soon`(`details.retryAfterSeconds`, `details.codeExpiresInSeconds`: 방금 보낸 인증번호가 아직 쓸 수 있으면 남은 초, 아니면 0 — 인앱 브라우저가 페이지를 다시 읽어 입력 단계를 잃었을 때 새 메일 없이 그 번호를 입력하게 한다)·IP당 20회/시간·이메일당 5회/시간, 502 `mail_failed`, 400 `verification_off`. 개발 환경에서만 `devCode` 반환 |
| POST | `/email-verification/confirm` | `{email,code}` → `{verificationToken, expiresInMinutes:30}`. 400 `invalid_code`(`details.attemptsLeft`), `too_many_attempts`(5회 오입력 시 새 인증번호 필요), `code_expired` |
| POST | `/register` | `{email,password,nickname,birthDate(YYYY-MM-DD),locale?,agreements:{age14:true,privacy:true},emailVerificationToken?,referralCode?,pushConsent?:{service,night}}` → 201 MeDto + 세션. 비밀번호는 8자 이상 + 영문(대·소문자 무관)·숫자·특수문자. 만 14세 미만 400 `underage`. 이메일 인증이 켜져 있으면 해당 이메일의 유효한 `verificationToken` 필수(없거나 다르면 400 `email_not_verified`, 1회용). 생년월일·인증 시각·동의 버전/시각 저장, 가입 칩 지급(원장), 계정 언어로 환영 쪽지. 409 `email_taken`/`nickname_taken`. `referralCode`(40자까지, 공백·대소문자 무시)가 활동 중인 회원의 코드가 아니면 아무것도 쓰지 않고 400 `referral_invalid`. 맞으면 가입 칩 뒤에 추천을 그때 정책으로 기록하고 지금 줄 수 있으면 지급한다(아래 추천인 보상). 추천 기록·지급이 실패해도 가입은 성공한다 |
| GET | `/referral/:code` | 가입 화면의 추천 코드 확인 → `{valid, inviter(닉네임)\|null, reward{amount, minHands, paused}\|null}`. `reward`는 추천 보상이 꺼져 있으면 null(코드는 그래도 받는다). IP당 60초에 30회(429) |
| POST | `/login` | `{email,password,remember?}` → MeDto + 세션. `remember:true`(자동 로그인)면 30일 쿠키와 30일 슬라이딩 만료, 기본값 `false`면 브라우저 세션 쿠키와 1일 슬라이딩 만료. 401 `invalid_credentials`, 403 `suspended`, 429 |
| POST | `/logout` | 세션 폐기 |
| GET | `/me` | 현재 사용자(MeDto). 세션 만료를 연장하고 쿠키를 다시 발급 |
| PATCH | `/me` | `{nickname?, avatarUrl?(https), locale?}` |
| GET | `/nickname-available?nickname=` | `{available}` |
| POST | `/me/password` | `{currentPassword,newPassword}`(가입과 같은 비밀번호 규칙) → 다른 기기 세션 폐기 |
| GET | `/me/sessions` · DELETE `/me/sessions/:id` | 로그인 세션 목록과 폐기 |
| POST | `/me/delete` | `{password}` → 탈퇴(착석 중이면 409 `seated`). 계정 정보 비식별화, 세션·친구·차단·1:1 메시지(양쪽)·쪽지·아카데미 진도·재설정 링크·활동한 날 기록·추천 코드·핸드 노트·계정 설정 삭제. 원장·핸드·게시글·신고는 회원 ID로 남는다(`docs/PRIVACY_OPERATIONS.md` 3절) |
| POST | `/password-reset/request` | `{email}` → 항상 200(IP당 5회, 이메일당 3회/시간 초과 시 429). 메일 설정 시 재설정 메일 발송. 개발 환경에서만 `devToken` 반환 |
| POST | `/password-reset/confirm` | `{token,newPassword}`(가입과 같은 비밀번호 규칙) → 1회용. 모든 세션 폐기 |

이메일 인증은 `MAIL_FROM`, `RESEND_API_KEY`, `APP_ORIGIN`이 모두 설정되면 켜집니다(운영 발신 주소 `JC ROYAL <noreply@jc-royal.site>`, 메일 속 링크는 https://jc-royal.site). 운영에서 메일이 꺼져 있으면 인증 단계 없이 가입되고 `emailVerifiedAt`은 비어 있습니다. 개발·테스트 환경에서는 항상 켜져 있고 인증번호는 `devCode`로 돌려줍니다.

## 내 정보 `/api/me`

| 메서드 | 경로 | 설명 |
|---|---|---|
| GET | `/ledger?limit&before` | 칩 변동 내역 |
| GET | `/stats` | 본인 것만. 카드를 받은 핸드만 세고 관전은 빠진다. 플레이 핸드, 승리 핸드(`pot_won > 0`: 팟 일부라도 획득, 스플릿 포함, 콜 안 된 베팅만 돌려받은 핸드 제외)와 승률, 총 획득(`pot_won` 합), 순손익, 참여한 최대·평균 팟(`largestPot`, `avgPot`: 내 칩이 들어간 핸드에서 실제로 다툰 팟, 콜 안 된 베팅 반환분 제외), 한 핸드 최대 순이익(`biggestWin`), 최고 핸드, `vpip`·`pfr`(분모: 행동 기록을 읽은 핸드), `raiseShare`(PFR ÷ VPIP 핸드), `wtsd`(쇼다운 ÷ 플랍을 본 핸드), `wsd`(팟 획득 ÷ 쇼다운), `positions`(EP·MP·CO·BTN·SB·BB 순서, 핸드·VPIP·PFR·손익). 비율은 `{ n, of }`이며 `of = 0`이면 화면에 —. 계산 정의는 `packages/db/src/handStats.ts` |

| GET | `/posts` · `/comments` | 내가 쓴 글과 댓글 |
| GET | `/refill` | 무료 칩 보충 상태 → `{policy{version, enabled, paused, below, amount, cooldownMs}\|null, wallet, tables\|null, eligible, reason, hold, nextAt, last{at, amount}\|null, received, now}`. `reason`은 받을 수 없는 이유(`off`·`paused`·`suspended`·`cooldown`·`above`·`held`), `hold`는 보류 이유(`busy` 칩이 오가는 중, `unreachable` 테이블이 답하지 않음, `mismatch` D1과 룸의 좌석이 다름). `tables`는 앉은 테이블의 스택 합(물어보지 않았으면 null). 시각은 서버 ms. 이 조회는 테이블마다 한 번만 묻는다 |
| POST | `/refill` | 보충 받기 → `{amount, balance, nextAt, duplicate, status}`. 조건은 서버가 다시 확인하고, 같은 회원의 동시 요청·재시도는 원장 멱등 키 `refill:<회원>:<n번째>`로 한 건만 지급(`duplicate: true`는 이미 받은 그 건). 받을 수 없으면 409 `refill_refused`, 확인 사이에 잔액·좌석·정책이 바뀌면 409 `refill_changed`(둘 다 `error.details.status`에 위 상태). 두 테이블 이상에 앉은 회원이 지급될 조건이면 모든 테이블에 한 번 더 묻고, 두 번 모두 같은 세션·스택·마지막 정산 핸드(`settled`)를 답한 경우에만 그 합으로 판정한다. 그 사이 어느 테이블에서든 핸드가 정산됐거나 칩이 움직였으면 `held`(`busy`)로 보류한다. 첫 회 답은 테이블마다 다른 순간이라, 한 테이블은 정산 전·다른 테이블은 정산 뒤를 더해 회원이 가진 적 없는 합계로 지급하는 것을 막는다. 회원당 60초에 10회(429) |
| GET | `/referral` | 내 추천 → `{code, link, policy{version, enabled, paused, referrerAmount, inviteeAmount, dailyCap, totalCap, minHands}\|null, counts{invited, paid, pending, unpaid}, earned, waiting, invitedBy\|null, recent[≤20], paidNow, now}`. 코드는 처음 열 때 만들고(`JC` + 5자, 0·O·1·I 없음) `link`는 `<사이트>/register?ref=<코드>`. `invitedBy`·`recent[]`는 한쪽 보상 `{status, side, amount, paidAt, failure, handsLeft, createdAt, nickname}`(`handsLeft`는 가입자 본인에게만, 추천인 목록에서는 null). 열 때 내가 관련된 지급 대기 추천을 10건까지 정산하고, 이번 요청이 지갑에 넣은 칩을 `paidNow`로 알린다. 회원당 60초에 30회(429) |
| GET | `/settings?for&fails` | 계정 설정 → `{epoch, rev, prefs, fav[], updatedAt}`(`prefs`는 계정에 값이 있는 설정만, 나머지는 기본값을 보임, 저장한 적 없으면 `rev` 0). `for`는 기기가 기대하는 회원 ID(다르면 409 `settings_account`), `fails`는 그 기기에서 실패한 시도 수(20까지 운영 통계에 더함). 마지막 동기화 시각은 10분에 한 번만 쓴다 |

| POST | `/web-error` | 회원 화면이 겪은 오류(스크립트 오류, 처리되지 않은 프로미스, 화면 일부·페이지를 불러오지 못함)를 센다. 본문 `{}`: 메시지·페이지·스택은 받지도 저장하지도 않는다 → 204. 운영 지표 `web_error` +1(관리자 대시보드 "화면 오류"). 회원당 1시간에 10회(429). 화면은 페이지당 최대 3번, 30초에 한 번까지만 보낸다(`apps/web/src/lib/webErrors.ts`). 로그인하지 않은 방문자는 401이라 세지 않는다 |
| PUT | `/hands/:id/note` | 내 핸드 노트 저장(아래 핸드 복기 노트) → 저장된 노트. 받지 않은 핸드는 404, 메모 버전이 다르면 409 `note_conflict`(`error.details.note`). 회원당 60초에 60회(429) |

**추천인 보상**(`apps/api/src/lib/referral.ts`): 가입 때 그 시점 정책 버전의 보상액·필요 핸드 수를 추천 행에 적어 두므로, 나중에 정책을 바꾸거나 꺼도 이미 받아들인 추천의 약속은 바뀌지 않는다. 꺼진 상태의 가입은 `unpaid`(`off`)로 기록만 한다. 추천 행을 쓸지와 그 상태(대기·`unpaid`의 이유·`review`)는 행을 넣는 한 문장(INSERT … SELECT) 안에서 정한다. 그래서 동시에 들어온 가입끼리도 같은 메일함·같은 네트워크 판단이 서로를 본다. 같은 정규화 이메일로 여러 가입이 동시에 와도 하나만 대기가 되고 나머지는 `unpaid`(`repeat_email`)이다. 한 네트워크의 몰린 가입도 동시에 와서 `burstLimit`번째부터 모두 `review`가 된다. 한도는 지급할 때 판단한다(아래). 양쪽은 각각 원장 `referral` 한 행으로만 지급되며(멱등 키 `referral:<추천 ID>:invitee`·`referral:<추천 ID>:referrer`), 원장 행을 쓰는 같은 문장에서 그쪽이 아직 대기인지, 일시중지가 아닌지, (추천인은) 지금 하루·누적 한도 안인지 다시 확인한다. 가입 직후, 두 회원이 카드를 열 때, 매일 크론(오래된 순 50건), 관리자의 다시 정산이 같은 추천을 동시에 처리해도 한쪽에 한 번만 지급된다. 추천인이 한도에 닿았으면 추천인 쪽만 `capped`로 끝나고 가입자는 그대로 받는다. 막는 것: 추천인 자기 이메일의 별칭으로 가입(정규화: 소문자, `+태그` 제거, Gmail은 점 제거), 가입자당 추천인 한 명(가입자 ID 고유), 탈퇴 뒤 같은 이메일로 다시 가입(정규화한 이메일의 HMAC이 이미 있으면 보상 없음, 둘 다 `repeat_email`), 이메일 인증이 켜졌는데 인증하지 않은 가입(`email`), 봇·정지·탈퇴 회원의 코드(`referral_invalid`). 같은 추천인 코드로 하루 안에 같은 네트워크에서 `burstLimit`번째 가입부터는 `review`(운영자 확인)로 둔다. 같은 IP라는 것만으로는 아무것도 거절하지 않고, 관리자 화면에는 '같은 네트워크' 신호만 보인다. 필요 핸드 수를 30일 안에 채우지 못하면 `unpaid`(`hands`)로 끝난다. 정지된 회원 쪽은 해제될 때까지 기다리고, 탈퇴한 가입자의 대기 보상은 지급하지 않으며, 탈퇴한 추천인 쪽은 `skipped`(가입자는 그대로 받음). 지급되면 계정 언어로 쪽지를 보낸다.

**핸드 복기 노트**(`apps/api/src/lib/handNotes.ts`, 표 `hand_notes`): 회원·핸드마다 한 행, 본인만 읽고 쓴다. 본문은 `{bookmarked?, tags?: {태그: true|false}, memo?, rev?}`(모르는 키·빈 본문은 400 `invalid_input`). 북마크와 태그는 보낸 것만 바뀌고(태그는 비트로 켜고 꺼서 다른 태그를 동시에 저장해도 모두 남음) 버전 없이 저장된다. 메모(최대 500자, 앞뒤 공백 제거, 빈 메모는 지움)는 읽었던 `rev`와 함께 보내야 하고, 저장된 `rev`가 같을 때만 바뀌며 `rev`가 1 오른다. 다르면 아무것도 바꾸지 않고 409 `note_conflict`로 저장된 노트를 돌려준다(다른 창·기기의 저장을 덮지 않음). 소유 확인과 저장은 한 batch이며 탈퇴 중인 회원은 쓸 수 없다. 날짜별로 저장 종류(`hn_bookmark`·`hn_tag`·`hn_memo`)와 실패 이유(`hn_fail_conflict`·`invalid`·`notfound`·`limit`·`error`)만 `daily_stats`에 센다. 메모·태그 내용, 회원, 핸드는 통계·로그·감사 기록 어디에도 남기지 않는다. 탈퇴하면 그 회원의 행을 지운다.

**계정 설정 동기화**(`apps/api/src/lib/settings.ts`, 표 `user_settings`, 타입 `packages/types/src/settings.ts`): 회원마다 한 행. 동기화 대상은 테마·4색 덱·위험 액션 확인·초보자 모드·금액 단위·퀵 반응·색각 모드·친구 정렬·내 차례 진동·현재 내 족보 표시(`SYNCED_PREF_KEYS`, 이전 기기가 보내는 `autoMuck`도 받지만 쓰지 않음)과 즐겨찾기 테이블(최대 50개, 최신 순). 사운드와 브라우저 자동재생 허용, 최근 연 테이블, 앱 설치 안내 숨김은 기기마다 남는다(서버에 보내지 않음). 언어는 이전부터 계정의 `locale`.
- 설정 하나·테이블 하나마다 마지막으로 바뀐 시각을 **서버 시계**로 적는다. 기기는 바꾼 지 몇 ms 지났는지(`ago`, 30일까지 셈)만 보내므로 기기 시계가 틀려도 순서가 바뀌지 않는다. 더 나중에 바뀐 쪽이 설정·테이블 하나씩 이기므로, 두 기기가 서로 다른 설정을 바꾸면 둘 다 남고 오프라인이던 기기가 다른 기기의 나중 변경을 되돌리지 못한다. 진 항목은 `kept`(`'theme'`, `'fav:<테이블>'`)로 알려 주고 계정 값이 화면에 반영된다. 즐겨찾기를 끈 기록은 한동안(최대 100개·30일) 남아 오래된 추가가 되살리지 못한다.
- **최초 병합**: 기기에 동기화 이전 설정(`jc.prefs`, 계정별 즐겨찾기)이 있으면 그 기기에서 처음 로그인한 계정이 `legacy`로 한 번 보낸다. 계정에 값이 **없는** 설정·테이블만 채우고(시각 0, 어떤 실제 변경에도 짐), 서버에 이미 있는 설정은 새 기기의 값·기본값으로 덮지 않는다. 관리자가 초기화한 계정(`epoch > 0`)에는 받지 않는다.
- **계정 분리**: 저장 본문의 `user`는 그 기기에서 변경을 만든 계정이고 지금 로그인한 계정과 다르면 409 `settings_account`(다른 탭에서 다른 계정으로 로그인한 경우). 화면은 계정별 저장소(`jc.settings:<회원>`)만 쓰고, 로그아웃하면 기본값으로 돌아가며 저장된 것은 기기에서 지운다(아직 저장 못 한 변경만 그 계정의 다음 로그인을 위해 남김).
- **실패**: 저장이 실패해도 화면 설정은 그대로 쓰이고 기기에 남아 늘어나는 간격(2–60초)과 연결 복구 때 다시 보낸다. 실패 횟수는 다음 요청의 `fails`로 운영 통계에 더한다. 화면의 동기화 상태는 저장 중·저장됨·실패(로컬에 유지)·다른 기기 변경 반영·관리자 초기화 반영.
- **자동 머크**: 2026-10-19부터 항상 적용되어 설정이 아니다. 이전 기기가 저장하는 `autoMuck`은 다른 칸처럼 받아 두지만(초기화·복구도 함께) 어디에도 쓰지 않고, 테이블에도 알리지 않는다(`docs/WEBSOCKET_PROTOCOL.md` '쇼다운 머크').
- 탈퇴하면 행을 지운다. 관리자는 값을 보지도 바꾸지도 못하고 초기화·복구만 한다(아래 관리자 API).

**핸드 재생 필드(`HandReplayFields`, `packages/types/src/community.ts`):** `/hands/:id`와 게시판 첨부 핸드 리뷰가 같이 준다. 종료 핸드의 저장된 기록만 쓰고, 새 정보를 계산해 내지 않는다. 팟을 나눠 보이는 일은 서버(`apps/api/src/lib/community.ts` `replaySettlement`)가 하고, 화면은 받은 값을 그대로 읽는다.
- `maxSeats`(테이블 좌석 수), `buttonSeat`(딜러 버튼), `smallBlind`·`bigBlind`, `board`, `potTotal`.
- `actions`: `{seatIndex, stage, type, amount}`. `amount`는 그 액션으로 **더 낸 칩**(레이즈 총액이 아님). 블라인드는 `post-sb`·`post-bb`.
- `returned`: 콜 받지 못해 가장 많이 낸 플레이어에게 돌아간 칩 `{seatIndex, amount}`. 금액은 핸드 통계가 저장한 `won − pot_won`(`packages/db/src/handStats.ts`, 정의는 한 곳)이고 여기서 다시 계산하지 않는다. 돌아간 칩이 없거나, 통계가 아직 채워지지 않았거나(게임 워커가 핸드 기록 직후 채운다), 저장된 팟과 맞지 않으면(한 사람 몫이 아님, 엔진이 따로 둔 팟과 다름, 그 사람의 팟 몫보다 큼) null이고 `pots`는 저장된 그대로다.
- `pots`: 메인 팟부터 `{amount, eligibleSeats, winners: [{seatIndex, amount}], uncalled}`. `uncalled: true`는 콜 받지 못해 돌려준 베팅. 엔진은 누군가 올인했을 때만 이를 따로 둔다. 모두가 폴드한 베팅은 엔진이 지급한 팟 안에 남아 있어, `returned`가 있으면 그 플레이어가 이긴 마지막 팟에서 떼어 `uncalled: true` 팟으로 보낸다. 나눈 뒤에도 각 팟의 `winners` 합은 `amount`, 모든 팟의 합은 `potTotal`, 플레이어별 합은 `won`이다. 저장된 기록(`hands.event_log`, `hand_players`)은 바꾸지 않는다.
- 플레이어별 `stackStart`, `net`, `won`, `holeCards`, `rankClass`, `bestFive`. 카드 세 필드는 본인과 쇼다운에서 공개된 패만 값이 있고 나머지는 null(위 머크 규칙).
- 이 변경 전에 기록된 핸드는 `buttonSeat`·`pots`가 null이다. 화면은 플레이어별 `won`에서 `returned`만큼 뺀 값을 보여 주고, `returned`가 null이면 `won`에 돌려받은 베팅이 섞일 수 있다.

로비 응답의 각 테이블에는 `roomType`(`official`/`member`)과 `host`(회원 방이면 `{id,nickname}`, 공식 테이블이면 `null`, 방장이 관리자면 `role`도)가 있습니다. 공식 테이블이 먼저, 회원 방이 뒤에 나옵니다.

테이블 봇: `bots`는 지금 앉아 있는 봇 수(`seated`에 포함, 회원 수 = `seated − bots`), `botLevel`은 봇을 허용한 공식 테이블이면 `easy`·`normal`·`hard`·`expert`, 아니면 `null`입니다(`expert`는 봇 AI 2.0부터. 배포 전에 열어 둔 이전 화면은 이 값을 몰라 로비 배지·좌석·봇 카드의 난이도 글자가 `undefined`로 보이고, 새로고침하면 '전문가'로 보입니다). 테이블 상태의 좌석에는 봇이면 `bot`(난이도)과 `botStyle`(그 핸드를 두는 스타일: `balanced`·`tag`·`lag`·`tight-passive`·`loose-passive`·`casual`), 핸드 뒤 일어날 봇이면 `botLeaving`이 붙고, 봇의 홀카드는 다른 좌석처럼 쇼다운 전에는 보이지 않습니다. 봇 계정은 회원이 아니어서 로그인(401 `invalid_credentials`), 친구 신청·차단(409 `bot_account`), 1:1 대화(친구가 아니므로 403 `not_friends`), 신고(409 `bot_account`)를 받지 않습니다. 내 핸드 상세(`/api/me/hands/:id`)의 봇 좌석에는 `bot: true`가 붙습니다(난이도 없음).

빠른 참가는 열린 공개 테이블(비공개·입장 제한 제외, 이미 앉아 있는 테이블과 `exclude` 제외) 가운데 `maxSeats`·`bigBlind`가 일치하는 것만 봅니다. 순서는 로비 수치상 빈자리가 있어 보이는 테이블 → 입문자(완료 핸드 50 미만)에게는 입문 테이블 먼저, 그 밖의 플레이어에게는 입문 테이블을 나중에 → 착석 인원이 많은 순 → 낮은 블라인드 → 공식 테이블 → id 순입니다. 로비 수치는 늦을 수 있으므로 상위 5개 테이블에 차례로 테이블 룸(Durable Object)의 착석 검사(`sit`과 같은 검사, 지갑 제외)를 물어 처음 통과한 테이블을 돌려줍니다. 자리를 잡아 두지는 않으므로 실제 착석은 `sit`이 다시 검사합니다. 실패 코드는 `404 no_table`(조건에 맞는 테이블 없음), `409 insufficient_balance`(`details: {minBuyIn, balance}`, 맞는 테이블 중 가장 낮은 최소 바이인도 지갑보다 큼), `409 tables_full`(검사한 테이블이 모두 찼거나 대기 명단 우선)입니다.

**배지의 성격:** 배지는 본인 학습 기록으로 받는 **장식용 표시**이며 공식 수료 증명이 아니다. 레슨·퀴즈는 브라우저에서 진행되고 서버가 채점하지 않으므로, 서버는 공부했다는 사실을 증명할 수 없다. 배지는 본인 화면(아카데미·진행 현황·마이페이지)에만 보이고, 다른 사용자·관리자 화면이나 게임 로직, 칩·원장에는 쓰이지 않는다. 화면에도 이 점을 안내한다.

**타당성 검사(`plausibleBadges`, `packages/types/src/academy.ts`):** 실제 앱이 만들 수 없는 진도는 배지에 세지 않는다. 시계 오차는 24시간(`BADGE_CLOCK_SKEW_MS`)까지 허용한다.
- 레슨 완료: `startedAt`·`completedAt`이 정수 ms이고 가입 시각~서버 현재 시각 사이, 시작 ≤ 완료, `step`이 그 레슨의 마지막 단계(카드 3, 족보 4, 홀덤 4, 액션 3, 연습 0) 이상.
- 연습 시나리오: 완료 시각이 같은 범위의 정수 ms.
- 복습 세트(`review.sessions`): 한 세트는 8문제를 모두 맞혀야 끝나므로 `quiz.correct + quiz.wrong ≥ sessions × 8`일 때만 인정.
- 모든 규칙은 기기 간 병합(가장 이른 시각, 가장 큰 단계·카운터) 뒤에도 성립한다. 서버 시각보다 24시간 넘게 앞선 시각은 그 시각이 지난 뒤의 다음 동기화에서 인정된다.
- 이미 지급된 배지는 회수하지 않으며(검사 도입 전 지급분 포함) DB 스키마 변경은 없다.

`rooms`(점검 예약·변경·종료 응답): `{tables, reached, unreached[], truncated}`. 접속자나 착석자가 있는 열린·종료 중 테이블(연결 많은 순, 최대 60곳)의 룸에 테이블 설정을 다시 읽게 해(한 번 더 시도) 점검 표시와 핸드 중단·재개를 바로 반영한다. 답하지 않았거나 60곳 밖의 룸은 다음 점유 기록 때나 핸드를 기록할 때(같은 batch에서 점검을 읽음) 알게 되고, 알고 난 뒤에는 점검 시작·종료 시각의 알람에서 D1을 다시 읽는다. 사람이 그대로인 채 핸드를 이어 가던 룸도 그 핸드를 기록하면서 점검을 알아 다음 핸드를 시작하지 않는다. 설정·좌석·칩은 바꾸지 않는다.

아카데미 지표(관리자): `GET /api/admin/academy/stats` → `[{kind, itemId, starts, completes, correct, wrong}]`(익명 집계). 테이블 생성·수정 본문에 `beginner`(입문 테이블) 추가.

## 토너먼트(6인 SNG)

회원 `GET /api/tournaments`, `GET /api/tournaments/:id`, `POST /api/tournaments/:id/register`, `POST /api/tournaments/:id/unregister`와 관리자 `/api/admin/tournaments*`, `/api/admin/tournament-templates*`. 요청·응답·오류 코드·권한은 `docs/TOURNAMENT.md` "API"에 있다. 대회 테이블(`roomType: 'tournament'`)은 로비 목록과 빠른 참가에 나오지 않고, 착석·충전·리바이는 룸이 `tournament_table`로 거절하며, 관리자 테이블 종료·긴급 제어·설정 변경은 409 `tournament_table`이다. 관리자 테이블 상세(`GET /api/admin/tables/:id`)는 대회 테이블이면 `tournament: {id, name, status}`를 더한다.
