# 접속 상태 · 웹 푸시 · 알림 설정 · 색각 보조

이 문서는 친구에게 보이는 접속 상태(A–B), 웹 푸시(C–I), 알림 동의와 야간 시간(E–F), 발송 큐(G), 보안(H), 색각 보조(J)를 코드 기준으로 적는다. API 목록은 `docs/API.md`, 배포 순서와 비용은 `docs/DEPLOYMENT.md`, 개인정보 처리는 `docs/PRIVACY_OPERATIONS.md`에 있다.

**만들지 않은 것**: 테이블 채팅 푸시(테이블 화면을 보고 있는 동안만 의미가 있어 넣지 않았다), 친구 접속 알림 푸시, 광고·이벤트 푸시, 정확한 마지막 접속 시각, 관리자용 전체 접속 현황. 야간 시간(21:00–08:00 KST) 기준과 동의 문구는 법률 검토가 남아 있다(아래 "남은 일").

## 1. 접속 상태

### 상태와 모드

| 상태 | 친구에게 보이는 뜻 | 표시 |
|---|---|---|
| `online` | 기기 하나라도 최근 5분 안에 조작했다 | 채운 점 + "온라인" |
| `away` | 접속해 있지만 모든 기기에서 5분 넘게 조작이 없다(또는 자리 비움 모드) | 초승달 + "자리 비움" |
| `offline` | 살아 있는 기기가 없다(또는 오프라인 표시 모드) | 빈 고리 + "오프라인" |

모드(`users.presence_mode`, 계정 설정이라 모든 기기에 같다): `auto`(기본, 위 규칙), `away`(접속해 있으면 항상 자리 비움), `invisible`(친구에게 항상 오프라인). 모드는 상태를 낮추기만 한다. 자리 비움 모드가 온라인을 만들 수 없고, 오프라인 표시는 무엇보다 앞선다(`packages/types/src/presence.ts`의 `mergePresence`).

- **서버가 정한다.** 기기는 "나 여기 있다"와 "마지막 조작이 몇 ms 전"만 보낸다. 서버가 자기 시계로 `activeAt = now − idleMs`(최대 24시간)를 계산하고, 하트비트 간격도 믿지 않는다(기기는 마지막으로 들은 때부터 90초가 지나면 사라진다).
- **여러 기기**: 기기 하나가 온라인이면 온라인, 모두 자리 비움이면 자리 비움, 살아 있는 기기가 없으면 오프라인. 회원당 기기 10개까지 기억하고 넘으면 가장 오래 소식이 없던 기기를 버린다. 기기는 (로그인 세션, 페이지마다 새로 만든 id)로 구분해, 같은 id를 다른 로그인이 보내도 다른 기기다.
- **테이블과 별개**: 계정의 자리 비움은 테이블의 `sittingOut`과 관계없다. 자리 비움이 폴드·싯아웃·턴 시계를 바꾸지 않는다. 게임 서버의 테이블 코드는 바뀌지 않았다.

### 하트비트(웹, `apps/web/src/lib/presence.ts`)

- 로그인해 있는 동안 30초마다 `POST /api/me/presence/heartbeat {conn, idleMs, visible, view?}`를 보낸다(숨긴 탭도 브라우저가 늦추는 만큼 보낸다).
- 조작(포인터·키·터치·휠) 자체는 아무것도 보내지 않는다. 5분 넘게 조용하다가 다시 조작하면(친구에게 자리 비움으로 보일 수 있으므로) 10초 안에, 탭을 숨기거나 다시 보이거나 대화 화면을 열고 닫으면 3초 안에 한 번 더 보낸다. 두 박동 사이는 그보다 가깝지 않다.
- 30분 동안 조작이 없으면 박동을 멈춘다. 그 기기는 90초 뒤 사라져 친구에게 오프라인으로 보이고, 다음 조작에서 다시 시작한다.
- 페이지를 닫거나 뒤로/앞으로 캐시에 들어가면 `keepalive` 요청으로 `POST /api/me/presence/leave {conn}`을 보낸다. 실패하면 90초 뒤 사라진다.
- 실패하면 30초부터 두 배씩 최대 5분까지 늦추고, 429면 1분 쉰다.
- 박동의 응답은 계정의 모드와 친구에게 보이는 상태다. 다른 기기에서 바꾼 모드가 다음 박동(최대 30초)에 이 기기에 보인다.

### 허브(`apps/game-worker/src/presence.ts`, `presence-book.ts`)

- 게임 Worker의 Durable Object `PresenceHub` 한 개(`hub-0`)가 모든 기기를 **메모리에만** 둔다. 저장소·D1에 쓰지 않으므로 하트비트마다 D1 쓰기가 없다(DO 마이그레이션 `v2`, SQLite 클래스지만 저장소를 쓰지 않는다).
- API만 부를 수 있다(내부 비밀 헤더). API가 인증·친구 관계·모드를 판단하고, 허브는 누가 누구를 볼 수 있는지 모른다. 허브에 묻는 것은 자기 기기 또는 수락된 친구 목록뿐이다.
- 한도: 회원당 박동 분당 40회, 상태 질문 분당 30회, 한 질문에 1,000명. 넘으면 429.
- 1분에 한 번 사라진 기기와 지난 한도 창을 지운다(회원 수에 비례).
- **허브가 다시 시작되면**(배포, 퇴거, 장애) 모든 기억이 사라지고, 각 기기의 다음 박동(최대 30초)까지 친구가 오프라인으로 보인다. 데이터 손실은 없다(저장한 것이 없다). 허브에 닿지 못하면 박동은 503 `presence_unavailable`으로, 친구 상태는 모든 친구를 오프라인으로 답한다(친구 목록 자체는 보인다).
- **로그인이 끝날 때**: 로그아웃(이 기기)·다른 기기 모두 로그아웃·비밀번호 변경·정지·탈퇴는 세션 행을 지운 뒤 허브에 `leave`를 보내 그 로그인의 기기를 바로 지운다(`apps/api/src/lib/signout.ts`). 허브는 끝난 일을 90초 동안 기억해, 로그아웃 직전에 세션 확인을 통과하고 늦게 도착한 박동이 그 로그인을 다시 살리지 못한다(그 뒤의 박동은 세션 확인에서 401로 막힌다). 로그아웃과 세션 목록에서 다른 기기 하나를 끝내는 것은 그 로그인을, 비밀번호 변경은 그 시각(API의 시계) 전에 만든 로그인 중 이 기기를 뺀 전부를, 비밀번호 재설정·관리자의 정지와 강제 로그아웃·탈퇴는 그 시각 전에 만든 모든 로그인을 막는다. 이런 막음은 도착 순서와 관계없이 모두 기억하고 하나라도 해당하면 박동을 받지 않는다(남겨 둔 로그인이 같은 막음은 하나로 합친다: 나중 것이 앞의 것이 막은 로그인을 모두 막는다. 남겨 둔 로그인이 다른 막음은 회원당 16개까지이고 넘치면 가장 먼저 끝나는 것이 빠지지만, "모든 기기 로그아웃"은 빠지지 않는다): 먼저 한 "이 기기 빼고 로그아웃"이 나중에 한 "모든 기기 로그아웃"보다 늦게 도착해도 그것을 되돌리지 않는다. 그래서 박동은 세션 만료 시각(`until`)과 만든 시각(`since`)을 함께 보내고, 허브는 기기를 세션 만료보다 오래 두지 않는다. 허브가 이것을 기억하는 동안 다시 시작되면 기억도 사라지지만, 그때는 기기 기록도 함께 사라지고 늦은 박동 하나가 남길 수 있는 것은 최대 90초다.
- **샤딩 시점**: 허브 하나가 모든 회원을 맡는다. 동시 접속 기기 수천 대까지는 요청 수(기기당 분당 2회)가 DO 하나의 처리량 안이라고 보지만 측정하지 않았다. 동시 접속이 늘어 허브 응답이 느려지면 회원 id 해시로 `hub-<n>`을 나누고, 친구 질문은 해당 허브들에 나눠 묻는다(지금 코드에는 없다).

### 친구 상태 조회와 개인정보

- `GET /api/friends/presence`: D1에서 **수락된 친구**이면서 상대가 활성 회원이고 어느 쪽도 차단하지 않은 회원만 고른 뒤 허브에 묻고, 각자의 모드를 적용한다(`apps/api/src/routes/social.ts`). 친구 요청 대기·거절, 차단(양방향), 친구 해제, 정지·탈퇴 회원은 응답에 없다.
- 응답은 상태 세 가지뿐이다. 마지막 접속 시각, 기기 수, 보고 있는 화면은 내보내지 않는다. 관리자 콘솔에 전체 접속 현황을 만들지 않았다(대시보드의 기존 "최근 5분 접속자 수"는 그대로).
- 웹은 친구 목록이나 대화 화면이 떠 있고 페이지가 보일 때만 30초마다 묻는다. 마지막으로 읽은 지 75초(조회 간격의 2.5배)가 지난 상태는 현재처럼 보이지 않는다: 읽지 못하면 지우고, 숨긴 탭이나 닫았던 목록으로 돌아오면 다시 묻는 동안 비워 둔다(전에는 10분 전 상태가 새 답이 올 때까지 보였다).

### 화면

- 친구 목록·친구 상세·대화 상단에 모양 + 글자로 표시한다(색만으로 구분하지 않는다).
- 친구 목록 정렬: 온라인 → 자리 비움 → 오프라인, 같은 상태 안에서는 최근 대화 순. "최근 대화 순"을 고르면 상태와 관계없이 최근 대화 순이다.
- 내 상태(모드)는 마이페이지, 설정 창, 데스크톱 메뉴, 휴대폰 메뉴에서 바꾼다. 저장은 서버에 하고, 화면은 서버가 저장했다고 답한 값만 보인다. 실패하면 그 자리에 이유와 함께 오류를 보이고 선택은 저장된 값 그대로다.

## 2. 웹 푸시

### 보내는 것

| 종류 | 언제 큐에 넣나 | 받는 사람 | 클릭하면 |
|---|---|---|---|
| `dm` 1:1 메시지 | 메시지 저장 뒤 | 받는 친구 | 그 대화 |
| `invite` 게임 초대 | 기존 초대 메시지(DM) 저장 뒤 | 초대받은 친구 | 초대 메시지가 있는 대화(테이블 입장 권한은 들어갈 때 다시 확인) |
| `friend_request` | 요청이 **새로 생겼을 때만**(이미 있던 요청을 다시 보내면 없음) | 받는 회원 | 친구 화면(요청 목록) |
| `friend_accepted` | 수락 뒤 | 요청을 보낸 회원 | 수락한 친구와의 대화 |
| `tournament_start` | 대회가 시작 상태로 바뀐 그 변경에서 한 번 | 그 대회에 등록해 자리에 앉은 회원(봇 제외) | 대회 테이블 |
| `tournament_cancel` | 관리자의 취소(시작 전)·중단(진행 중) 처리 뒤 | 취소: 등록자. 중단: 참가자(탈락자 포함) | 대회 상세 |
| `tournament_result` | 대회가 끝나 순위가 정해진 뒤(게임 Worker) | 참가자(탈락자·우승자) | 대회 상세 |

- 문구는 종류마다 고정된 일반 문장이다(`apps/api/src/lib/notify.ts` `TEXT`, 한국어·영어는 회원의 언어). 보낸 사람 이름, 메시지 내용, 테이블 이름, 카드, 금액을 넣지 않는다(잠금 화면에 보인다).
- 클릭 주소는 사이트 안의 경로뿐이다. 서비스 워커가 `/`로 시작하지 않거나 `//`·`\`가 든 주소는 홈으로 바꾼다.
- 같은 친구의 DM은 같은 태그(`dm:<친구>`, 초대는 `invite:<친구>`)라 화면의 이전 알림을 바꾸고, 푸시 서비스의 `Topic`도 같아 기기가 꺼져 있는 동안 쌓이지 않고 마지막 것만 남는다.

### 동의(E)

- **계정 동의**(`service`, "[선택] 서비스 푸시 알림 수신 동의"), **야간 동의**(`night`, "[선택] 야간(21:00–08:00) 푸시 알림 수신 동의"), **기기 권한**(브라우저·OS의 알림 허용)은 각각 따로다. 계정 동의가 없으면 어떤 기기에도 보내지 않고, 기기 권한은 그 기기에서만 의미가 있다.
- 가입 화면에 두 선택 항목이 있고 기본은 꺼짐이다. 가입 화면은 브라우저 권한을 묻지 않는다. 권한은 회원이 마이페이지에서 "이 기기에서 받기"를 누를 때만 묻는다.
- 설정은 서버가 정본이다(`notification_settings`, 버전 열). 저장할 때 화면에 보인 버전을 함께 보내고, 확인과 쓰기가 한 D1 batch라 두 기기가 동시에 저장하면 하나만 이기고 다른 하나는 409 `stale_settings`로 다시 읽는다. 다른 기기에서 철회한 동의를, 그것을 보지 못한 기기가 예전 화면 그대로 저장해 되살릴 수 없다.
- 동의·철회는 `notification_consents`에 종류(서비스·야간), 값, 동의 문구 버전(`NOTIFICATION_CONSENT_VERSION`), 시각, 경로(가입·설정)로 한 줄씩 남는다. IP와 기기 정보는 남기지 않는다.
- 계정 동의를 철회하면 그 회원의 모든 기기 등록을 지운다.

### 야간 시간(F)

- 21:00:00–07:59:59 KST(UTC+9, 서머타임 없음)는 야간이다. 20:59:59는 보내고, 21:00:00은 막고, 07:59:59는 막고, 08:00:00은 보낸다(`isKstNight`, 단위 테스트에 네 경계가 있다).
- 서버 시계로 판단한다. 기기의 시간대와 관계없다.
- 야간 동의가 없으면 야간에 생긴 일은 큐에 넣지 않고, 낮에 큐에 넣었더라도 보내는 순간이 야간이면 보내지 않는다. 아침에 몰아 보내지 않는다(버린다). 그래서 야간 동의를 나중에 켜도 그 전에 생긴 야간 일은 오지 않는다.
- 야간 동의 기본값은 꺼짐이다.

### 발송 큐(G, `notification_events`)

1. 푸시를 알리는 일(메시지 저장, 친구 요청 등)이 **먼저 커밋된 뒤** 다른 D1 batch로 큐에 넣는다. 큐 넣기가 실패해도 로그만 남고 원래 일은 그대로다.
2. 계정 동의가 있고, 그 종류가 켜져 있고, 등록된 브라우저가 있고, 야간이면 야간 동의도 있는 회원에게만 행을 쓴다(`packages/db/src/notify.ts`). 푸시를 켜지 않은 회원은 비용이 없다.
3. `dedupe_key`(고유 인덱스)로 같은 일은 몇 번 써도 한 행이다. 대회 시작은 `tournament_start:<대회>:<회원>`이고, 시작 상태로 바꾼 그 UPDATE가 성공했을 때만 쓴다.
4. 보내기: 요청을 처리한 Worker가 `waitUntil`로 그 회원 것을 바로 보내고, 매분 크론이 남은 것과 게임 Worker가 넣은 대회 알림을 보낸다. 둘이 겹치지 않도록 행을 60초 동안 잡는다(`lease_until`, `UPDATE … RETURNING` 한 문장). 잡은 행은 그 실행만 끝낼 수 있다.
5. 보내기 직전에 다시 확인한다: 회원이 활성인지, 동의·종류·야간, 친구 관계(또는 요청)가 그대로이고 상대가 활성이며 차단이 없는지(차단은 DM 보내기와 같이 일반 회원을 막은 것만 센다: 운영진이 된 친구는 차단해도 메시지가 오므로 그 푸시도 막지 않는다), DM·초대는 그 메시지(초대도 메시지 한 건이다)를 그새 읽었는지(다른 기기에서 읽었거나 다시 시도 전에 읽었으면 `read`로 건너뛴다. 큐의 `dedupe_key`에 든 메시지 id로 상한·쿨다운과 같은 질의에서 기본 키 1행을 더 읽는다), 시간당 30개 상한과 같은 친구 1분 쿨다운(둘 다 실제로 보낸 시각 `sent_at`으로 센다: 오래 기다린 일도 보낸 시간의 푸시다. 마이그레이션 0030의 `(user_id, status, sent_at)` 인덱스로 최근 1시간만 읽는다), 그 대화를 지금 보고 있는지(허브의 `viewing`: 그 대화가 열린 기기가 보이고 있고 5분 안에 조작이 있었을 때만. 대화를 띄워 둔 채 자리를 비운 기기는 보고 있는 것으로 치지 않는다). 시간 확인은 행마다 그 순간의 시계로 한다.
6. 받는 기기: 아직 살아 있는 로그인 세션의 등록만(최대 10개). 로그아웃·만료된 로그인의 등록은 쓰지 않는다.
7. 결과: 한 기기라도 받으면 `sent`. 푸시 서비스가 바쁘거나(429·5xx·응답 없음·10초 초과) 실패하면 1분·5분 뒤 다시(최대 3회), 만료가 먼저 오면 버린다. 404·410은 그 등록을 지우고, 거절(400·401·403·413)이 3번 이어지면 지운다.
8. 만료: DM 1시간, 초대 30분, 친구 요청·수락 6시간, 대회 시작 15분, 대회 취소·결과 6시간. 지나면 `expired`로 끝낸다. 늦은 푸시는 안 보내느니만 못하다고 보았다.
9. 실행 하나가 푸시 서비스에 보내는 요청은 40개까지다(무료 플랜 하위 요청 한도 50). 남은 것은 다음 실행이 보낸다. 잡은 시간이 끝나기 전에 마칠 수 없으면 남은 행을 놓아 두고 멈춘다(다른 실행이 같은 행을 다시 잡아 두 번 보내지 않게). 보낸 결과를 두 번(결과 기록과 예외 경로) 다 쓰지 못해도 멈추고 남은 행을 놓는다: 기록되지 않은 발송은 다음 일의 쿨다운·상한이 셀 수 없기 때문이다.
10. 기록은 7일 뒤 매일 정리(`housekeeping`)에서 지운다. 기록에는 본문이 없다(종류, 내부 경로, 상태, 시각).

### 전송(`apps/api/src/lib/webpush.ts`)

- 표준 Web Push: VAPID(RFC 8292, ES256 JWT, `aud`는 푸시 서비스 출처, 12시간, `sub`는 `https://jc-royal.site`), 본문 암호화 `aes128gcm`(RFC 8291·8188). 외부 라이브러리 없이 WebCrypto로 만들었고 RFC 8291 부록의 시험 벡터로 단위 테스트한다.
- 헤더: `TTL`(만료까지 남은 초, 그보다 길지 않게. 푸시 서비스가 만료 뒤에 전하지 않는다). 암호화·서명 뒤 요청 직전에 만료를 한 번 더 보고, 그새 만료됐으면 보내지 않으며(그 브라우저의 실패로 세지 않는다) TTL도 그때 남은 시간으로 다시 정한다, `Urgency`(DM·초대·대회 시작 high, 나머지 normal), `Topic`(태그의 해시).
- 등록할 수 있는 주소는 허용 목록뿐이다: `fcm.googleapis.com`, `updates.push.services.mozilla.com`, `web.push.apple.com`, `*.push.apple.com`, `*.notify.windows.com`, `https`·기본 포트·사용자 정보 없음. 리다이렉트를 따라가지 않는다(SSRF 방지). 등록 키는 길이와 P-256 곡선 위의 점인지 확인한다(`onCurve`).
- 푸시 서비스의 응답 본문은 읽지 않는다. 등록 주소(endpoint)는 로그·응답·관리자 화면에 내보내지 않는다. 회원에게는 등록 id, "Chrome · Android" 같은 대략의 이름, 등록·마지막 성공 시각만 보인다.
- VAPID 개인 키는 Worker 시크릿이다(`docs/DEPLOYMENT.md` 2절). 키가 없으면 큐에 넣지도 보내지도 않고 D1도 읽지 않는다.

### 서비스 워커(`apps/web/public/sw.js`)

- push, notificationclick, notificationclose, pushsubscriptionchange, message만 처리한다. **fetch 처리기가 없고 아무것도 캐시하지 않는다.** 페이지·로그인·게임·카드·API는 서비스 워커가 없을 때와 똑같이 네트워크에서 온다. `/sw.js`는 `Cache-Control: no-cache`로 나가 수정이 바로 퍼진다.
- 회원이 이 브라우저에서 푸시를 켤 때만 설치한다.
- 페이지가 "지금 로그인한 회원"을 알려 주고(IndexedDB에 회원 id와, 바뀔 때마다 오르는 세대 번호만), 푸시는 받는 회원 id를 담는다. 둘이 다르면 보이지 않는다. 만료 시각은 서비스 워커가 따로 보지 않는다(기기 시계가 틀릴 수 있다). 위 TTL이 상한이다.
- 보이기 직전에 사이트에 "이 브라우저에서 그 회원이 아직 로그인해 있는지"를 한 번 묻는다(`GET /api/me/notifications/recipient`, 같은 출처 쿠키, 캐시 없음, 세션 연장 없음). 401이면 기억한 회원을 지우고 떠 있는 알림을 닫는다. 사이트가 답하지 않으면(네트워크 오류·5xx) 보이지 않는다. 묻는 동안 회원이 바뀌었으면(다른 계정, 또는 로그아웃 뒤 같은 회원 재로그인: 세대가 다르다) 그 답은 이전 로그인에 대한 것이라 보이지도 지우지도 않는다. 회원 변경과 보이기는 한 줄로 차례대로 하고(회원 변경은 한 트랜잭션의 비교 후 쓰기), 보인 뒤 회원이 바뀌었으면(업데이트 중인 다른 서비스 워커) 그 알림을 다시 닫는다. 회원을 알릴 때마다 다른 회원 몫의 알림을 닫는다.
  - 대가: 크롬은 푸시를 받고 알림을 띄우지 않으면 "백그라운드에서 사이트가 업데이트됨" 같은 기본 알림을 띄울 수 있고, 사파리는 보이지 않는 푸시가 반복되면 등록을 철회할 수 있다. 로그아웃한 브라우저의 등록이 철회되는 것은 받아들인다(어차피 지울 등록이다). 사이트 장애 중에 오는 푸시는 놓친다.
- 클릭: 같은 사이트의 창 중 **게임 테이블(`/table/…`)이 아닌 창**(보이는 창 먼저)을 앞으로 가져와, 그사이 테이블로 가지 않았는지 다시 본 뒤 페이지에 이동을 부탁한다(`jc-navigate`, 답은 `MessageChannel`의 포트로). 페이지는 앱 시작 때부터 듣고 있어(`apps/web/src/lib/push-nav.ts`, 로그인 확인 전에도) 라우터로 이동한 뒤 `ok`를 답한다. 3초 안에 답이 없으면(이전 버전 페이지, 멈춘 탭) 서비스 워커가 그 창을 직접 이동하고(`WindowClient.navigate`), 그것도 안 되면 새 창을 연다. 알림은 이동했거나 이동을 맡겼을 때 닫는다. 로그인되어 있지 않으면 앱이 로그인 화면으로 보낸 뒤 로그인하면 그 주소로 돌아간다. 권한 확인은 일반 링크와 같이 페이지가 한다.
  - **게임 테이블은 푸시 때문에 떠나지 않는다.** 테이블 창에는 묻지도, 이동시키지도, 그 옆에 새 창을 열지도 않는다(안드로이드 Chrome의 설치 앱은 `openWindow`가 기존 창을 이동시킬 수 있다). 열린 창이 테이블뿐이면 그 창을 앞으로 가져오기만 하고 알림은 그대로 두어 핸드가 끝난 뒤 다시 누를 수 있다. 페이지도 `/table/`에 있으면 이동을 거절한다(`ok: false`, 이중 방어). 사이트 창이 하나도 없으면 새 창을 연다.
- **클릭만으로 DM을 읽음 처리하지 않는다.** 대화 화면이 열리면 기존 읽음 처리를 그대로 쓰되, 페이지가 실제로 보일 때만 읽음을 보낸다(백그라운드 창에서 열린 대화는 보이게 될 때까지 기다린다, `apps/web/src/pages/Friends.tsx`).
- 대화를 읽으면(읽음 요청이 성공하고, 서비스 워커를 찾은 뒤에도 그 대화가 화면에 보일 때) 이 브라우저에 떠 있는 그 친구의 메시지·초대 알림(`dm:<친구>`, `invite:<친구>` 태그)을 닫고 배지를 다시 센다(`jc-read`, 서버 요청 없음). 다른 기기에 이미 떠 있는 알림은 그 기기에서 누르거나 지울 때까지 남는다(웹 푸시에는 다른 기기의 알림을 닫는 수단이 없다). 다만 읽은 메시지에 대한 푸시는 위 5번에서 더 보내지 않는다.
- 배지: `setAppBadge`가 있으면 떠 있는 알림 수, 없으면 아무것도 하지 않는다.
- 헤더의 안 읽은 수(받은함·DM·친구 요청)는 계정별로 둔다(`apps/web/src/lib/unread.ts`): 다른 계정이 로그인하면 이전 계정의 수를 보이지 않고, 이전 계정 때 보낸 질문의 늦은 답은 버린다. 로그인이 끝났으면(401) 0으로, 오프라인이면 보이던 수를 유지한다.
- `pushsubscriptionchange`: 기억한 회원이 있을 때만 새 등록을 서버에 보낸다(서버가 그 쿠키의 회원으로 등록한다).

### 계정 전환과 로그인 종료(H)

| 경우 | 푸시 |
|---|---|
| 같은 브라우저에서 A 로그아웃 → B 로그인 | A 로그아웃 때 서버가 그 로그인의 등록을 지우고, 로그아웃이 성공한 뒤(또는 로그인이 이미 끝나 있었으면, 401) 페이지는 서비스 워커의 회원 id를 지우며(떠 있는 알림도 닫는다) 브라우저 구독을 해지한다. 로그아웃 요청 자체가 실패하면(오프라인 등) A는 그대로 로그인해 있으므로 이 브라우저의 푸시도 그대로 둔다(전에는 먼저 꺼서, 실패하면 로그인한 채 푸시만 꺼져 있었다). 그중 무엇이 실패해 A의 구독이 남아도, B가 로그인한 페이지가 서비스 워커에 B를 알리므로 A의 푸시는 보이지 않고, 페이지는 A가 켠 구독을 해지한다. 같은 주소를 B가 등록하면 그 행이 B의 것으로 바뀐다(주소 해시 고유 인덱스) |
| 세션 목록에서 다른 기기 끝내기 | 그 로그인의 등록을 지운다. 이미 푸시 서비스에 있던 푸시는 서비스 워커의 로그인 확인(401)에서 막힌다 |
| 비밀번호 변경 | 이 기기를 뺀 모든 로그인의 등록을 지운다(비밀번호 재설정과 관리자의 강제 로그아웃은 이 기기도). 남은 푸시는 위와 같이 막힌다 |
| 정지 | 세션을 지우고 등록도 지운다. 보내기 직전 확인에서 `inactive`로 막는다 |
| 탈퇴 | 설정·등록·발송 기록을 지운다. 동의 이력은 가명 id로 남는다(`docs/PRIVACY_OPERATIONS.md`) |
| 세션 만료 | 보내는 기기는 살아 있는 세션의 등록뿐이다. 매일 정리가 세션 없는 등록을 지운다 |
| 브라우저 권한 철회 | 푸시 서비스가 404·410을 주면 등록을 지운다. 다음에 페이지를 열면 이 기기의 상태를 "꺼짐"으로 보인다 |

### iOS·지원 범위

- 기능 감지로만 판단한다(User-Agent를 보지 않는다): `serviceWorker`, `PushManager`, `Notification`이 있으면 지원.
- iPhone·iPad는 iOS 16.4 이상에서 홈 화면에 추가한 앱으로 열 때만 Web Push가 있다. 사파리 탭에서는 이 세 가지가 없고 `navigator.standalone`이 `false`라, "홈 화면에 추가한 뒤 켤 수 있다"는 안내를 보인다.
- 실기기 확인은 하지 않았다. 서버의 큐·암호화·전송은 통합 테스트가 로컬 푸시 수신 서버(`tests/support/push-sink.ts`)로 확인하고 받은 본문을 복호화해 본다. 서비스 워커가 실제 브라우저에서 푸시를 받아 보이는 것은 확인하지 않았다(푸시 서비스에 닿아야 한다).

- 계정 설정 `colorVision`: `normal`(기본), `protan`(적색약), `deutan`(녹색약), `tritan`(청색약), `highContrast`(고대비). 모든 기기에 같다(기존 계정 설정 동기화).

- 2026-10-19 추가(`feat/game-ux-vip-gto`): 좌석 아래 마지막 액션 글자(폴드·콜·올인, `--act-*-text`), 칩 액면 9단계(`--chip-t0..t8-base/face`, 적·녹색약에서 5·25, 100·500, 5K·25K가 한 색으로 보이던 것을 주황·청록·분홍·보라·하늘색으로), 퀴즈 정답·오답의 밝은 글자(`--color-success-soft`·`--color-danger-soft`)도 모드마다 바꾼다. 퀴즈에서 고른 카드·선택지·비교 버튼과 연습 테이블의 선택지에는 ✓·✗ 원을 함께 붙여 빨강·초록만으로 정오답을 알리지 않는다. 칩 스택 옆에는 늘 금액이 적힌다. 테스트는 이웃 칩 단계(테두리·면)와 액션 글자 쌍이 시뮬레이션에서 15 이상, 폴드·콜 글자가 30 이상 떨어지는지, 글자 대비가 기준 이상인지 본다.
