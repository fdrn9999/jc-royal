## 2. 재현한 결함 (P0)

`tests/integration/tournament-hands.test.ts`의 첫 시험. 핸드 기록 없이 연 SNG를 두 사람이 끝까지 친 뒤:

- `tournaments.hands` > 0 인데 `hands`·`hand_players`에 그 테이블/회원의 줄이 0개.
- 두 사람 모두 `GET /api/players/:id/hud?scope=tournament`의 `stats.hands`가 0.

이것이 main의 모든 대회가 하는 일이고, 고친 뒤에도 플래그를 켜지 않으면 그대로다(기본 꺼짐). 가설과 판정은 `docs/V4_PLATFORM_AUDIT.md` 2절.

## 4. 리뷰 (Codex, 읽기 전용)

여덟 가지(원장 분리, 한 번만 기록, 기본 꺼짐과 배포 순서, 리플레이의 가린 카드, 대회 진행을 막지 않는가, 남은 캐시 전용 읽기, MTT 테이블 닫힘·이동, `HAND_BB` SQL)를 보게 했다.

| 지적 | 판정 | 조치 |
|---|---|---|
| `/api/me/stats`의 최고 핸드 쿼리가 대회 핸드를 뺀 조건이 없다 | 맞음(코드로 확인) | `tournament_id IS NULL` 추가, 통합 시험에 `bestHand: null` 단언 |
| api가 먼저 올라가고 플래그가 켜져 있으면 앞 버전 룸이 시작한 대회는 끝까지 기록되지 않는다 | 맞음(시험으로 재현) | 룸이 대회를 다시 읽을 때 D1의 `record_hands`를 받아들인다. 새 통합 시험 |
| 복구 알람에서 핸드 기록 재시도가 대회 동기화보다 먼저 돈다 | 맞음 | 대회 동기화·테이블 이동을 먼저 하도록 순서를 바꿨다 |
| 핸드 기록의 D1 쓰기가 룸의 직렬 큐 안에서 돈다(느린 D1이 다음 명령을 늦춘다) | 맞지만 기존 구조 | 캐시 핸드가 처음부터 같은 길이다. 이 PR에서 바꾸지 않았다(6절) |

문제없다고 본 것: 원장·지갑 쓰기 없음, 중복 없음(기본 키 + `INSERT OR IGNORE` + 룸 저장소), 리플레이가 캐시와 같은 가림 규칙, 닫힌 룸·이동한 플레이어의 미기록 핸드가 남아 다시 시도됨, `HAND_BB` SQL.

## 5. 하지 않은 것 · 확인하지 못한 것

- `pnpm test:load`: 돌리지 않았다. 이 변경은 꺼져 있을 때 핸드 경로를 바꾸지 않는다. 켰을 때 핸드당 D1 쓰기가 캐시 핸드만큼 생기는 것의 비용은 재지 않았다. 운영 대상 부하 시험은 하지 않는다.
- MTT에서의 대회 핸드 기록: 단위 시험(메타)과 코드 읽기까지다. 여러 테이블 MTT를 끝까지 돌리며 기록을 세는 통합 시험은 없다(Phase 4).
- 운영 D1에서의 마이그레이션 `0045`: 로컬 D1에서만 적용했다(통합 70회, e2e).
- 16절의 화면 크기 가운데 이 변경을 직접 본 것은 모바일(Pixel 7)과 데스크톱 1440폭 둘이다. 나머지 크기는 기존 e2e가 보는 범위 그대로다.
- 감사 문서에서 [보고]·[추정]으로 표시한 항목은 재현하지 않았다.
- 로컬에서 e2e 서버를 다른 실행 바로 뒤에 띄울 때 wrangler가 `bad port`로 마이그레이션 적용에 실패한 일이 두 번 있었다(시험이 시작되기 전). 둘 다 다시 돌리자 그대로 통과했다. 원인은 확인하지 못했다. 통합 시험(같은 마이그레이션을 70번 적용)에서는 나오지 않았다.

## 6. 남은 위험

- 핸드 기록 쓰기가 룸의 직렬 큐 안에 있다(기존 구조). 기록을 켠 대회에서 D1이 느리면 캐시 테이블과 같은 만큼 다음 핸드가 늦어진다. 실패는 대회를 막지 않고 다음 알람에 다시 시도된다.
- 플래그를 켜고 끄는 사이에 열린 대회는 열릴 때의 값으로 끝까지 간다(의도). 플래그가 켜진 채 api가 game-worker보다 먼저 올라간 사이에 친 핸드는 기록되지 않는다(지어내지 않는다).
- main 병합은 곧 운영 배포다(마이그레이션 `0045` 포함). 오너가 한다.
