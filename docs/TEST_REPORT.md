## 1. 게임 규칙 테스트 (`packages/poker-engine`)

엔진 `poker-engine-ts@0.1.3`과 JC ROYAL 어댑터를 고정 덱과 무작위 시나리오로 검증했다.

| 지시서 요구 | 테스트 | 결과 |
|---|---|---|
| 로열 플러시~하이 카드 핸드 평가 | `hand evaluation through showdown` 10건 | ✅ |
| 프리플랍~쇼다운 전체 핸드 | 위 10건 + 속성 테스트 | ✅ |
| 여러 플레이어 올인, 사이드팟 분배 | `multi-way all-in … side pots` (900/800/300) | ✅ |
| 무승부·홀수 칩 | `split pot … odd chip` (25 → 12/13) | ✅ |
| 최소 레이즈 | `minimum raise is one big blind …` | ✅ |
| 숏 올인 재오픈 제한 | `a short all-in does not reopen raising …` | ✅ |
| 헤즈업 규칙 | `heads-up: button posts SB and acts first preflop …` | ✅ |
| 턴 종료(타임아웃) | `turn timeout checks when free and folds when facing a bet` | ✅ |
| 정확한 칩 정산 | 모든 규칙 테스트 + 속성 테스트의 보존 검사 | ✅ |
| 블라인드 올인 | `a player who cannot cover the big blind posts all-in …` | ✅ |
| 이벤트 재생·상태 복원 | `restores from a JSON-serialised log mid-hand …` | ✅ |
| 속성 기반 테스트 | 무작위 2,000 + 2,000핸드(2·6·9석, 스택 1~3000) | ✅ |

**속성 테스트 불변식**(매 액션마다 검사):

- 칩 총량 보존, 음수 스택 없음
- 핸드가 항상 정산까지 진행
- 무작위 시점의 로그 복원 상태가 원본과 동일
- 다른 플레이어 홀카드 비노출
- 정산 합계 = 팟, 순손익 합계 = 0

폴드 회피 실행 기준 커버리지는 2,000핸드 전부 쇼다운 도달, 사이드팟 실지급 1,835건, 정체 해소 127건이다.

**테스트로 발견한 엔진 결함 3건**(상세는 `docs/ENGINE_NOTES.md`):

1. 블라인드 기여액 미기록(과다 청구)
2. BB 옵션 소실 — 패치로 수정. 패치를 되돌리면 테스트가 실패하는 것을 대조 실험으로 확인했다.
3. 블라인드 올인 시 핸드 정지

## 6. 알려진 한계

- 10인 테이블은 엔진 미지원이라 최대 9석이다.
- 가입 인증·비밀번호 재설정 메일은 Resend로 보낸다(2026-10-15 운영 배포). 자동 테스트는 메일 본문 생성과 Resend 요청 형식(가짜 fetch, `apps/api/src/lib/mail.test.ts`)까지이고, 운영 메일함 도착은 테스트하지 않았다.
- 부하 시나리오는 로컬 workerd에서만 수행했다(최대 30테이블·소켓 300개, 아래 "부하 시나리오"와 `docs/LOAD_TEST.md`). 로컬 workerd는 Cloudflare 엣지 성능을 대표하지 않으며, 엣지·운영 환경 부하 테스트는 하지 않았다.
- 로컬 `wrangler dev`에서는 서버가 닫은 소켓이 클라이언트에서 CLOSING 상태로 남는다(서버 쪽 동작은 정상, 테스트에 명시).

### E2E 간헐 실패와 하네스 수정

전체 E2E에서 데스크톱 22번째 테스트 `social.spec.ts`(친구 요청·수락·1:1·읽음 표시)가 두 번 90초 시간 초과로 실패했다. 한 번은 페이지 스크린샷에서, 한 번은 두 번째 회원 가입의 `/register` 이동에서 멈췄다. 그 테스트만 돌리면 5/5 통과했다.

- **원인:** `signUp`(그리고 `admin.spec`·`academy-followups.spec`)이 `browser.newContext()`로 연 컨텍스트를 닫지 않았다. 워커 하나가 브라우저 하나로 전체를 돌리므로, 22번째 테스트 시점에 앞선 21개 테스트의 페이지 33개가 살아 있었다(실패 트레이스 두 개 모두 페이지 35개, 실패 스크린샷 34장). 이 페이지들은 로비·1:1·안 읽음 폴링, 테이블 WebSocket과 25초 핑을 계속 보냈다(트레이스에 이전 테스트 `reconnect.spec.ts`의 핑 전달이 찍혀 있다).
- **근거:** 두 번째 실패에서 `/register` 문서는 서버가 11 ms 만에 200으로 응답했다. 그런데 같은 페이지의 CSS·JS 요청이 Chrome 안에서 `net::ERR_INSUFFICIENT_RESOURCES`로 실패해 load 이벤트가 오지 않았다. 서버가 아니라 브라우저 자원 고갈이다.
- **수정:** `tests/e2e/helpers.ts`의 `test`에 자동 픽스처를 두어, 테스트가 연 컨텍스트를 테스트가 끝날 때 닫는다. 컨텍스트를 직접 여는 spec 16개가 이 `test`를 쓴다(import만 변경). 단언과 시간 제한은 바꾸지 않았다.
- **확인:** 수정 후 전체 E2E를 돌리며 테스트마다 시작 시점에 열린 컨텍스트 수를 찍었다(임시 로그, 확인 후 제거). 이 `test`를 쓰는 31개 테스트 모두 0개였고, 34/34 통과(5.6분, 수정 전 실패한 실행은 7.3분). 로그를 뺀 최종 실행: 34/34 통과(5.7분).
- **배제한 가설:** 앱 메인 스레드 무한 루프(멈춘 페이지의 폴링은 계속 정상), S8 회귀(앱 코드 변경 없음, 단독 5/5 통과), 서버 지연(문서 응답 11 ms). 첫 실패 직후에는 "백그라운드 페이지의 캡처 정지"로 보았지만, 두 번째 실패의 자원 오류와 두 트레이스의 페이지 수를 보고 근본 원인을 누수로 고쳤다.

### 이번 작업에서 찾아 고친 문제

- 최대 팟(`MAX(won)`)과 승리 수·총 획득이 돌려받은 미콜 칩까지 셌다. 한 핸드에서 진 사람도 자기 칩을 돌려받으면 '승리'로 집계됐다.
- 로비 카드의 이동 버튼이 만석·관전 불가 테이블에서도 관전으로 보냈다.
- 로비 목록 쿼리가 `status <> 'closed'`로 전체를 훑었다. `IN`과 인덱스로 바꿨다.
- 숨긴 탭에서도 로비를 폴링했고, 겹친 요청의 오래된 응답이 나중 응답을 덮을 수 있었다.
- 모바일 로비에 방 만들기 버튼이 두 개였다.
- 원장 처리 결과가 'duplicate'일 때 칩을 다시 더하던 문제, 차감 중 멈춘 좌석이 충전을 막던 문제.
- 통계 추이 차트가 순손익 0인 날을 표시하지 않았고, 모든 값이 0이면 기준선이 위 끝에 붙었다.
- 진입 번들이 675KB로 한도(650KB)를 넘었다. 마이페이지·게시판을 지연 로딩으로 분리했고, 번들 가드가 진입 파일과 함께 미리 받는 공용 청크까지 합산하도록 고쳤다.
- 통합 테스트의 DB 직접 실행 도우미(`tests/support/d1.ts`)가 워커의 쓰기와 겹치면 `SQLITE_BUSY`로 실패했다(전체 실행 중 1회). 쓰기 부하를 걸어 25회 중 15–16회 실패로 재현했고, 실패한 배치는 행을 남기지 않음을 확인한 뒤 `SQLITE_BUSY`일 때만 재시도하게 했다. 수정 후 같은 부하에서 25/25 성공, 중복 행 없음.
- (Codex 적대적 리뷰 지적) 충전 복구가 이미 반영된 충전을 다시 더할 수 있었다. 룸은 최근 `reqId` 200개만 기억한다. 그보다 오래된 충전 요청이 다시 오면 원장에 이미 있는 키로 '차감 중' 표시를 저장했고, 그 D1 호출이 실패하거나 룸이 재시작하면 복구가 "원장에 있음 = 아직 안 더함"으로 보고 칩을 한 번 더 더했다. 테스트 프로세스가 D1 쓰기 잠금을 잡은 상태로 재전송해 재현했다(일어선 뒤 지갑 10,200, 기대 10,000, 원장 차감은 200 한 번). 원장에 이미 있는 키는 '차감 중'으로 표시하지 않고(이미 반영된 요청으로 보고 `ack`만), 복구는 원장이 실제로 차감한 금액만 더하도록 고쳤다. 원장 확인이 표시보다 먼저라 D1이 실패하면 아무것도 남기지 않는다. 최종 테스트는 수정 전 코드에서 D1 복구 뒤 재전송 시 스택 700(기대 500)으로 실패하고, 수정 후 통과한다.

### PART A에서 찾아 고친 문제

- **A1**: D1은 '종료 중'인데 룸이 종료 호출을 받지 못하면 방이 계속 열려 있었다. 종료 중 D1 쓰기가 실패하면 환급과 핸드 기록이 로그만 남기고 버려져 칩이 테이블에 묶였다. 방 깨우기·설정 변경·종료 호출이 실패해도 API는 성공으로 답했다.
- **A2**: 참가 코드가 페이지 주소와 WebSocket 주소에 그대로 실렸다. 코드를 바꿔도 이전 코드로 들어온 대기 명단과 연결이 남았다.
- **A3**: 연결이 끊기면 기다리던 요청을 모두 실패로 처리해, 룸이 이미 처리한 바이인도 화면에는 오류로 떴다. 요청에 시한이 없었고, 자리 비움·대기열·채팅·액션에는 성공 응답이 없었다. 25초마다 무조건 보낸 ping을 룸이 직접 답해 잠든 룸을 매번 깨웠다.
- **A4**: 핸드마다 도는 통계 SQL이 `hand_players` 전체를 훑었다. 결과를 D1 기록 뒤에 보내 핸드를 끝낸 액션의 응답이 D1만큼 늦었다. 띄워만 둔 로비가 5초마다 목록을 불렀다.
- **A5**: 사전 액션·쇼다운 머크·단계별 리플레이가 없었다. 쇼다운에서 진 패를 포함해 모든 패가 공개됐다. 핸드 기록에 딜러 버튼과 팟별 정산이 없었다.

### 찾아 고친 문제

- 첫 전체 통합 실행이 135/136이었다. `warns about …`에서 '종료 중' 테스트 테이블이 바쁜 테이블 목록(12개)에 없었다.
  - 가설 1(행이 안 들어감): 같은 테스트의 '오래 종료 중' 경고 검사가 통과해 기각.
  - 가설 2(상태 조건이 '종료 중'을 뺌): 문장의 `WHERE status IN ('open','closing')`로 기각.
  - 가설 3(목록이 이미 참): 실행 끝의 테스트 DB에 사람·연결이 있는 열린 테이블이 36개였고, 정렬이 연결 수 → 착석 수뿐이라 '종료 중' 테이블(연결 0)이 밀려남. 확인.
  - 고침: 종료 중 테이블을 먼저 정렬(`ORDER BY status = 'closing' DESC, …`). 바쁜 열린 테이블 13개를 넣는 검사를 더해, 예전 정렬에서 실패(`expected -1 to be greater than or equal to 0`)하고 고친 뒤 통과함을 확인했다. 전체 통합 136/136.
- 닫힌 테이블에 남은 착석 세션을 찾는 문장의 실행 계획이 닫힌 테이블(계속 늘어남)부터 훑었다. `CROSS JOIN`으로 착석 세션 부분 인덱스에서 시작하게 했다(`SCAN ts USING COVERING INDEX tsess_open_user_uq` → `SEARCH t USING sqlite_autoindex_tables_1`).

### 찾아 고친 문제

- 정합성 이벤트 중복(위 재현). 가설: 검사가 지급과 경쟁(기각: 순차 실행, 값 일치), 목록이 200건만 읽음(기각: 이벤트 6건뿐), 중복 판정 키에 기대·실제 값이 들어감(채택). 키를 `범위:대상:차이`로 바꾸고, 지갑 이상은 열린 이벤트와 메모로 닫은 이벤트를 모두 같은 이상으로 본다. 테이블 이상은 열린 이벤트만 같은 키로 본다(좌석 차이는 정리되면 사라지므로, 메모로 닫은 뒤 다시 생기면 새 이벤트).
- 정정 결과 문구가 사라졌다. 정정에 성공하면 이벤트가 열린 목록에서 빠지며 그 줄의 증거 패널과 결과 문구가 함께 없어졌다. 성공 문구를 페이지 위(`rec-result`, 회원 닉네임과 처리 종류 포함)로 옮기고, 거절은 증거 옆에 남긴다.
- 통합 테스트 작성 중: 같은 테이블에 같은 회원을 두 번 앉히는 픽스처가 `UNIQUE(table_id, user_id)`에 걸려 두 번째 회원을 쓰고, 정리 순서를 착석 → 테이블로 바꿨다(외래 키).
- 화면 확인에서 칩 경제 화면이 390px에서 가로로 308px 넘쳤다(한·영 모두, 페이지 폭 698px). 가설: 차트 막대 수(기각: 막대는 `min-w-0 flex-1`이고 기본 7일 화면에서도 넘침), 합계 카드의 긴 숫자(기각: 카드 grid는 `grid-cols-2`로 열이 정해져 있고, 카드를 건드리지 않은 수정 뒤 넘침 0), 흐름 표·차트를 담은 grid에 열 지정이 없음(채택: lg 미만에서 암묵적 `auto` 열이 표의 최소 폭 640px까지 늘어남). `grid-cols-1`(minmax(0, 1fr))로 바꿔 표가 패널 안에서 스크롤되게 했다. 같은 확인에서 데스크톱 1440px도 두 칸이 같은 폭이라 흐름 표의 마지막 열이 잘려, 가장 넓은 화면(xl)에서만 3:2로 나누고 그보다 좁으면 위아래로 놓았다.
- 390px 정합성 화면에서 열린 증거 패널이 표의 최소 폭을 따라가 오른쪽 카드와 처리 버튼이 잘렸다(표 안 가로 스크롤로만 보임). 표를 감싼 요소를 크기 기준 컨테이너로 두고, 증거 줄은 보이는 폭에 맞추고 왼쪽에 붙게(`sticky`) 했다.
- 지갑 합계 카드의 '정지 회원 0 · 운영진 20,000'이 사람 수처럼 읽혔다(실제로는 그 계정들이 가진 칩). '정지 회원 보유 · 운영진 보유'로 고쳤다.

## B5 공지·점검 (2026-10-15)

## B6 신고·제재 워크플로 (2026-10-15)

신고 접수, 해결·기각, 같은 대상 신고 함께 닫기, 콘텐츠 숨김, 동시 처리 원자성(감사 행을 먼저 쓰는 claim)은 그대로 두고 다시 쓴다. 그 위에 심각도·담당자, 처리 기록·내부 메모, 결과 안내, 목록 필터·정렬·페이지, 참고 통계, 신고와 정지의 연결을 더했다. 신고 수·통계로 회원 상태를 바꾸는 경로는 만들지 않았다. 정지는 관리자가 증거를 보고 재확인과 사유를 거쳐 직접 준다.

- 반복 피신고 집계가 기간과 상관없이 신고 전부를 읽었다: 커밋 전 쿼리 계획(`node:sqlite`, 마이그레이션 0000~0017 적용)을 보니 `SCAN r USING INDEX reports_target_user_idx`로, SQLite가 묶기 정렬을 아끼려고 피신고 회원 순서로 모든 신고를 훑었다. 가설 셋을 봤다. (1) 기간 인덱스가 없음 — 기각, `reports_created_idx`가 있고 사유·대상 종류 집계는 그것을 쓴다. (2) 조인 순서 때문에 users부터 읽음 — 기각, 계획의 바깥 루프가 reports였다. (3) GROUP BY와 같은 순서의 인덱스를 고르는 계획 선택 — 채택. 기간 안의 신고를 `MATERIALIZED` CTE로 먼저 뽑게 바꿔 `SEARCH reports USING INDEX reports_created_idx (created_at>?)`가 됐다. 같은 계산의 합성 데이터(신고 50,000건, 7일 안 992건)에서 결과는 같고(20행 일치) 중앙값 3.16 → 1.13 ms. 로컬 D1(workerd)이 이 문법을 받는 것과 `reports-workflow.test.ts` 5/5를 다시 확인했다. 로컬 D1은 읽은 행 수를 주지 않아 D1 읽은 행 감소(약 50,000 → 약 1,000)는 실행 계획에서 추정한 값이다.
- 기존 통합 테스트 1건 실패: `social.test.ts`의 '다른 신고 수' 단언이 `{ total: 1, resolved: 0 }`과 정확히 같은지 봤는데 `reporters: 1`이 더해져 실패했다. 가설 셋을 봤다. (1) 응답에 필드를 더해 정확 일치 단언이 깨짐 — 채택. (2) 다른 신고 수 계산이 바뀜 — 기각, `total`·`resolved` 값은 같았다. (3) 다른 신고를 집어 옴 — 기각, 같은 신고 ID였다. 단언에 `reporters: 1`을 더했고 다시 돌려 15/15.

## B7 관리자 권한·감사 (2026-10-16)

관리자 콘솔의 분리 세션(별도 쿠키·SameSite=Strict·출처 검사), 매 요청 D1에서 읽는 역할 판정, 비밀번호 재확인은 그대로 두었다. 그 위에 라우트마다 하나인 권한 표, 서버가 계산하는 변경 미리보기, 실패한 관리자 요청의 감사, 감사 로그 검색·페이지, 관리자 세션 보기·종료를 더했다. WebAuthn·USB 보안 키는 다시 넣지 않았다. 진행 중인 핸드의 다른 회원 홀카드나 덱을 보는 기능은 만들지 않았다.

### 찾아 고친 문제

- 기존 통합 테스트 `admin.test.ts`의 내보내기 테스트가 일반 관리자로 내보내던 흐름이라, 내보내기를 최고관리자 전용으로 바꾸면 깨진다. 일반 관리자는 재확인 뒤에도 403을 받는지 확인하도록 바꾸고, 성공 경로는 새로 만든 두 번째 최고관리자로 확인했다. 공용 최고관리자로 다시 로그인하면 계정당 로그인 횟수 제한(15분 5회)에 걸리기 때문이다.
- 새 E2E가 단독으로는 통과했지만 전체 순서에서 `admin.spec.ts`가 409 `a super admin already exists`로 실패했다. 가설 셋을 봤다. (1) 부트스트랩 토큰 불일치 — 기각, 토큰이 틀리면 403이고 409는 최고관리자가 이미 있을 때만 나온다(`admin-auth.ts`). (2) 이전 실행의 상태가 남음 — 기각, `server.mjs`가 실행마다 상태를 지운다. (3) 파일 이름 순서로 새 spec(`admin-security.spec.ts`)이 먼저 돌아 SQL로 최고관리자를 만들어 둠 — 채택. 새 spec을 `security.spec.ts`로 바꿔 `admin.spec.ts` 뒤에 돌게 했고, 두 파일을 함께 돌려 3/3을 확인했다.
- 실행 계획 확인에서 문서의 "본문 검색만 전부 읽는다"가 틀린 것을 찾았다. 조치 묶음(`user.*`)도 인덱스로 범위만 좁히고 묶음의 행을 모두 읽어 정렬한다(`USE TEMP B-TREE FOR ORDER BY`). 쿼리는 그대로 두고 문서와 주석을 고쳤다(아래 성능·비용).
- 전체 통합 테스트에서 `social.test.ts` "admins handling the same report at once"가 이 신고의 감사 행을 1개가 아니라 3개 받아 실패했다(178/179). 가설 셋을 봤다. (1) 동시 처리 가드가 깨져 결정이 여러 번 들어감 — 기각, 같은 테스트의 앞 단계(200 한 건, 409 `report_closed` 두 건, 두 신고에 같은 결정)가 통과했다. ## B8 운영 통계 (2026-10-16)

기존 운영 대시보드(지금 이 순간의 수치와 최근 1시간 추이)는 그대로 두고, 날짜별 추이를 보는 "운영 통계" 화면(`/stats`)과 API(`GET /api/admin/stats`)를 더했다. 가입·좌석·핸드·신고는 이미 있는 기록에서 하루에 한 번 집계한다. 날짜별 기록이 없던 활동 회원과 아카데미 진행만 최소한의 서버 기록을 새로 두었다. 외부 분석 도구, 쿠키, 추적 스크립트, 차트 라이브러리는 넣지 않았다.

### 수정 전 상태

| 항목 | 수정 전 코드 |
|---|---|
| 운영 추이 | 대시보드는 지금 값(온라인 회원, 진행 중 핸드 등)과 누적 현황, `ops_metrics`의 5분·1시간 오류 추이(14일 보관)만 보여 줬다. 날짜별 수치를 돌려주는 API·화면이 없었다 |
| 활동 회원 | 날짜별 활동 기록이 없었다. `sessions.last_seen_at`은 세션마다 마지막 사용 시각 하나, `users.last_login_at`(B3)은 마지막 로그인 하나라 지난 날의 활동 회원 수를 셀 수 없었다 |
| 아카데미 | `academy_stats`는 회원 ID 없는 항목별 누적 카운터라 날짜별 시작·완료를 셀 수 없었다 |
| 게임·동시접속 | 핸드(`hands.ended_at`, `hands_table_idx`)와 좌석(`table_sessions`의 앉은·일어난 시각)은 있었지만, 닫힌 좌석을 일어난 시각으로 찾는 인덱스가 없었다. 사이트 접속 기록은 없다 |
| 신고 처리 시간 | B6 신고 통계(최근 7·30·90일 합계, 참고용)뿐이고 기간별 추이는 없었다 |

### 설계

- 집계 구조(마이그레이션 0019): `daily_stats(day, metric, n)`은 날짜·지표별 숫자 하나, `active_days(day, user_id)`는 회원이 활동한 날(하루 1행). 날짜는 한국 시간 자정 기준이다. 닫힌 좌석용 부분 인덱스 `tsess_closed_idx`를 더했다.
- 활동 기록: 로그인(세션 생성)과 날이 바뀐 뒤 첫 요청에서 `INSERT OR IGNORE` 한 번(`waitUntil`, 실패해도 요청은 성공하고 로그만 남는다). 시각·IP·화면·기기는 남기지 않는다. 35일 보관(집계가 밀리면 최대 60일), 탈퇴 시 삭제.
- 아카데미: 기존 이벤트 기록 batch에 날짜별 카운터(`ac_*`: 레슨·시나리오 시작·완료, 퀴즈 답·정답)를 더한다. 회원 ID는 없다.
- 집계: 매일 cron이 정리 작업 전에 끝난 날을 한 번에 최대 372일(31일 × 12) 집계하고, 화면을 열 때 빠진 날이 있으면 31일만 먼저 채운다. 하루를 통째로 계산해 통째로 바꾸므로 cron과 화면이 동시에 돌거나 같은 날을 다시 집계해도 같은 값이 된다. 첫 실행은 첫 가입일부터(최대 366일 전) 시작한다.
- 지표:
  - 활동 회원: 그날 활동 기록 수(DAU), 그 전에 가입한 회원(재방문), 그날로 끝나는 7·30일의 고유 회원(WAU·MAU). 주·월 단위는 DAU 일 평균과 기간 마지막 날의 WAU·MAU다.
  - 첫 게임 참여율: 가입일 묶음별로 가입 후 24시간·7일 안에 좌석에 앉은 비율. 7일이 지나야 확정되므로 그 뒤에 가입일에 기록한다.
  - 게임: 끝난 핸드 수와 핸드가 있던 테이블 수(공식·회원 방별), 평균 착석 시간(일어난 좌석의 앉은 시간), 시간마다 동시에 열린 좌석의 최대값(좌석 시작·끝을 훑어 계산).
  - 신고: 접수일별 접수 수, 처리일별 처리 수와 처리 시간.
- 화면: 일·주·월(기본 30·12·12개, 주소에 남음) 단위, 요약 수치, CSS 막대 그래프 4개, 공식·회원 방 비중(핸드·착석·착석 시간), 아카데미, 시간대별 동시 착석, 기간별 표, 기준 안내. 집계 전 날짜는 0이 아니라 "집계 전"으로, 활동 기록이 시작되기 전 날짜가 섞인 값은 `*`로 표시한다.

### 성능·비용

- 합성 데이터(120일, 회원 5,000명, 좌석 15만, 핸드 60만, `node:sqlite`에 마이그레이션 0000~0019 적용, 실제 집계·화면 코드를 D1 흉내 계층으로 실행): 첫 집계 120일 1,022 ms(31일씩 4번), 하루 집계 10.5 ms, 집계할 날이 없을 때 0.1 ms, 화면 응답 일 90개 8.7 ms·주 26개 7.7 ms·월 12개 11.7 ms, 좌석 15만 개 동시 착석 계산 102.5 ms, 정리 작업 0.8 ms.
- 실행 계획: 화면은 `daily_stats` 기본 키 범위 한 번만 읽는다. 하루 집계는 핸드를 `hands_table_idx`, 닫힌 좌석을 새 `tsess_closed_idx`, 접수 신고를 `reports_created_idx`, 활동 기록을 기본 키 범위로 찾는다. `users`·`tables` 전체와 결정된 신고 전체(처리 시각 인덱스 없음)는 하루 집계마다 한 번씩 읽는다. 로컬 D1은 읽은 행 수를 주지 않아, 하루 활동 회원 1,000명일 때 하루 집계가 읽는 행은 약 4만5천 행으로 추정한다.
- 쓰기: 회원마다 하루 첫 요청에 D1 쓰기 1회(활동 기록), 아카데미 이벤트 batch에 문장 1개, 하루 집계마다 지표 행 수십 개(합성 데이터에서 하루 43행)가 늘어난다. 핸드 인덱스는 새로 만들지 않았다.
- 게임 서버·지갑·원장 코드는 바꾸지 않아 부하 테스트는 돌리지 않았다.

### 테스트하지 않은 것

- 운영 규모(회원 수십만 명, 1년치 좌석)에서 D1의 실제 집계 시간과 읽은 행 수. 첫 따라잡기 집계의 CPU 시간은 로컬 합성 데이터로만 쟀다.
- 집계가 하루 넘게 밀렸을 때 활동 기록 삭제 기준이 늘어나는 경로(cron은 집계를 먼저 돌리므로 테스트에서는 밀리지 않는다. 계산식만 검토).
- 자정을 넘겨 테이블 WebSocket에만 머무는 회원(API를 부르지 않으면 그날 활동으로 남지 않는다).
- 배포 중간 상태(0019 없이 새 api, 이전 api와 새 admin).
- 테스트가 한국 시간 자정을 넘겨 실행되는 경우(통합·E2E의 날짜 창이 실행 중 바뀌지 않는다고 가정).
