# 플랫폼 실시간(`/ws/realtime`)

로그인한 페이지가 테이블 밖에서 여는 소켓 하나다. 칩 지급, VIP, 친구·1:1 메시지, 쪽지, 로비 테이블, 토너먼트, 공지·점검이 바뀌면 새로고침 없이 화면에 반영된다. 테이블 소켓(`/ws/tables/:id`, `docs/WEBSOCKET_PROTOCOL.md`)은 바꾸지 않았다.

프로토콜 타입은 `packages/types/src/realtime.ts`, 허브는 `apps/game-worker/src/realtime.ts`(규칙은 `realtime-rules.ts`), 핸드셰이크는 `apps/api/src/routes/realtime.ts`, 발행은 `apps/api/src/lib/realtime.ts`와 `apps/game-worker/src/realtime-publish.ts`, 페이지 쪽은 `apps/web/src/lib/realtime.ts`다. 부하 측정은 `docs/LOAD_TEST.md` 6절.

## 1. 원칙

- **D1과 테이블 룸이 진실이다.** 이벤트는 "무엇이 바뀌었다"만 알린다. 페이지는 API로 다시 읽는다. 공개 숫자(로비 카드의 인원 등)만 이벤트에 그대로 들어 있다.
- **이벤트로는 아무것도 실행되지 않는다.** 칩, 좌석, 상태를 바꾸는 이벤트는 없다. 페이지가 보낼 수 있는 것은 받고 싶은 공개 토픽(`{"t":"sub","topics":[…]}`)뿐이다. 그 밖의 프레임은 읽지 않는다(통합 테스트 "nothing a page sends is published or changes anything").
- **금액을 싣지 않는다.** `wallet.changed`에는 금액이 없다. 페이지는 `/api/auth/me`를 다시 읽는다(`balance += amount` 같은 계산은 없다).
- **개인·공개를 나눈다.** 개인 이벤트(`scope: 'user'`)는 그 회원의 소켓에만 간다. 허브는 `users` 없는 개인 이벤트와 `users`가 붙은 공개 이벤트를 400으로 거절한다. 공개 이벤트에는 모든 회원이 볼 수 있는 값만 넣는다.
- **발행은 D1 쓰기가 커밋된 뒤, 백그라운드에서 한다.** 발행이 실패해도 요청은 실패하지 않고, 지급·정산을 다시 하지 않는다.
- **이벤트는 사라질 수 있다.** 재연결하면 다시 읽고, 소켓이 열려 있는 동안에도 느린 폴링을 안전망으로 남긴다(7절).
- **Web Push와 별개다.** 이 소켓은 열려 있는 페이지의 화면 동기화만 한다. 푸시 동의·설정·발송(`notification_events`)은 바꾸지 않았고, 이 소켓 때문에 새로 보내는 푸시는 없다. 푸시를 꺼도 실시간 동기화는 그대로 된다.

## 2. 구조

```
페이지 ──wss /ws/realtime──▶ API Worker ──(세션 확인, Origin, 속도 제한)──▶ RealtimeHub rt-<shard>  (game-worker의 DO)
                                                                              ▲            ▲
                       API 라우트(지급, VIP, 친구, 쪽지, 방, 공지 …) ── publish ┘            │
                       테이블 룸(TableRoom: 좌석·관전 수, 바이인·캐시아웃, 토너먼트) ── publish ┘
```

- **허브는 `RealtimeHub` Durable Object다.** 이름은 `rt-0 … rt-3`이다. 회원의 소켓은 `realtimeShardOf(userId)`(FNV-1a, `REALTIME_SHARDS = 4`) 허브에 붙는다.
- **개인 이벤트**는 그 회원의 허브 하나에만 간다. 허브는 소켓 태그 `u:<userId>`로 그 회원의 소켓만 찾는다. 한 번에 500명까지 묶는다.
- **공개 이벤트**는 허브 4개에 한 번씩 간다. 보는 사람이 몇 명이든 발행자의 허브 요청은 4개다.
- **PresenceHub(`hub-0`)는 쓰지 않는다.** 접속 표시용 단일 객체라 모든 이벤트를 몰면 병목이 된다. 접속 표시는 그대로 두었다(`docs/PRESENCE.md`).
- **회원마다 DO를 두지 않았다.** 그러면 개인 이벤트마다 그 회원의 객체를 깨워야 하고, 공지 하나가 회원 수만큼의 요청이 된다. 샤드 허브는 소켓이 없는 회원에게 보낼 때도 그 허브 하나만 깨운다.
- **샤드 수 4는 시작값이다. 측정으로 정하지 않았다.** 로컬에서는 허브 4개가 한 프로세스라 허브 하나의 한계를 잴 수 없다(`docs/LOAD_TEST.md` 6.2). DO 하나가 최대 약 32,000개 소켓을 하이버네이션으로 들고 있을 수 있다는 Cloudflare의 안내에 맞춰, 허브당 상한은 16,000개로 두었다. 배포 뒤 허브 하나의 CPU 시간과 팬아웃 지연을 재고 정한다. 값을 바꾸면 api와 game-worker를 함께 배포해야 하고, 그때 모든 소켓이 다시 연결된다.

## 3. 연결과 인증

`GET /ws/realtime`(API Worker, `realtimeSocket`):

1. `Upgrade: websocket`이 아니면 426.
2. **Origin**이 사이트 자신이나 `ALLOWED_ORIGINS`가 아니면 403(교차 사이트 소켓 차단, 테이블 소켓과 같다).
3. **세션 쿠키**를 `resolveSession(c, 'user', { touch: false })`로 확인한다. 없거나 만료됐거나, 계정이 활성이 아니면 401.
   - 관리자 콘솔 세션(`kind = 'admin'`)으로는 열리지 않는다.
   - `touch: false`: 열린 페이지가 세션 만료를 늦추지 않는다.
4. 회원·IP마다 1분에 30회까지(`rt-ws:<user>:<ip>`).
5. API가 확인한 `{ userId, sessionId, authAt, expiresAt }`를 내부 헤더(`x-jc-identity`)에 넣고, `x-jc-internal`(INTERNAL_SECRET)과 함께 허브로 넘긴다. **페이지는 자기가 누구인지 말하지 않는다.** 브라우저가 보낸 같은 이름의 헤더는 덮어쓰이고, 허브는 내부 비밀값이 없는 요청을 403으로 거절한다.

허브(`open`):
- 최근 1분 안의 로그아웃(`REVOKE_WINDOW_MS`, 시계 차이 2초 허용)보다 먼저 확인된 핸드셰이크는 4401로 닫는다. 로그아웃 직전에 확인된 연결이 늦게 도착하는 경우다.
- 회원당 10개(`REALTIME_MAX_PER_USER`)를 넘으면 가장 오래된 소켓을 4008로 닫는다. 허브당 16,000개(`REALTIME_MAX_PER_HUB`)를 넘으면 1013으로 거절한다.
- 받은 소켓은 `ctx.acceptWebSocket`(하이버네이션)으로 들고, 신원과 토픽은 `serializeAttachment`에 둔다. 그 뒤 `{"t":"hello","v":1}`을 보낸다.
- `{"t":"ping"}`은 `setWebSocketAutoResponse`가 `{"t":"pong"}`으로 답한다. 허브를 깨우지 않는다. 페이지는 45초마다 ping을 보내고, 10초 안에 답이 없으면 소켓을 닫고 다시 연다.
- 페이지가 1분에 31번째 프레임을 보내면 1008로 닫는다(`FRAMES_PER_MIN`). 200자를 넘거나 `sub`가 아닌 프레임은 무시한다.

### 소켓이 닫히는 경우

| 코드 | 언제 | 페이지 |
|---|---|---|
| 4000 `reauth` | 핸드셰이크 후 1시간(`REALTIME_MAX_AGE_MS`), 또는 세션 만료 시각이 지났을 때. 발행이나 알람 때 확인한다 | 1초 안에 다시 연결한다(API가 세션을 다시 확인한다) |
| 4401 `signedOut` | 로그인이 끝났을 때(아래) | 계정을 다시 읽는다. 로그아웃이면 그 페이지도 로그아웃 상태가 된다 |
| 4008 `tooMany` | 그 회원의 11번째 페이지가 열렸을 때 가장 오래된 것 | 다시 연결하지 않는다. 그 페이지로 돌아오면(보이게 되면) 다시 연다 |
| 1008 | 프레임이 너무 많을 때 | 백오프로 다시 연결한다 |
| 1013 | 허브가 가득 찼을 때 | 백오프로 다시 연결한다 |
| 그 밖 | 네트워크, 배포, 허브 재시작 | 1, 2, 5, 10, 20, 30초 백오프(±50%)로 다시 연결한다. 탭이 다시 보이거나 온라인이 되면 바로 시도한다 |

**로그인이 끝나는 경우**: 로그아웃, 다른 기기 로그아웃(그 기기는 남는다), 비밀번호 변경·재설정, 관리자의 강제 연결 종료와 정지, 탈퇴. 모두 `apps/api/src/lib/signout.ts`의 `signedOut()`을 지난다. 세션 행을 지운 뒤 허브에 `/revoke`를 보낸다. 실패하면 한 번 더 보낸다.

**revoke가 끝내 닿지 않으면**: 허브는 소켓이 열려 있는 동안 5분(`SWEEP_MS`)마다 알람에서 D1을 한 번 읽는다(`liveSessionsSql`). 그 허브 소켓들의 세션 id를 100개씩 묶어 한 batch로 보내고, D1에 더 이상 없는 세션(또는 활성이 아닌 계정, 회원 세션이 아닌 것)의 소켓을 4401로 닫는다. 그래서 끝난 로그인의 소켓은 최대 약 5분 열려 있다. 그동안 받는 것은 내용 없는 알림뿐이다. 그 알림을 보고 다시 읽어도 끝난 세션이라 API가 거절한다. D1을 못 읽은 알람은 아무것도 닫지 않고 30초 뒤 다시 시도한다(`SWEEP_RETRY_MS`). 그래도 1시간이 지나면 4000으로 닫힌다. 메시지마다 D1을 읽지는 않는다. 새 소켓은 허브의 다음 알람이 한 주기보다 멀면 그 알람을 당긴다(`sweepAlarmFor`). 소켓 없는 허브에 닿은 로그아웃은 기록을 지우려고 알람을 1분 뒤로 잡는데, 주기가 그보다 짧은 통합 테스트에서는 그 사이 열린 소켓이 첫 확인을 1분까지 기다렸다(68.7초 재현, `docs/TEST_REPORT.md`). 운영 주기(5분)에서는 그런 알람이 더 이른 쪽이라 바뀌는 것이 없다.

**관리자 역할 회수**: 이 소켓은 회원 세션으로만 열리고 관리자 데이터를 보내지 않는다. 관리자 콘솔은 이 소켓을 쓰지 않는다(9절).

## 4. 이벤트

모든 이벤트는 `{ type, eventId, scope, occurredAt, resourceId?, revision?, payload? }`이고 zod 판별 유니언(`RealtimeEventSchema`)으로 검사한다. 허브는 발행 때, 페이지는 받을 때 검사한다. 페이지가 모르는 이벤트(새 서버)는 무시한다. 프로토콜 버전은 `REALTIME_PROTOCOL = 1`이고 `hello`에 실린다.

| 이벤트 | 범위 | 발행처(D1 커밋 뒤) | 받는 쪽 | 내용 | 페이지 처리 | 놓쳤을 때 |
|---|---|---|---|---|---|---|
| `wallet.changed` | 개인 | 관리자 칩 지급·차감(`POST /api/admin/users/:id/chips`), 관리자 정합성 정정, 무료 리필, 추천 보상, 테이블 바이인·캐시아웃·충전(룸) | 그 회원 | 없음 | 헤더 잔액: `/api/auth/me` 한 번(묶음). 내 정보: 잔액·원장 다시 읽기 | 재연결 때 다시 읽기. 탭 포커스 때 계정 읽기 |
| `account.changed` | 개인 | 프로필 저장, VIP 지정·해제·색 변경, 역할 변경 | 그 회원 | 없음 | `/api/auth/me` 한 번 | 재연결 때 다시 읽기 |
| `message.changed` | 개인 | 쪽지 읽기·삭제(내 다른 기기), 관리자 쪽지, 칩 지급 안내, 신고 처리 결과, 설정 초기화·복원 안내 | 그 회원들 | 많은 회원에게 보낼 때 `spreadMs` | 안 읽은 수(쪽지 화면이면 목록)를 무작위 대기 뒤 읽기 | 재연결 때, 120초 폴링 |
| `social.friend.changed` | 개인 | 친구 요청·수락·거절·취소·삭제, 차단 | 양쪽 회원 | 없음(무엇이 바뀌었는지 말하지 않는다) | 친구 목록·받은 요청 수 다시 읽기, 열린 대화는 그 `seq` 뒤를 읽어 아직 보낼 수 있는지 | 재연결 때, 60초(대화는 30초) 폴링 |
| `social.dm.created` | 개인 | 1:1 메시지(테이블 초대 포함) | 받는 사람, 보낸 사람의 다른 기기 | `peerId`, `seq` | 열린 대화면 그 `seq` 뒤를 읽기, 아니면 목록·안 읽은 수 | 재연결 때 `afterSeq`로 이어 읽기, 30초 폴링 |
| `social.dm.read` | 개인 | 대화 읽음 | 상대, 내 다른 기기 | `peerId`, `readerId`, `seq` | 읽음 표시·안 읽은 수 다시 읽기 | 재연결 때 |
| `lobby.mine.changed` | 개인 | 테이블 룸의 점유 기록 뒤, 좌석이나 대기 순번이 바뀐 회원에게만 | 그 회원 | `resourceId`(테이블) | `GET /api/tables/:id` 한 번(그 회원의 `myParticipation`) | 재연결 때 목록 다시 읽기, 60초 폴링 |
| `lobby.table.changed` | 공개, 토픽 `lobby` | 테이블 룸의 점유 기록 뒤(1초에 한 번까지) | 로비를 보는 페이지 | 인원 수(`seated`, `bots`, `playing`, `waitlist`, `spectators`, `status`)와 `rev` | 그 카드의 숫자만 바꾼다(더 새 `rev`일 때) | 재연결 때 목록, 60초 폴링 |
| `lobby.table.updated` | 공개, 토픽 `lobby` | 방 만들기, 이름·스테이크·공개 여부·관전·입장 제한 변경(API) | 로비를 보는 페이지 | 그 테이블의 공개 카드 전체(`myParticipation` 없음) | 설정은 더 새 `rev`, 인원은 더 새 `liveRev`를 각각 고른다 | 같음 |
| `lobby.table.removed` | 공개, 토픽 `lobby` | 테이블 닫힘(API, 룸) | 로비를 보는 페이지 | `resourceId` | 목록에서 뺀다 | 같음 |
| `tournament.changed` | 공개, 토픽 `tournaments` | 만들기·등록·시작·탈락·종료·취소·일시정지(API, 룸) | 토너먼트 화면 | `resourceId` | 0–3초 흩어서 목록·상세 다시 읽기 | 재연결 때, 60초(진행 중 상세 15초) 폴링 |
| `service.changed` | 공개 | 공지·점검 생성·변경·삭제(관리자) | 모든 페이지 | `rev`, `spreadMs` | 이미 그 `rev`면 읽지 않는다. 아니면 무작위 대기 뒤 `/api/service/status` | 기존 시각 기반 새로고침(`refreshAt`)과 탭 복귀 |
| `inbox.broadcast` | 공개 | 모든 회원 쪽지함 공지(관리자) | 모든 페이지 | `spreadMs` | 무작위 대기 뒤 안 읽은 수 | 재연결 때, 120초 폴링 |
| `member.vip.changed` | 공개 | 관리자 VIP 지정·해제·색 변경(`PATCH /api/admin/users/:id/vip`). 다른 회원에게 보이는 색이 바뀔 때만(정지된 회원의 변경은 보내지 않는다) | 모든 페이지 | `resourceId`(회원), `revision`(그 회원의 VIP 버전), `vip`(보이는 색, 없으면 `null`). 사유·변경한 관리자는 없다 | 그 회원이 보이는 화면만 그 회원의 색을 바꾼다(친구 목록, 차단 목록, 대화 머리, 게시판 목록·글·댓글, 열린 플레이어 카드, 로비 방장). 아무것도 다시 읽지 않는다. 같거나 오래된 `revision`은 무시한다 | 그 화면의 다음 읽기(D1의 색) |

- 이벤트 이름은 기획안이 예로 든 것보다 적다. 예를 들어 친구 요청·수락·삭제를 `social.friend.changed` 하나로 묶었다. 페이지가 하는 일이 같고(목록을 다시 읽는다), 무엇이 바뀌었는지 말하지 않아야 차단 여부가 새지 않기 때문이다.
- `spreadFor(n)`: 20명까지는 0, 그 뒤로 회원당 10 ms, 최대 30초. 수천 페이지가 같은 초에 읽지 않게 흩는다.
- 테이블 초대는 1:1 메시지의 `invite` 종류라 `social.dm.created`로 온다. 초대를 받아도 자동 바이인, 좌석 생성, 대기 등록은 없다. 링크는 PR #39의 테이블 진입(계속 플레이·대기 현황 확인)을 그대로 탄다.
- **공개 VIP 색(`member.vip.changed`, `apps/web/src/lib/memberVip.ts`).** 페이지는 들은 색을 5분 동안 기억한다. 이벤트보다 먼저 시작해 늦게 끝난 읽기에도 그 색을 얹는다(`withHeardVip`). 그래서 늦은 응답이 새 색을 되돌리지 않는다. 테이블 좌석은 기존 `refreshVipEverywhere()`가 바꾼다. 한계:
  - 정지·정지 해제·역할 변경은 이 이벤트를 보내지 않는다. 열린 화면의 표시는 그 화면의 다음 읽기까지 예전 그대로다.
  - 토너먼트 참가자 목록에는 회원 id가 없어 바꾸지 않는다. 상세 폴링이 다시 읽을 때 반영된다.
  - 지난 핸드 기록과 테이블 채팅 줄은 그때의 표시다.
  - 변경 전에 만들어져 변경 뒤에 도착한 `lobby.table.updated` 카드는 다음 목록 읽기까지 예전 방장 색을 보일 수 있다(서버 시각과 페이지 시각을 비교하지 않는다).
  - 새 이벤트 종류라 허브(게임 워커)가 API보다 먼저 배포되어야 한다(10절 순서와 같다). 거꾸로면 허브가 그 이벤트를 400으로 거절하고, 이벤트만 사라진다(VIP 변경은 그대로 저장된다).

## 5. 로비

1. 로비 화면은 토픽 `lobby`를 먼저 요청한 뒤 `GET /api/tables`를 읽는다. 그래서 읽기가 시작된 뒤 커밋된 변경도 놓치지 않는다.
2. `lobby.table.changed`는 그 카드의 숫자만, `lobby.table.updated`는 카드를, `lobby.table.removed`는 삭제를 마지막 목록 위에 얹는다(`mergeList`).
3. 내 좌석·대기 순번(`myParticipation`)은 공개 이벤트에 없다. `lobby.mine.changed`를 받은 페이지만 `GET /api/tables/:id`를 한 번 읽는다(같은 테이블은 묶음).

**순서와 중복.** `rev`(설정, `tables.updated_at`)와 `liveRev`(인원, `tables.live_updated_at`)는 D1에 쓴 시각이다. 룸이 다시 시작해도 줄지 않는다. 페이지는 둘을 따로 비교한다(`newerCard`, `keepCard`). 늦게 도착한 목록이나 테이블 조회가 더 새 이벤트를 되돌리지 않는다. 같은 `rev`의 목록 행이 와도 인원이 더 오래되었으면 이벤트 카드를 남긴다. 테스트는 `apps/web/test/lobby.test.ts`에 있다.

**몰림.** 룸은 첫 변경을 바로 보내고, 1초 안에 이어진 변경은 1초 뒤 한 번에 보낸다(`LOBBY_PUSH_MS`). 같은 숫자는 다시 보내지 않는다. 관전자 30명이 한꺼번에 드나들 때 화면마다 이벤트는 4개였다(`docs/LOAD_TEST.md` 6.2).

**공개되지 않는 것.** 공개 패킷에는 다음이 없다(통합 테스트 `realtime-public.test.ts`가 패킷 원문에서 확인한다):
- `live_waitlist_users` 원본과 대기자 id.
- 남의 `myParticipation`과 대기 순번.
- 비공개 방의 입장 코드와 그 해시.
- 내부 인증 값.

대기자는 수(`waitlist`)로만 나간다.

**게임 액션은 로비로 가지 않는다.** 베팅, 카드, 턴, 타이머는 테이블 소켓에만 있다. 로비에는 좌석·대기·관전 수, 진행 여부, 열림·닫힘만 간다. 토너먼트 테이블은 로비에 없으므로 보내지 않는다.

## 6. 페이지(클라이언트)

- **소켓은 탭마다 하나다.** 로그인한 동안 `AuthProvider`가 열고(`startRealtime`), 다른 계정으로 바뀌거나 로그아웃하면 닫는다(`stopRealtime`). 닫을 때 세대 번호를 올린다. 그래서 이전 계정 소켓의 늦은 콜백은 아무것도 하지 않고, 이전 계정의 이벤트는 새 계정 화면에 닿지 않는다.
- **중복 제거.** 최근 `eventId` 300개를 기억한다.
- **묶음.** `coalesced()`는 한 번에 하나만 실행한다. 실행 중에 들어온 요청은 끝난 뒤 한 번으로 합친다. 이벤트 10개가 몰리면 요청 2번이다.
- **열릴 때마다 다시 읽기.** 허브는 소켓이 없던 사이의 이벤트를 남기지 않는다. 그래서 화면의 첫 조회와 첫 소켓 사이, 또는 끊긴 사이에 바뀐 것은 이벤트로 오지 않는다. 소켓이 열릴 때마다(첫 `hello`도) 화면마다 등록한 resync가 한 번씩 돈다(페이지를 열면 그 화면의 읽기가 한 번 더 든다):
  - 계정·잔액(`AuthProvider`).
  - 안 읽은 수.
  - 친구 목록과 열린 대화.
  - 쪽지 목록.
  - 내 정보의 원장.
  - 토너먼트.
  - 로비 목록(소켓이 다시 올라오면 한 번 읽는다).
- **숨긴 탭은 이벤트로 읽지 않는다.** 안 읽은 수와 열린 1:1 대화는 숨긴 탭에서 이벤트나 소켓 열림을 받아도 요청하지 않는다. 탭이 다시 보일 때 한 번 읽는다. 대화의 읽기가 이미 나가 있을 때만 그 뒤에 한 번 더 읽는다. 대화 쪽은 E2E `social.spec.ts`가 확인한다.
- **폴링.** 소켓이 끊긴 동안은 원래 간격으로, 열려 있는 동안은 더 느리게 폴링한다. 놓친 이벤트는 최대 느린 폴링 한 번으로 메워진다.

| 화면 | 소켓 없음 | 소켓 연결 |
|---|---|---|
| 로비 목록 | 5초(1분 동안 입력 없으면 30초) | 60초 |
| 안 읽은 수 | 30초 | 120초 + 이벤트 |
| 친구 목록 | 15초 | 60초 + 이벤트 |
| 열린 1:1 대화 | 4초 | 30초 + 이벤트 |
| 토너먼트 목록 | 15초 | 60초 + 이벤트 |
| 토너먼트 상세 | 5초 | 진행 중 15초, 그 밖 60초 + 이벤트 |

## 7. 신뢰성

**보장하는 것**
- 이벤트를 몇 번 받든, 순서가 바뀌든 지갑과 원장은 D1 그대로다. 페이지는 금액을 계산하지 않는다. 관리자 지급을 같은 멱등 키로 다시 보내면 원장 행은 그대로 1개이고, 이벤트도 나가지 않는다(`duplicate: true`). 통합 테스트와 부하 테스트에서 확인했다.
  - 반복으로 받는 것은 그 키의 원장 행과 회원·금액·메모·연결 거래가 같은 요청뿐이다. 보낸 관리자는 달라도 된다. 다른 회원이나 다른 내용에 같은 키를 쓰면 409 `idempotency_conflict`로 거절하고 아무것도 옮기거나 기록하지 않는다(미리보기도 같다).
  - 지급 뒤 감사 기록(`user.chips`)을 못 썼으면 다음 반복이 남긴다. 내용은 요청이 아니라 원장 행에서, 행위자는 처음 지급한 관리자로 남기고 `late: true`를 붙인다. 조건부 INSERT 한 문장이라 첫 시도와 동시에 도착한 반복이 둘 다 남기지 않는다.
- 같은 이벤트를 두 번 받아도 한 번만 처리한다(`eventId`). 오래된 로비 값은 더 새 값을 되돌리지 않는다(`rev`/`liveRev`).
- 소켓이 다시 열리면 화면이 보여 주는 것을 한 번 다시 읽는다.
- 소켓이 없거나 실시간 허브가 죽어도 REST와 폴링으로 모든 화면이 동작한다(E2E `lobby.spec.ts`가 소켓을 거절한 채 확인한다).

**보장하지 않는 것**
- **전달은 최선 노력이다. 실시간 아웃박스는 두지 않았다.**
  - 허브에 닿지 못한 이벤트는 사라진다.
  - 그 페이지는 다음 재연결이나 폴링에서 따라잡는다. 소켓이 열린 채 이벤트 하나만 잃으면 최대 느린 폴링 한 번만큼 늦는다.
  - 칩 지급, 제재, 시스템 쪽지 같은 중요한 사건은 D1에 남아 있다(원장, 감사, 쪽지). 이벤트는 그것을 다시 읽으라는 알림일 뿐이다.
  - 로비 변경을 영속 이벤트 표에 쌓지 않는다.
- **순서.** 서로 다른 자원 사이의 순서는 보장하지 않는다. `occurredAt`으로 정렬하지 않는다.
- **로그아웃 직후.** revoke가 닿지 않은 소켓은 최대 약 5분 열려 있을 수 있다(3절).
- **관리자 콘솔은 실시간이 아니다.** 9절.

## 8. 비용

- **하이버네이션.** 소켓은 이벤트 사이에 하이버네이션한다. ping은 허브를 깨우지 않는다.
- **허브 알람.** 소켓이 있는 허브는 5분마다 한 번 깬다. D1 batch 하나로 소켓당 약 1–2행을 읽는다(`sessions` 기본 키와 `users` 기본 키). 소켓이 없으면 알람도 없다. 최근 로그아웃 기록이 남아 있으면 1분 뒤 한 번 더 깨서 지운다.
- **공개 이벤트.** 받는 페이지가 D1을 읽지 않는다. 바뀐 테이블의 공개 카드나 숫자가 이벤트에 들어 있다. 방 만들기·닫기는 API가 카드를 만들려고 D1을 한 번(2행) 읽는다. 보는 사람 수와 상관없다.
- **폴링 감소.** 로비를 보는 1,000명 기준으로 `/api/tables` 읽은 행은 분당 288,000에서 24,000으로 준다(계산, `docs/LOAD_TEST.md` 6.3).
- **측정.** 요청별 D1 행과 쿼리 계획은 `docs/LOAD_TEST.md` 6.3–6.4에 있다. `D1_STATS`(응답 헤더 `x-d1-*`)는 로컬 측정 전용이다.

## 9. 하지 않은 것

- 관리자 콘솔 실시간(관리자 사이 동기화). 콘솔은 기존 읽기와 버전 충돌 검사를 그대로 쓴다.
- 토너먼트 초대, 리더보드, 플레이 업적, 9인 토너먼트.
- 실시간 아웃박스, 탭 사이 `BroadcastChannel`. 탭마다 소켓을 따로 열고, 회원당 10개로 제한한다.
- Web Push 변경. 없다.

## 10. 배포

- **D1 마이그레이션은 없다.** game-worker에 DO 마이그레이션 `v3`(`new_sqlite_classes: ["RealtimeHub"]`)를 더했다. `v1`(`TableRoom`)과 `v2`(`PresenceHub`)는 그대로다. api의 `REALTIME` 바인딩은 `script_name`으로 game-worker의 `RealtimeHub`를 가리킨다(dev와 production 둘 다).
- **순서는 game-worker → api(web 포함) → admin이다**(`docs/DEPLOYMENT.md` 3절과 같다).

**섞인 버전**
- api만 새것일 때: 바인딩이 가리키는 클래스가 아직 없어 `/ws/realtime`이 실패한다. 발행도 실패하지만 요청은 실패하지 않는다. 새 페이지는 소켓 없이 원래 간격으로 폴링한다. 이 경우는 로컬에서 재현하지 않았다.
- game-worker만 새것일 때: 소켓을 여는 페이지가 없다. 룸이 보내는 로비 이벤트는 빈 허브에 닿고 버려진다. 허브 요청 비용만 든다.
- 이전 web 클라이언트: 소켓을 열지 않고 이전 간격으로 폴링한다. 이벤트 타입이나 기존 API 응답은 더하기만 했다.

**되돌리기**
- api나 web은 이전 버전으로 되돌리면 된다. 페이지는 폴링으로 돌아간다.
- game-worker를 되돌릴 때는 `RealtimeHub` 클래스와 `v3` 태그를 남긴다. Cloudflare 문서 기준으로, 클래스를 빼려면 `deleted_classes` 마이그레이션이 따로 필요하다. 이 저장소에서 시험하지 않았다.

**운영에 넣지 않는 값.** `REALTIME_SWEEP_MS`와 `D1_STATS`는 로컬 테스트·측정 전용이다. 배포 설정(`wrangler.jsonc`)에 넣지 않는다. api는 브라우저가 보낸 `x-jc-sweep-ms` 헤더를 지운다. 허브는 1–300초 범위 밖의 값을 무시한다.

**배포 뒤 확인할 것**
- 허브 하나의 CPU 시간과 팬아웃 지연(샤드 수의 근거).
- 엣지의 이벤트 지연 p95.
- 허브 알람의 D1 행.
- 혼잡한 허브에서 닫힘 프레임이 늦게 가는지(아래).

## 11. 로컬 테스트 메모

- **닫힘 프레임이 늦게 간다.** 로컬 `wrangler dev`(workerd)에서는 허브가 서버 쪽에서 소켓을 닫아도, 클라이언트는 그 허브가 약 10초 동안 쉬어야 닫힘을 받는다. 서버 쪽에서는 `ws.close()` 뒤로 그 소켓에 아무것도 보내지 않는다. 그래서 끝난 세션이 이벤트를 더 받지는 않는다. 운영에서도 바쁜 허브의 닫힘 프레임이 늦는지는 확인하지 않았다.
- **통합 테스트의 점검 간격은 15초다.** 통합 테스트 Worker는 `REALTIME_SWEEP_MS = 15000`(`tests/support/global-setup.ts`)으로 허브가 15초마다 D1을 확인하게 한다. 그래야 revoke가 사라진 로그아웃이 소켓을 닫는 것을 볼 수 있다. 5초로 하면 알람이 허브를 계속 깨워 위의 10초 쉼이 오지 않고, 닫힘이 클라이언트에 닿지 않는다. 그 실패를 실제로 봤다(`docs/TEST_REPORT.md`).
- **부하 하네스는 운영 값으로 돈다.** `pnpm test:load`, 5분.
