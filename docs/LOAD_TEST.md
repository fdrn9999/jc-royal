# 부하 시나리오 (로컬)

> **여기 있는 숫자는 모두 개발 PC 한 대의 로컬 `wrangler dev`(workerd) 결과다.** Cloudflare 엣지, 운영 환경, 실제 네트워크에서는 부하 테스트를 하지 않았다. 운영 용량이나 지연을 약속하는 근거로 쓰지 않는다.

## 1. 무엇을 하는가

`tests/load/tables.load.ts`가 테이블 여러 개를 동시에 WebSocket으로 진행한다.

1. 테이블 `load-0 … load-(N-1)`을 시드한다(6석, 5/10, 바이인 100–2,000). 상태는 `tests/.state/load`에 따로 둔다(통합·E2E와 공유하지 않음).
2. 테이블마다 플레이어와 관전자 계정을 만든다(동시 8개).
3. 로비 폴러가 테스트 내내 `GET /api/tables`를 1초마다 부른다.
4. 모든 소켓을 동시에 연결한다. 플레이어는 1,000칩으로 착석한다.
5. 봇이 서버가 보낸 합법 액션 중에서 고른다. 15%는 최소 벳·레이즈, 나머지는 체크·콜이다. 각 테이블이 지정한 핸드 수를 마치면 전원이 `leave`를 보내고, 진행 중인 핸드가 끝날 때까지 계속 액션한다.
6. 끝나면 정합성을 검사하고 `tests/.state/load-report.json`을 남긴다. 서버 로그는 `tests/.state/load-worker.log`에 남는다. 액션마다 시각·지연·테이블은 `tests/.state/load-actions.json`에, 로비 요청과 기준 시각은 `tests/.state/load-timeline.json`에 남는다(5절 분석에 씀).

`wrangler dev`의 로컬 트레이스 저장소(요청마다 기록, 기본으로 켜짐)는 이 하네스에서 끈다(`tests/load/setup.ts`). 켜 두면 실행 중에 로컬 런타임 전체가 최대 1초 남짓 멈췄다(5절). 켜고 재려면 `X_LOCAL_OBSERVABILITY=true`를 준다.

**측정 항목**
- 지연(p50/p95/p99/최대): 가입, WS 연결, 착석, 액션 왕복(보낸 뒤 결과 상태가 올 때까지), 팬아웃(같은 테이블의 플레이어·관전자 중 가장 늦게 새 상태를 받은 소켓), 일어서기, 로비 목록. 백분위는 정렬한 값의 `floor(p/100 × n)`번째(0부터)를 쓴다. 표본이 적은 항목(착석·연결·일어서기)은 표준 nearest-rank보다 한 칸 높은 값이 나올 수 있다.
- 메시지 수와 바이트: 클라이언트→서버, 서버→클라이언트(핸드당).
- D1 행 증가: `hands`, `hand_players`, `chip_ledger`, `table_sessions`, `rate_limits`, `sessions`, `admin_audit_log`, `reconciliation_events`.

**통과 조건**(하나라도 어기면 실패)
- 클라이언트 오류, 서버 `error` 메시지, 예상하지 못한 소켓 종료, 팬아웃 누락, 로비 실패가 모두 0.
- 관리자 정합성 검사가 200이고 불일치 0, 열린 착석 세션 0.
- 플레이어 지갑 합계 = 테이블 수 × 플레이어 수 × 10,000. 관전자 지갑은 10,000 그대로.
- 테이블마다 기록된 핸드가 지정 수 이상. 모든 핸드는 참가자 2명 이상이고 `SUM(net) = 0`. 칩을 잃은 플레이어는 일어서므로, 칩이 남은 플레이어가 2명 미만으로 6초 넘게 이어진 테이블은 거기서 멈추고 보고서 `hands.stoppedEarly`에 핸드 수와 함께 남긴다(이 테이블은 핸드 수 조건에서 빼지만, 모든 테이블이 일찍 멈추면 실패). 플레이어 2–3명에 `LOAD_HANDS`를 크게 주면 이렇게 될 수 있다.
- 닫힌 착석 세션 = 테이블 수 × 플레이어 수. 원장 증가 = 바이인(세션 수) + 환급(잔액이 남은 세션 수).

## 2. 실행

```bash
pnpm test:load                                                  # 기본: 10테이블 × (플레이어 4 + 관전 2), 5핸드
LOAD_TABLES=30 LOAD_PLAYERS=6 LOAD_SPECTATORS=4 pnpm test:load  # PowerShell: $env:LOAD_TABLES='30'; ...
```

| 변수 | 기본값 | 범위 | 뜻 |
|---|---|---|---|
| `LOAD_TABLES` | 10 | 1–60 | 동시에 진행하는 테이블 수 |
| `LOAD_PLAYERS` | 4 | 2–6 | 테이블당 착석 플레이어 |
| `LOAD_SPECTATORS` | 2 | 0–20 | 테이블당 관전 소켓 |
| `LOAD_HANDS` | 5 | 1–200 | 테이블마다 진행할 핸드 수 |
| `LOAD_PORT` | 8796 | | 로컬 Worker 포트(통합 8799, E2E 8798과 겹치지 않음) |

`pnpm test:load`는 6절의 실시간 시나리오(`tests/load/realtime.load.ts`)와 7절의 관제센터 시나리오(`tests/load/monitor.load.ts`)도 같은 Worker에서 차례로 돌린다(파일을 동시에 돌리지 않음). 시나리오들이 같은 테이블에 앉으므로, 테이블 시나리오의 착석 세션 검사는 자기 플레이어의 세션만 센다. 관제센터 시나리오가 먼저 돌아 닫힌 테이블 5,000개를 남겨도 나머지 둘은 통과했다(2026-10-30, 기본값으로 세 파일 모두 통과, 192초). 실시간 시나리오만 돌리려면 다음과 같이 한다.

```bash
pnpm exec vitest run --config tests/load/vitest.config.ts tests/load/realtime.load.ts
RT_VIEWERS=1000 pnpm exec vitest run --config tests/load/vitest.config.ts tests/load/realtime.load.ts
TEST_D1_STATS=1 pnpm exec vitest run --config tests/load/vitest.config.ts tests/load/realtime.load.ts   # D1 행 수(6절)
```

| 변수 | 기본값 | 범위 | 뜻 |
|---|---|---|---|
| `RT_VIEWERS` | 100 | 10–2,000 | 실시간 소켓을 연 로비 화면(회원 1명당 1개) |
| `RT_CHANGES` | min(6, `LOAD_TABLES`−1) | 1–59 | 한 명씩 앉았다 일어서는 테이블 수 |
| `RT_BURST` | min(30, `RT_VIEWERS`) | 1–`RT_VIEWERS` | 한 테이블을 동시에 여는 관전자 |
| `RT_GRANTEES` | min(20, `RT_VIEWERS`−`RT_CHANGES`−1) | 1–`RT_VIEWERS` | 관리자가 칩을 지급하는 회원 |
| `RT_DEVICES` | 3 | 1–10 | 지급받는 회원마다 연 페이지 수(허브 하나에 회원당 소켓 10개까지) |
| `TEST_D1_STATS` | 끔 | `1` | 응답마다 D1이 센 읽은 행·쓴 행을 `x-d1-*` 헤더와 Worker 로그에 남긴다(`apps/api/src/lib/d1-stats.ts`). 배포 설정에는 넣지 않는다 |

통합 테스트(`pnpm test:integration`)와 CI에는 포함하지 않는다. 느리고, 합격·불합격보다 측정이 목적이다.

## 4. 읽는 법과 한계

- **한 프로세스에서 모든 테이블이 돈다.** 운영에서는 테이블마다 Durable Object가 따로 돈다. 테이블 수가 늘수록 지연이 커진 것(기본 → 넓게)은 이 PC의 CPU와 같은 PC에서 도는 테스트 클라이언트(넓게 실행에서 상태 메시지 146 MB를 파싱)의 몫이 크다. 운영의 테이블 수 확장성을 보여 주지 않는다.
- **테이블 하나 안은 직렬이다.** DO는 한 테이블의 메시지를 하나씩 처리하므로, 이 부분의 지연은 운영에서도 테이블 인원·관전자 수에 따라 늘어난다.
- **지속 실행의 꼬리 지연(p99 440 ms, 최대 1.2 s)은 5절에서 분석했다.** 게임 도중의 멈춤은 로컬 트레이스 저장소와 함께 나타났고, 테이블이 끝나며 일어서는 구간의 멈춤은 원인을 찾지 못했다. 둘 다 로컬 개발 도구에서 본 현상이고 운영 지연의 근거가 아니다.
- **핸드 속도는 서버 타이머가 정한다.** 핸드 사이 4초(`BETWEEN_HANDS_MS`, 2026-10-19부터 회원이 카드를 받은 핸드는 카드를 보일지 고르는 1.5초를 더해 5.5초, `afterHandMs`), 첫 핸드 2.5초. 테이블당 약 5.5초에 한 핸드(봇은 즉시 액션, 위 기록은 1.5초를 더하기 전)라 사람이 하는 테이블보다 훨씬 빠르다. 부하 봇은 회원 계정이므로 이 변경 뒤에는 핸드마다 약 1.5초 길어진다(다시 재지 않음).
- **운영과 다른 설정**: PBKDF2 1,000회(운영 100,000회)라 가입 지연은 운영 비용이 아니다. IP 레이트 리밋 1,000배 완화. 회원 방 유휴 종료 8초.
- **웹 클라이언트와 다른 점**: 부하 클라이언트는 앱 핑(`{t:'ping'}`)을 보내지 않는다. 웹 클라이언트는 서버 메시지가 25초 동안 없을 때만 보내므로, 핸드가 계속 도는 이 시나리오에서는 웹 클라이언트도 거의 보내지 않는다. 핑은 런타임 자동 응답이 받으므로 룸 처리량에 들어가지 않는다(비용 영향은 `docs/DEPLOYMENT.md` 5절).
- **보지 않은 것**: 엣지 지연, 지역 배치, isolate 재시작·축출, Hibernation 후 깨우기 비용, 실제 과금, 운영 D1의 동시 쓰기 한도, 브라우저 렌더링.

여섯 번 모두 300핸드, 오류·끊김 0, 칩 보존 600,000 = 600,000, 정합성 불일치 0, 열린 세션 0이었다. 실행 6은 PART A를 모두 마친 코드로 나중에 돌렸다(`docs/test-logs/load-part-a-sustained.json`). 첫 테이블이 153.9초에 끝났고, 250 ms 이상 액션 26개가 모두 그 전 150.7–152.4초에 9개 테이블에서 함께 나왔다(핸드를 끝낸 액션은 0개). 같은 때 로비 목록도 265·288 ms로 느렸다.

**관찰**
- 게임 중 멈춤은 트레이스를 켠 3회 모두에 있었다. 끈 3회 중에는 실행 6에서 1회(약 1.7초, 최대 479 ms) 나왔다.
- 종료 구간 멈춤은 켠 3회 중 2회, 끈 3회 중 1회에 있었다. 이 멈춤이 있던 실행은 일어서기 p95도 높았다(532 / 1,060 / 652 ms, 없던 실행은 86 / 278 ms).
- 한 구간 안에서 여러 테이블이 같은 순간에 함께 느려졌다. 실행 5에서는 테이블 4개가 20 ms 안에 같이 느려졌다. 테이블 하나가 아니라 로컬 런타임 전체가 멈춘 모양이다.
- 핸드를 끝낸 액션의 p50은 수정 뒤 39 → 15–16 ms(트레이스 켬)로 줄었다. 결과를 D1 기록보다 먼저 보낸 효과다. 꼬리(p99·최대)는 이 수정으로 설명되지 않았다.
- 실행 횟수가 적다(켬 3회, 끔 3회). 비율은 참고로만 본다.

| 가설 | 근거 | 판정 |

**원인**
- 게임 중 멈춤은 로컬 트레이스 저장소와 함께 자주 나타났다. 켠 3회 모두에 있었고, 끄고 나서는 3회 중 1회(실행 6)로 줄었지만 없어지지는 않았다. 트레이스 저장소만으로는 설명되지 않는다.
  - 이 저장소는 요청마다 기록하는 SQLite다. 실행 3이 끝났을 때 16.5 MB와 WAL 4.4 MB였다.
  - 실행 3에서 본 파일을 72번(약 2초마다) 썼다. 멈춤(132.5초) 바로 전에 쓰기(131.70초)가 있었고, 그 뒤 7초 동안 쓰기가 없었다.
  - 다른 쓰기 뒤에는 멈춤이 없었다. 저장소 안의 어떤 동작이 런타임을 멈추는지는 밝히지 못했다.
  - 실행 6의 멈춤은 트레이스를 끈 상태였다. 이 실행에서는 성능 카운터와 파일 쓰기 시각을 기록하지 않아 원인을 더 좁히지 못했다.
- 종료 구간 멈춤은 원인을 찾지 못했다.
  - 트레이스를 꺼도 1회 나왔다. 일어서기(정산과 D1 쓰기)가 몰리는 때와 겹친다.
  - 실행 2의 이 구간에서 workerd CPU가 낮았다. 계산이 아니라 무언가를 기다린 것으로 보인다. 이 이상은 추적하지 않았다.

**운영에 대한 의미**
- 운영에는 이 로컬 트레이스 저장소가 없다. 운영에서는 테이블마다 Durable Object가 따로 돈다.
- 그래서 위 멈춤은 운영 지연의 근거가 아니다. 운영의 꼬리 지연은 재지 않았다.
- 바꾼 것: 부하 하네스는 트레이스를 기본으로 끈다. 통합·E2E 하네스는 그대로 둔다.

## 6. 플랫폼 실시간 허브와 D1 행 (2026-10-28)

> 이 절의 숫자도 개발 PC 한 대의 로컬 `wrangler dev`(workerd) 결과다. 실시간 허브 4개(`rt-0 … rt-3`), 테이블 방, API가 모두 한 프로세스에서 돌고, 테스트 클라이언트도 같은 PC에서 돈다. 엣지 지연, 실제 네트워크, 과금이 아니다. 구조는 `docs/REALTIME.md`.

### 6.1 무엇을 하는가

`tests/load/realtime.load.ts`:

1. 회원 `RT_VIEWERS`명이 로비 화면처럼 실시간 소켓(`/ws/realtime`, 토픽 `lobby`)을 연다(동시 25개씩).
2. **좌석**: 테이블 `load-0 … load-(RT_CHANGES−1)`에 한 명씩 앉았다가 일어선다. 테이블 방이 보내는 `lobby.table.changed`를 모든 화면이 받는지 본다(변경 사이 1.1초).
3. **방**: 회원이 방을 만들고 닫는다. API가 보내는 `lobby.table.updated`와 `lobby.table.removed`를 본다.
4. **관전 몰림**: 관전자 `RT_BURST`명이 테이블 하나를 동시에 열고 동시에 닫는다. 방은 관전자 수를 1초에 한 번까지만 보낸다(첫 변경은 바로, 나머지는 1초 뒤 한 번).
5. **칩 지급**: 관리자가 회원 `RT_GRANTEES`명에게 500칩씩 지급한다. 회원마다 페이지가 `RT_DEVICES`개 열려 있다. 같은 멱등 키로 한 번씩 더 보낸다.
6. 끝나면 받은 이벤트 전체에서 중복(같은 `eventId`), 누락, 끊긴 소켓을 세고, D1의 최종 상태(원장 행, 잔액)를 읽는다. 보고서는 `tests/.state/realtime-load-report-<RT_VIEWERS>.json`이다.

지연은 요청을 보내기 직전부터 각 화면이 이벤트를 받은 때까지다. 백분위는 1절과 같이 계산한다.

**통과 조건**(하나라도 어기면 실패)
- 연결 실패, 클라이언트 오류, 누락, 중복, 끊긴 소켓이 모두 0.
- 관전 몰림 뒤 `GET /api/tables/:id`의 관전자 수가 `RT_BURST`, 모두 나간 뒤 0.
- 지급받은 회원의 페이지마다 `wallet.changed`를 정확히 1번 받는다. 재시도(`duplicate: true`) 뒤에는 이벤트가 0개다.
- 회원마다 `admin_adjust` 원장 행이 1개이고 잔액이 10,500이다.

- **100명 → 1,000명**에서 좌석 변경 p95가 24 → 64 ms, 방 이벤트 p95가 77 → 202 ms로 늘었다. 허브 4개와 1,000개 소켓, 26,144개 이벤트를 파싱하는 테스트 클라이언트가 모두 한 PC에서 돈 결과다. 엣지에서 허브는 각각 Durable Object로 따로 돈다. 이 값은 운영 확장성을 보여 주지 않는다.
- 가입은 1,000명 실행에서 p50 1,014 ms, p99 4,619 ms, 최대 5,610 ms였다(PBKDF2 1,000회, 동시 16개). 운영 비용이 아니다.
- 이 PC에서 본 일시 오류: 실행 중 가입 요청 하나가 wrangler 프록시의 `Network connection lost`(500)로 실패한 적이 1번 있다. 전역 준비에서 `Migration 0029_presence_push.sql failed … bad port`가 1번 있었다. 둘 다 다시 돌리니 나오지 않았다(같은 코드).

**샤드 수(`REALTIME_SHARDS` = 4)를 이 측정으로 정하지 않았다.** 로컬에서는 허브가 모두 한 프로세스라 허브 하나의 한계를 잴 수 없다. 개인 이벤트는 그 회원의 허브 하나에만 가고, 공개 이벤트(로비·공지·토너먼트) 1건은 허브 4개에 1번씩 간다. 보는 사람이 몇 명이든 발행자의 허브 요청 수는 4다. 4는 시작값이다. 엣지에서 허브 하나의 CPU 시간과 팬아웃 지연을 재고 정해야 한다(배포 뒤 확인 항목, `docs/REALTIME.md`).

### 6.4 쿼리 계획(EXPLAIN QUERY PLAN)

통계를 켠 실행의 Worker 로그에서 서로 다른 SQL 53개를 모아, 같은 실행의 로컬 D1 파일에 `EXPLAIN QUERY PLAN`을 돌렸다(`node:sqlite`, 읽기 전용).

- 폴링되는 경로는 모두 인덱스를 탄다. 예: `sessions_token_uq`, `users` 기본 키, `tables_status_idx`, `tsess_user_idx`, `messages_user_idx`, `dm_unread_idx`, `dm_pair_seq_uq`, `friendships_b_idx`, `tournaments_status_idx`, `maintenance_windows_ends_idx`, `service_notices_live_idx`.
- 전체 스캔으로 나온 4개:
  - `delete from email_verifications where expires_at < ?`: 인증 메일 요청마다 지난 행을 지운다. 수명이 짧은 행만 남는 표라 최대 15행을 읽었다. 그대로 둔다.
  - 관리자 첫 생성의 `select id from users where role = ? limit ?`: 한 번만 돈다.
  - `/api/service/status`의 `SCAN (subquery-2)`: 표가 아니라 쿼리 안의 하위 결과다.
  - 방 만들기 `INSERT INTO tables`의 `SCAN direct_messages`, `SCAN table_sessions`: 외래 키 검사 계획이다. 실제로는 기다리는 위반이 없으면 건너뛰고, 잰 읽은 행은 1이었다.

**고친 것: 관리자 칩 재시도의 감사 기록 조회**(`apps/api/src/routes/admin.ts`). 같은 멱등 키로 다시 온 지급은 첫 시도의 `user.chips` 감사 행이 있는지 찾는다. D1에 `ANALYZE` 통계(`sqlite_stat1`)가 없어서 쿼리 계획이 `audit_action_idx`(지금까지 쓰인 모든 `user.chips` 행)를 골랐다. 지급이 쌓일수록 읽는 행이 늘어난다. 인덱스를 새로 만들지 않고 `+action`으로 `action` 조건만 인덱스 선택에서 빼서 `audit_target_idx`(그 회원의 행)를 타게 했다. 결과는 같다.

| 재시도 20회(지급 20회 뒤) | 읽은 행 최소 / 최대 / 평균 |
|---|---|
| 고치기 전 | 1 / 20 / 10.5 (그때까지의 지급 수만큼 늘어남) |
| 고친 뒤 | 1 / 1 / 1 |

이 변경 뒤 관리자 칩·멱등·감사 통합 테스트(`admin`, `admin-concurrency`, `economy`, `realtime`)를 다시 돌려 62개 모두 통과했다. 늦게 쓰는 감사 행(`late: true`) 경로도 들어 있다.

**새 인덱스는 만들지 않았다.** 측정한 경로에서 근거가 나온 것은 위 하나였다. (이 실행의 데이터 기준이다. 7절에서 닫힌 기록을 쌓고 다시 재어, 근거가 나온 부분 인덱스 하나를 더했다.)

**남은 후보(바꾸지 않음)**: 반복 신고 대상 목록(`apps/api/src/routes/reports.ts`의 정지 횟수 하위 쿼리, `a.action = 'user.suspend'`)도 같은 계획을 고른다. 대상마다 `audit_action_idx`로 모든 `user.suspend` 행을 읽는다. `+a.action`이면 `audit_target_idx`를 탄다(같은 D1 파일의 `EXPLAIN QUERY PLAN`). 관리자 화면 하나만 쓰고 부하 시나리오에 없어서 읽은 행을 재지 않았다. 재고 나서 고친다.

고치기 전과 뒤는 다른 실행이라 기록 전 값이 1–4행 다르다. 원인은 같은 실행의 로컬 D1 파일 사본에 `EXPLAIN QUERY PLAN`을 돌려 확인했다(`node:sqlite`, 읽기 전용). D1에는 `ANALYZE` 통계가 없어 SQLite가 인덱스를 규칙으로 고른다(6.4).

**고친 것**

1. **닫힌 테이블에 남은 좌석**(`seatedOnClosed`, `apps/api/src/routes/admin-monitor.ts`). `JOIN`이면 SQLite가 `SEARCH t USING INDEX tables_status_idx (status=?)`로 모든 닫힌 테이블부터 읽었다(+5,001행). `CROSS JOIN`으로 순서를 고정해 열린 좌석(`SCAN s USING COVERING INDEX tsess_…`, 지금 앉아 있는 사람 수만큼)에서 시작하고 테이블은 기본 키(`SEARCH t USING INDEX sqlite_autoindex_tables_1 (id=?)`)로 찾는다. 대시보드(`apps/api/src/lib/ops.ts`)는 이미 이렇게 해서 83행 그대로였다.
2. **한 회원의 열린 좌석**(`user_id = ? AND status = 'seated'`). 인덱스가 `tsess_user_idx(user_id)`뿐이라 그 회원이 앉았던 모든 좌석(닫힌 것 포함)을 읽었다(로비 +2,000, 회원 검색 +2,000). **부분 인덱스 `tsess_seated_user_idx`를 더했다**(`packages/db/migrations/0037_seated_user_index.sql`):
   ```sql
   CREATE INDEX `tsess_seated_user_idx` ON `table_sessions` (`user_id`) WHERE status = 'seated';
   ```
   열린 좌석만 들어 있다. 이 조회는 로비의 `myParticipation`(`routes/tables.ts`), VIP 반영(`lib/room.ts`, `routes/admin-vip.ts`), 자동 충전(`lib/refill.ts`), 관리자 회원 상세(`routes/admin.ts`), 봇 고르기(`apps/game-worker/src/bots.ts`), 관제 회원 검색에서 돈다. 봇 계정은 하루 종일 앉고 일어나서 닫힌 좌석이 가장 빨리 쌓이고, 방이 빈 봇을 찾을 때마다 봇마다 이 조회를 한다. 계획은 `INDEX tsess_user_idx (user_id=?)`에서 `INDEX tsess_seated_user_idx (user_id=?)`로 바뀐다. 기록 조회(`user_id = ? ORDER BY created_at`)는 그대로 `tsess_user_idx`를 쓴다.
3. **테이블 관리의 활성 목록**(`routes/admin.ts`). `status <> 'closed'`는 인덱스를 타지 못해 모든 테이블을 읽었다. 로비처럼 `status IN ('open', 'closing')`으로 바꿔 `tables_status_idx`를 탄다. 결과는 같다.

**회귀 테스트**: `tests/integration/seat-plans.test.ts`가 실제 마이그레이션 파일로 메모리 SQLite를 만들고, 소스에서 옮긴 문장(소스에 그대로 있는지도 검사)의 계획을 본다. 0037을 빼면 로비 계획이 `SEARCH table_sessions USING INDEX tsess_user_idx (user_id=?)`로 돌아가고, 예전 `JOIN`은 `tables_status_idx`로 시작해 둘 다 실패함을 확인했다.

**인덱스 비용(재지 않음)**: 좌석이 열릴 때 인덱스 항목 하나를 쓰고, 닫힐 때(`seated` → `closed`) 지운다. 항목 수는 지금 열린 좌석 수다. 이 시나리오의 착석·일어서기에서 쓴 행은 따로 세지 않았다. 마이그레이션은 만들 때 `table_sessions`를 한 번 읽는다. 운영 `table_sessions`의 행 수는 재지 않았다. 되돌리려면 `DROP INDEX tsess_seated_user_idx;`면 된다(결과는 같고 계획만 예전으로 돌아감). CI 배포는 D1 마이그레이션을 Worker보다 먼저 적용한다(`docs/DEPLOYMENT.md`).

- state를 받고 React 커밋까지(`receiveToCommit`) p95는 desktop 5–24 ms, phone 24–41 ms, slowphone 41–131 ms다. 표본이 실행마다 14–26개라 꼬리가 거칠다. 도구의 `receiveToFrame`(그 뒤 rAF 타임스탬프 − 받은 시각)은 커밋까지보다 작게 나온 실행이 있어(6인 slowphone 19 대 128 ms) 인용하지 않는다.
- 프레임이 떨어지는 병목은 측정에서 나오지 않았다. 그래서 렌더링 코드는 바꾸지 않았다.

### 8.6 이 PC의 일시 오류: `bad port`

`TEST_D1_STATS=1` 실행의 전역 준비가 두 번 연달아 실패했다. 0023에서 한 번, 0034에서 한 번이고, 메시지는 `Migration … failed … bad port`였다. 세 번째에 통과했다(같은 코드). 6.2에 적은 0029 실패도 같은 메시지다.

**가장 그럴듯한 원인**: 이 PC의 동적 포트 범위가 1024부터 시작한다.
- `netsh int ipv4 show dynamicport tcp`의 결과는 1024부터 13,977개였다. Windows 기본값은 49152부터다.
- Node의 `fetch`는 Fetch 표준이 막는 포트에 `bad port`로 실패한다. `fetch('http://127.0.0.1:6000/')`은 `bad port`, 같은 범위의 열리지 않은 포트(14999)는 `ECONNREFUSED`였다.
- 로컬 D1이 이 범위에서 막힌 포트를 받으면 그 마이그레이션이 실패한다. 실패한 마이그레이션이 실행마다 다른 것과 맞는다.
- 실패한 실행에서 D1이 실제로 받은 포트는 기록하지 않았다.

**분류**: 환경. PC의 포트 설정은 바꾸지 않았다.

### 9.6 실패한 실행

1. **8단계 r2의 실시간 100명 시나리오**: 가입 단계에서 `POST /api/auth/email-verification/request`가 500으로 실패했다. 메시지는 miniflare 진입 Worker의 `Network connection lost`이고, 같은 실행의 테이블·관제 시나리오는 통과했다.
   - 가설과 근거:
     - (1) V3의 코드 결함: 버렸다. 이 경로(`auth.ts`)는 V3에서 탈퇴 정리 한 줄만 바뀌었고, 같은 코드가 r1·r3·r4에서 100명 가입을 모두 통과했다.
     - (2) 리소스 부족: 가능성이 낮다. 시작할 때 확약 가능 메모리가 18.5 GB였다.
     - (3) 로컬 workerd·miniflare 안의 연결이 한 번 끊김: 가장 그럴듯하지만 확인하지 않았다. Worker 로그는 다음 실행이 덮어써서 남지 않았고, 그 실행의 오류 줄 수는 0이었다.
   - 분류: 테스트 환경 문제(원인 미확정). 같은 구성으로 r4를 더 돌려 대신했다.
2. **main의 렌더링 측정 첫 시도**: 웹 서버 준비가 `Migration 0030_push_sent_idx.sql failed … bad port`로 실패했다(0001–0029는 적용됨). 8.6과 같은 동적 포트 범위 문제다. 분류: 테스트 환경 문제. 다시 돌려 통과했다. PC 설정은 바꾸지 않았다.

### 9.7 알려진 병목과 판단

측정에서 V3가 만든 병목은 나오지 않았다. 그래서 8단계에서는 성능 코드를 바꾸지 않았고, `memo`·캐시·큐도 더하지 않았다. 개선도 주장하지 않는다.

- **번들 한도**: 647 / 650 KB. 첫 화면에 새 기능을 더하려면 다른 것을 지연 로드로 옮기거나 한도를 다시 정해야 한다. 가장 가까운 위험이다.
- **착석 약 180 ms**: 동시 착석이 서로 기다리는 시험 구성의 값이다(8.4). 바뀌지 않았다.
- **로비 목록 p99 430–530 ms**: 표본이 실행마다 31–32개라 p99가 사실상 최댓값이다. 두 트리 모두 있다.
- **관제의 닫힌 기록 읽기**: 10,005·15,063행. 7.3의 '남은 것' 그대로다.
- **정산 뒤 D1 작업**: 5단계 상세 통계와 7단계 도전과제가 정산 뒤 batch를 늘렸다. 화면에 결과가 늦게 뜨지는 않는다(9.1). 그 읽기·쓰기 행과 운영 D1에서의 시간은 재지 않았다.
- **MTT**: 부하 시나리오가 없다. 100명 MTT 부하를 돌리지 않아 정원을 60으로 두었다(`docs/TOURNAMENT.md`).
- 운영(엣지) 측정은 하지 않았다. 이 절의 값을 운영 값으로 옮기지 않는다.
